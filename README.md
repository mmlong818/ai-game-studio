# AI 游戏工坊（工作名）

一个中文优先、面向非程序员的 AI 游戏制作平台：用户描述玩法，系统把想法转为玩法合同，选择合适的 2D 或 3D 运行时，生成代码与资源，在隔离环境中构建并自动试玩，最后把游戏部署到独立网址，并按需提供存档、排行榜和多人所需的服务器数据能力。

当前阶段：**第六个可运行产品切片**。这不是已完成的产品，也不是竞品复刻工程。

## 已经可以运行的第一版

- React 工作台：一句中文想法即可生成玩法合同；成熟模板可直接修改，另有 AI 实验玩法承接未模板化创意。
- 渐进式创建：第一层提供一句话、十二类 2D 玩法、独立 Web 3D 入口和六种可见画面风格（经典、沉稳、时尚、软萌、简笔画、色块）；经典拖拽拼图支持在创作时和试玩时替换横图、竖图或方图。
- Node API：提供健康检查、项目列表、项目详情和受控发布接口。
- Docker PostgreSQL 18.6：真实保存项目、玩法规格、构建步骤、不可变版本和发布记录；首次启动且数据库为空时，只读导入旧 SQLite，旧文件不被覆盖。
- MakePlay 式独立制作页：每个项目进入 `/projects/:id` 专属网址，左侧按时间展示分析、文档、代码、资源、测试和交付步骤，右侧加载真实试玩版本；不使用遮挡首页的浮动弹层。
- 统一游戏大厅：`/games` 只展示已经发布并在线的交付游戏，所有稳定玩家入口集中在一个页面。
- 本地构建编排：2D 与 3D 项目都可以生成独立 HTML/CSS/JS、四份制作文档、资源清单和真实视听文件，并将每一步状态写入数据库。
- Web 3D 垂直切片：Three.js WebGL 2 场景包含第三人称角色、跟随相机、实体碰撞、五枚收集物、限时胜负、发光出口、键盘和移动端控制；六种风格会改变场景几何、细节密度、位图纹理材质与 HUD 结构。
- 多玩法运行时：十二类游戏分别实现自己的规则、完成条件、重开、键盘和触控逻辑；拼图使用咬合边、自由拖拽和落点吸附，可选择 6—50 块，开局拼块全部位于中央画板外围，不是滑块拼图，也不是同一交互的换皮。
- 专业设计合同：每个项目都生成目标玩家、玩家幻想、单局时长、核心循环、胜负、推进、难度曲线、手感、新手引导、无障碍和制作风险；这些内容同时出现在制作页与 `GAME_DESIGN.md`。
- 开源模板台账：数字合成移植 2048 的核心规则结构，太空射击移植 Radius Raid 的帧循环与波次结构；均核验 MIT 许可并把来源、接入方式和媒体资产边界写入版本。
- 拼图难度属于玩法合同：轻松、标准、挑战分别改变默认块数、吸附范围和参考底图强度；玩家显式选择块数时覆盖默认数量，但仍受 50 块上限约束。
- 画面风格属于正式合同：选择结果进入 `game-spec`、硬约束、验收清单、美术方向和资源清单，并实际改变生成游戏的页面编排、组件造型、字体层级、边框与纹理、装饰密度、画布细节和反馈动效，不再只是替换配色；旧版本缺少该字段时按经典风格兼容读取。
- 正式视听资产：各成熟模板均有独立主视觉和游戏内位图图集；2D 角色、方块、道具和材质从 RGBA 图集绘制，信号目标使用位图精灵，3D 地面、遗迹、玩家和收集物使用位图纹理。每套另有环境声、操作、成功和失败 WAV，提示词、来源、尺寸、Alpha 处理和 SHA-256 随资产归档。
- 自动探针：2D 模板检查首次加载、主要输入、核心规则、完成条件、重开、响应式结构、真实视听资产、位图游戏美术、个性化能力、视觉风格合同和专业设计文档；3D 另检查本地引擎文件、真实透视场景、位图纹理材质、相机、碰撞、收集循环、键盘与触控和像素比预算，通过后才形成可玩版本。
- 黄金游戏：已把“星梦对决”作为真实可玩项目接入稳定玩家网址和不可变版本网址。
- 3D 黄金游戏：“遗迹撤离”使用真实 Three.js 场景并已发布到统一游戏大厅；重新构建的新版本会执行 14 项 3D 探针，其中包含位图纹理材质、位图角色与收集物检查。复杂战斗、骨骼动画、开放世界和多人仍不在当前能力范围内。
- 自动检查：合同、十二类生成物和数据库测试，加上类型检查、前端与服务器生产构建。

### 服务配置(环境变量)

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` | `4312` | 工作台与 API 端口 |
| `GAME_PORT` | `4313` | 游戏交付源端口(只 serve 游戏产物、模板美术与玩家遥测,不暴露工作台 API) |
| `PUBLIC_ORIGIN` | `http://HOST:PORT` | 工作台对外地址 |
| `PUBLIC_GAME_ORIGIN` | `http://HOST:GAME_PORT` | 游戏对外地址;生产环境指向独立子域,使 iframe 试玩真实跨源隔离 |
| `STUDIO_ACCESS_TOKEN` | 未设置 | 设置后所有工作台 API 需要 `Authorization: Bearer <令牌>`;健康检查与玩家遥测保持公开。浏览器端执行 `localStorage.setItem("forge-access-token", "<令牌>")` 解锁工作台 |
| `BUILD_CONCURRENCY` | `2` | 同时运行的构建数上限,多余构建排队 |
| `OPENAI_API_KEY` / `OPENAI_API_KEY_FILE` | — / `data/secrets/openai-api-key.txt` | 文本与生图模型密钥;无密钥时回退关键词识别、模板设计与模板封面 |
| `NODE_USE_ENV_PROXY` | 未设置 | 走系统代理访问 OpenAI 时必须设为 `1`(Node 的 fetch 默认忽略 `HTTP(S)_PROXY`,否则模型调用会静默回退) |

API 内置按 IP 限流:创建项目 5 次/分、启动构建 10 次/分、制作意见 20 次/分、试玩遥测 120 次/分、其余接口合计 240 次/分。

### 动态生图与对话式修订(需 OpenAI 密钥)

- 每次构建实时生成:主视觉封面(按画幅出图)、局内场景背景(低对比氛围图),以及模板允许的角色位图(snake 的食物/障碍、maze 的出口;透明底、规则语境优先)。提示词随产物归档在 `_studio/DYNAMIC_ART.json`。失败或无密钥时保留模板预设。
- 成套块面:2048 的六级块面共享"成套一致性锚点"整套并行生成(同轮廓/材质/光照,亮度随等级递增,块面禁文字数字);任何一张失败整套弃用,绝不与模板块混排。俄罗斯方块块面与砖块三态是同一机制的后续配置项。
- 制作对话的意见在下一次构建时被读入:设计合同由模型按意见修订,并逐条审计落实情况(✅/⚠️ 及依据),写入 `GAME_DESIGN.md` 的"创作对话修订依据"。

### 实验通道:无模板代码生成

一句话描述的玩法没有任何模板能承载时(塔防、卡牌、经营等),不再直接拒绝——项目进入实验通道(`template: "generated"`):模型先产出无基线的完整设计合同,构建时由 gpt-5.6 按合同生成独有游戏。2D 生成单文件 HTML;创意明确要求 3D 时生成基于本地 three.js 模块的场景(唯一放行的 import 是 `./vendor/three.module.js`,原始几何+程序纹理,像素比与光源受性能预算约束)。安全线与验收线:

- 静态安全扫描:禁网络(fetch/WS/beacon)、禁外链资源与绝对 URL、禁 eval/new Function/动态 import、禁 cookie/localStorage/postMessage/iframe;违规原因喂回模型重试,三轮不过构建失败。
- 运行时契约:`data-game-state` 状态机 + `game:state-change` 事件(接平台遥测)、`#start`/`#restart` 控件、`?probe=1` 门禁的胜负探针;平台注入存档垫片与遥测,哨兵标记注入边界并复扫生成段。
- 真实浏览器契约验收:三档画幅布局 + idle→开始→playing→won→重开→再开局→lost 完整状态环;控件点不到时自动附遮挡诊断(谁盖住了按钮、层叠上下文提示);失败原因喂回模型再生成一轮,仍失败则构建失败。
- 产物溯源:`_studio/GENERATED_CODE.json` 记录模型、轮数、SHA-256 与实现说明;确认面板与清单均标注"实验性作品"。
- 规则正确性审计:契约验收通过后,模型对照设计合同(核心循环各步+胜负条件)逐条核对代码,未实现的规则喂回再生成一轮;最终判定与证据写入 `_studio/RULE_FIDELITY.json`,如实记录不美化。
- 对话式迭代:实验作品重建时以上一版代码为修改基础(迭代模式),只落实制作对话的意见与验收反馈,其余实现、数值与手感保持原样——不再整局重写。

~~~bash
# 构建并启动应用 + 数据库(应用镜像内置 Chromium 供构建验收)
PUBLIC_ORIGIN=https://studio.example.com PUBLIC_GAME_ORIGIN=https://play.example.com \
~~~

## 当前产品判断

- 长期产品目标是开放式游戏创作：覆盖不同玩法、2D/3D 和多个运行时，而不是三消生成器或模板市场。
- 当前交付切片已经从小型 2D 浏览器游戏扩展到第一个真实 Web 3D 黄金游戏，用同一套项目、构建、版本和发布后端验证多运行时链路。
- 当前已用九种相互独立的规则运行时证明同一创作链可以承载明显不同的小游戏；它们仍是受控能力包，不等于已经能忠实生成任意玩法。
- 一句话创建默认走成熟模板运行时(模板承载规则,AI 定制设计合同、封面、局内背景与部分角色位图);模板无法承载的玩法走实验通道,由模型直接生成独有代码并通过安全扫描与真实浏览器契约验收。实验作品的状态机、胜负分支与布局有自动验证,但规则深度仍以真人试玩为准。
- “星梦对决”三消只是第一个黄金验收游戏，不是其他游戏的母版。
- 2D 模板使用轻量 Canvas 运行时并借鉴 Phaser 的场景分层；3D 使用本地固定版本 Three.js 模块，其他引擎仍通过统一协议接入，不把平台绑定到单一框架。
- 平台的真正差异是“玩法合同 + 真实试玩证据 + 版本回退”，不是单纯的聊天生成代码。
- 开源玩法已通过可追溯的代码结构移植进入模板库，但第三方视听资产没有进入交付；完整筛选与许可边界见开源模板研究文档。

## 成功标准

平台最终要证明不同玩法能够共享同一条创作链，同时保留各自的运行时、资源和测试方式：

> 中文想法 → 能力合同 → 运行时选择 → 可玩核心 → 资源与场景 → 自动验收 → 真实试玩 → 失败修复 → 不可变版本

第一阶段只验证这条平台链是否可靠，不代表产品只支持三消。首个垂直样条必须做到：

- 用三消需求生成或导入一份结构化玩法合同。
- 生成的游戏能完成玩家行动、AI 行动、消除、连消归属、扣分、结算和重开。
- 规则测试和浏览器测试都有可见证据。
- 修改一条规则后，未修改规则仍通过回归测试。
- 自动修复失败时保留上一个成功版本。
- 发布后得到可直接分享的独立 HTTPS 游戏网址；网址指向不可变版本并能安全回滚。
- 需要存档或排行榜的游戏通过受控游戏数据 API 工作，生成代码不直接接触数据库凭证。

## 证据边界

竞品能力以其官方页面和官方仓库为准；页面未公开的系统提示词、服务器命令、工具参数和内部架构不作还原。本项目只采用通用产品模式、公开技术和我们自己的可验证实现。
