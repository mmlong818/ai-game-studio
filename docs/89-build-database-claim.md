# 制作回执与执行权的数据库边界

2026-09-07

## 修正

原创建构建的活动任务检查在事务外，且串行锁仅对同一个仓储实例有效。现在 PostgreSQL 事务先锁项目行，再检查请求编号、归档状态与活动任务，并原子写入意见、构建和步骤。读取最终回执在事务提交后执行。SQLite 测试保留进程内串行锁。

构建执行器领取任务时使用 `UPDATE ... WHERE status = 'queued'`；只有影响一行的执行器能继续。另一执行器不调用模型、不写产物，也不会把别人的任务标为失败。running、succeeded、failed 状态均不能重新领取。

## 验证

`npm run test:publication-postgres` 的隔离真实数据库测试已增加：

- 两个独立连接同时确认同一修改，得到同一任务，只写一条意见。
- 另一修改在已有活动任务时被拒绝。
- 同一任务的两个并发领取仅一个成功，失败终态不能再次领取。
- 不携带修改编号的并发启动也只建立一条活动任务。

测试仅修改本轮新建 schema，退出时清理并校验清理结果，不调用模型、不修改现有项目。

## 仍未解决

这不是完整多实例部署支持：启动时的全局中断标记、服务端创建队列的进程归属、跨实例全局并发额度与检查点恢复仍需修正。当前部署仍应保持单 API 实例，不能因为构建领取加锁就扩容多个实例。

数据库领取保证同一任务的入口只被一个执行器接受，不代表外部付费 API 与数据库之间具备原子事务或恰好一次计费。
