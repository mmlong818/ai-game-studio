# 游戏托管、数据库与独立网址

## 1. 交付定义

游戏在工作台里成功预览，不等于真正交付。

一款游戏只有同时具备以下内容，才算完成网页交付：

- 可直接分享的稳定 HTTPS 玩家网址。
- 永远指向同一构建结果的不可变版本网址。
- 承载 HTML、JavaScript、图片、音频和 3D 资源的托管与 CDN。
- 可检查的发布状态、加载结果、错误和性能数据。
- 需要时可用的存档、排行榜、分析或多人服务器。
- 新版本发布失败时不影响上一线上版本的原子切换和回滚。
- 发布完成后自动进入统一游戏大厅；草稿、失败构建和未发布预览不得出现在玩家列表中。

## 2. 三种网址

| 类型 | 示例形态 | 用途 | 生命周期 |
|---|---|---|---|
| 构建预览 | `buildId.preview.product-games.example` | 创作者、自动试玩和内部验收 | 短期，可设 7—30 天过期 |
| 不可变版本 | `versionId.version.product-games.example` | 发布复核、历史版本、回滚和审计 | 永久，不改变内容 |
| 稳定玩家网址 | `game-slug.play.product-games.example` | 玩家访问、分享、二维码和搜索收录 | 长期不变，指向某个健康版本 |

用户以后绑定自己的域名时，自定义域名只是稳定玩家网址的别名，仍然指向 `publication`，不会绕过版本、安全扫描或回滚流程。

## 3. 游戏如何呈现

稳定玩家网址不是工作台分享页，而是一款独立游戏的网站：

- 独立标题、描述、封面、图标和社交分享卡。
- 进入前可展示加载进度、操作方式、设备和性能提示。
- 游戏画面支持全屏、静音、重开和必要的画面质量选项。
- 手机自动识别横竖屏，给出旋转提示和安全区处理。
- 3D 游戏显示资源下载和着色器准备进度，低性能设备可以选择降级档。
- 游戏崩溃时显示可恢复错误，不暴露内部堆栈、模型记录或密钥。
- 制作时间线、源文件、内部测试和项目 ID 不进入玩家界面。

首版可以保留很轻的品牌归属和举报入口；评论、推荐流、重混和商业化不阻塞游戏交付。

### 统一游戏大厅

平台提供一个稳定的玩家入口 `/games`，集中展示所有 `published + live` 游戏：

- 每张游戏卡显示名称、玩法摘要、2D/3D、当前版本和发布时间。
- “开始游戏”始终打开稳定玩家网址，不直接指向草稿或临时预览。
- 发布成功后由数据库状态自动进入列表，回收发布后自动移出。
- 游戏大厅是玩家浏览入口；合同、构建日志、错误和内部版本操作仍留在创作工作台。
- 首版按发布时间排序，后续再增加分类、搜索、推荐与创作者主页。

## 4. 服务器职责

### 控制平面

负责创作者侧业务：

- 登录、项目和权限。
- 玩法合同、构建、事件、配额和成本。
- 资产、测试、版本、域名和发布。
- 编排器、工作器和一次性构建沙箱。

### 交付平面

负责把静态游戏稳定交给玩家：

- 对象存储保存不可变游戏包。
- CDN 分发 HTML、脚本、图片、音频、字体、GLB/glTF 和纹理。
- 边缘路由把稳定游戏网址解析到当前 publication。
- 健康检查、缓存预热、访问日志和错误采样。

绝大多数单机小游戏不需要一台常驻专属服务器。它们是静态包，通过 CDN 低成本交付。

### 游戏数据平面

只有玩法需要动态状态时启用：

- 匿名或登录玩家标识。
- 云存档与跨设备同步。
- 排行榜、赛季和成就。
- 远程配置和活动。
- 脱敏玩法分析与客户端错误。
- 后续房间、匹配和实时状态。

生成游戏只能访问平台提供的游戏数据 API，不能拿数据库连接串，也不能直接调用控制平面内部 API。

## 5. 数据存放

| 数据 | 存放位置 | 原因 |
|---|---|---|
| 用户、项目、构建、版本、发布、域名 | 平台 PostgreSQL | 需要事务、关联和审计 |
| 玩家存档、排行榜和玩法事件 | 隔离的游戏数据 schema/数据库 | 与平台账号和内部数据隔离 |
| 游戏代码包和静态资源 | 对象存储 | 文件大、不可变、适合 CDN |
| 构建日志、截图和测试录像 | 对象存储，数据库保存索引 | 便于保留策略和按需下载 |
| 短期队列、限流和缓存 | 可选 Redis 或托管等价服务 | 不是权威数据源，丢失可恢复 |

首版可以共用 PostgreSQL 集群，但平台控制数据和玩家运行数据必须使用不同 schema、角色、密钥和 API。规模、地区或合规要求出现后再拆集群。

## 6. 游戏数据合同

首轮只提供三组受控能力：

### 玩家身份

- 默认生成游戏作用域的匿名玩家 ID。
- 用户主动登录后才能跨设备关联。
- 游戏令牌只允许访问一个项目和指定能力。

### 云存档

- 每个项目、玩家和槽位有大小与频率限制。
- 存档记录 `schemaVersion`，游戏升级必须提供兼容或迁移策略。
- 写入使用版本号或 ETag，避免多个设备静默覆盖。

### 排行榜

- 榜单有项目、规则、赛季和排序方向。
- 提交幂等、限流并记录版本。
- 客户端自报成绩只能进入“休闲榜”；可信榜需要服务端规则验证、签名事件或回放验证。

实时多人不与首轮存档 API 混做。它需要房间状态、权威服务器、延迟补偿、断线恢复和反作弊的独立黄金游戏。

## 7. 发布流程

~~~mermaid
flowchart LR
    A[测试通过的构建] --> B[秘密与依赖扫描]
    B --> C[上传不可变对象]
    C --> D[创建版本网址]
    D --> E[CDN 预热]
    E --> F[真实网址冒烟试玩]
    F -->|通过| G[原子切换稳定玩家网址]
    F -->|失败| H[保留上一线上版本]
    G --> I[持续错误与性能监控]
    I -->|异常| J[一键回滚指针]
~~~

发布不能直接覆盖已有文件。所有资源使用内容哈希命名并长期缓存；稳定网址只切换一条版本指针，因此发布和回滚都不需要重新构建。

## 8. 首版部署拓扑

供应商暂不写死，首版需要的逻辑组件是：

- Web/API 服务：工作台和控制 API。
- Worker 服务：AI 编排、构建、测试和发布任务。
- PostgreSQL：平台权威数据和隔离的游戏数据区。
- 对象存储：项目快照、构建包、资产和测试证据。
- CDN/边缘路由：游戏网址、缓存和 TLS。
- 一次性构建沙箱：不接触主站文件系统和数据库。
- Playwright 工作器：从真实预览或版本网址执行试玩。
- 监控与告警：API、构建、发布、游戏加载和数据接口。

生产环境至少划分开发、预发布和生产三个环境；域名、数据库角色、存储桶和密钥不能混用。

## 9. 发布验收

每次上线至少自动检查：

- HTTPS 与证书有效。
- 稳定网址、版本网址和所有资源返回成功。
- HTML 不引用草稿或预览地址。
- 关键加载、输入、暂停、重开和输赢路径可运行。
- 控制台没有未处理异常。
- 主站 Cookie、令牌和存储对游戏不可见。
- 云存档只能读写当前项目与玩家的数据。
- 排行榜限流、幂等和错误提示有效。
- 桌面、目标手机画幅和 3D 性能预算通过。
- 发布失败保留上一版本；回滚后稳定网址恢复旧版本。
- 标题、封面、图标和分享卡正确。

## 10. 首版与后续范围

### 首版必须有

- 平台服务器和 PostgreSQL。
- 对象存储与 CDN。
- 三类网址和独立内容域名。
- 原子发布、健康检查和回滚。
- 基础访问量、加载失败和客户端错误。
- 游戏数据 API 的隔离协议和能力开关；静态游戏发布不依赖它。

### P1 增加

- 匿名玩家、云存档和休闲排行榜。
- 存档配额、版本迁移和排行榜滥用防护。

### 后续增加

- 自定义域名和自动证书。
- 登录玩家跨游戏身份与家长控制。
- 可信排行榜、成就和活动系统。
- 地域部署、数据驻留和更完整分析。
- 实时多人房间与权威服务器。
- 桌面、移动商店包和专业引擎交付。
