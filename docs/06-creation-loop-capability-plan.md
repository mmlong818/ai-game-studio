# 二次规划：创作闭环能力计划

## 1. 目标与取舍

本计划吸收成熟游戏 IDE 中最有价值的四项能力：AI 资产直接进入项目、场景/层级/属性联动、构建后的多设备预览、AI 修改后的即时验证。

我们不复制完整桌面 IDE。平台仍然面向不懂编程的创作者，默认隐藏代码、引擎目录、扩展、模型密钥和构建参数，把复杂能力收敛成“选中对象、描述变化、看到预览、确认证据”的网页流程。

研究依据：

- PinK 官方说明把 AI 生成的 2D/3D 美术、动画、视频和声音直接导入引擎并供代码引用，证明生成与项目资产管线连接比单纯下载资源更有价值。
- PinK/OpenPaaS 把代码生成、实时错误诊断、构建和跨端运行串成一条链路；本平台借鉴闭环，不继承完整 IDE 的复杂度。
- 本项目既有规则合同和证据绑定继续作为完成标准，任何可视编辑都不能绕过玩法验收。

参考：[PinK 官方产品页](https://pink.sud.tech/)、[OpenPaaS 官方介绍](https://openpaas.sud.tech/)、[SUD Runtime 文档](https://developer.sud.tech/openpaas/app/introduction/runtime/runtime-introduction.html)。

## 2. 目标用户路径

```text
确认游戏规格
  → 生成或选择 AI 位图
  → 自动加工并绑定到场景对象
  → 在画面/层级/属性中检查对象
  → AI 或用户修改安全属性
  → 生成不可变桌面与手机预览
  → 自动验证受影响规则、资源和视口
  → 接受修改或整组回滚
  → 发布同一构建并导出完整资源包
```

这条路径必须满足：用户始终知道正在修改哪个对象、会影响什么、真实画面是什么，以及平台凭什么认定修改完成。

## 3. C1：AI 资产直接进入项目

### 用户结果

- 用户描述“把主角改成 Q 版瓢虫”后，平台生成候选位图、自动处理尺寸和透明背景，并直接替换预览中的主角。
- 用户不需要下载、改名、寻找目录或手工修改资源路径。
- 失败或不满意时可以回到上一个版本，不影响仍在使用的健康资源。

### 最小数据对象

`AssetGenerationRecord` 至少记录：资源 ID、玩法角色、提示词哈希、模型与版本、生成时间、原始文件、加工步骤、许可/来源说明、派生文件、内容哈希和当前状态。

`AssetBinding` 至少记录：资源版本绑定到哪个场景节点、动画状态、界面状态或音效事件，以及替换它会影响哪些视图。

### 边界

- 核心美术只使用 AI 生成或来源明确的位图，禁止 SVG 作为游戏美术。
- 模型 Key 只存在于服务端或用户私密配置，不进入项目、日志和交付包。
- 平台先支持角色、背景、障碍、收集物、特效序列帧和界面位图；3D 资产生成继续保持实验状态。

## 4. C2：场景、层级与属性联动

### 用户结果

- 点击画面中的对象，层级树定位到同一对象，属性面板显示它的普通名称和玩法作用。
- 用户可以修改规格允许的安全属性，例如视觉尺寸、位置偏移、显示层级、动画速度和已登记难度参数。
- 碰撞尺寸、胜负条件、资源增减等核心属性默认锁定；修改它们会转入规则变更和重新验收。

### 统一场景节点

每个可编辑对象至少暴露：

- 稳定节点 ID 与用户可读名称。
- 玩法角色：玩家、危险、奖励、背景、界面、特效或辅助。
- 父子层级与渲染顺序。
- 位置、尺寸、锚点和可见性。
- 视觉资源、动画、碰撞体与规则 ID 绑定。
- 桌面/手机是否使用不同布局，以及差异由什么规则控制。

### 边界

- 这不是任意 DOM 或代码检查器，只显示平台能解释、保存、回滚和验证的对象。
- DOM、Canvas 和有限 3D 可以使用不同运行时实现，但工作台呈现相同对象心智。
- 手机端优先保证游戏画布可见，编辑属性使用底部抽屉或独立步骤，不做缩小版桌面三栏。

## 5. C3：构建与多设备预览闭环

### 用户结果

- 用户点击预览后只产生一个不可变构建，同时用于工作台桌面预览、手机浏览器预览、正式发布和开源包导出。
- 手机通过短期链接或二维码打开真实浏览器版本，不用桌面尺寸模拟替代真机检查。
- 构建失败时明确指出代码、资源、浏览器或设备问题，并继续保留上一个健康版本。

### 构建记录

`PreviewBuild` 至少绑定：构建 ID、规格哈希、代码哈希、资源清单哈希、变更集 ID、浏览器结果、参考视口截图、错误日志和有效期。

### 边界

- 第一阶段只交付现代网页浏览器，不扩展原生 iOS、Android 或桌面安装包。
- 临时预览和正式发布使用不同访问权限，但字节内容和构建 ID 必须一致。
- 真机预览负责发现触控、安全区、地址栏、音频恢复和性能问题，不能被截图模拟完全替代。

## 6. C4：AI 修改后的即时可视验证

### 用户结果

- AI 每次修改后，用户看到“改了什么、影响什么、实际画面、验证结果”，而不是只有一条完成文案。
- 资源、代码或规格任一变化都会让相关旧证据失效，并自动重跑最小受影响检查集。
- 修改失败可以整组撤销，避免新图片已经进入目录但画面、碰撞和验收仍指向旧版本。

### 变更集

`ChangeSet` 至少记录：用户目标、修改文件、资源版本、场景节点、规则 ID、目标设备、风险等级、前后构建 ID、验收结果和回滚目标。

### 完成条件

一次 AI 修改只有同时满足以下条件才显示完成：

1. 变更集已保存且没有半完成操作。
2. 新的不可变预览构建可以打开。
3. 所有受影响 P0/P1 自动检查通过。
4. 资源清单和场景引用一致。
5. 需要人工判断的视觉或游戏感项目明确显示“待复核”，没有被自动标绿。

## 7. 分阶段实施

| 阶段 | 交付重点 | 前置依赖 | 证明结果 |
| --- | --- | --- | --- |
| A：资源基础 | 生成记录、资源版本、加工、绑定和打包收集 | Game Spec v2、资源哈希 | AI 图片能直接替换项目对象且可回滚 |
| B：对象编辑 | 统一场景节点、选中联动、安全属性 | 规则 ID、运行时适配器 | 不读代码也能识别并修改对象 |
| C：预览构建 | 不可变构建、桌面/手机/真机入口 | 证据绑定、发布版本 | 各入口运行完全相同的构建 |
| D：修改验证 | 变更集、影响分析、自动重验、整组回滚 | A、B、C | AI 修改不再以文本承诺作为完成 |

实施时先在“虫虫攀枝”黄金游戏中贯通四阶段，因为它同时包含角色分层、可动部件、头部碰撞、背景滚动、收集物、障碍和手机操作。通过后再迁移到棋盘、射击、拼图和 3D 黄金游戏，避免先做一个只适用于单一渲染方式的编辑器。

## 8. 不做的内容

- 不开发完整代码编辑器或 VS Code 扩展生态。
- 不允许用户安装任意运行时代码插件。
- 不在第一阶段实现多人协作场景编辑。
- 不为了模拟专业引擎而暴露原始组件、着色器和打包参数。
- 不把生成一张图片、通过一次构建或出现一个预览页面单独视为任务完成。

## 9. 总体验收

四项能力全部完成时，非程序员应能完成以下真实路径：选择一个游戏对象，用自然语言替换 AI 位图，检查对象层级与安全属性，在桌面和真实手机预览同一构建，看到受影响规则自动重验，并在失败时完整回滚。最终开源包必须包含当前构建所需的全部本地资源、来源记录和质量证据。
