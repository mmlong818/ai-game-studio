# ADR-0002：采用能力图与多运行时适配器架构

状态：已接受，用于平台架构。  
日期：2026-08-26。

## 背景

产品目标是生成多种 2D、3D 游戏，后续还要支持专业引擎和多人。若把 Phaser、三消结构或任何单一工程骨架写入项目、版本和编排核心，新类型将迫使平台重写后端，3D 也会变成另一套产品。

同时，完全让模型自由选择依赖、引擎和工程结构，会使构建成功率、安全、测试与升级成本不可控。

## 决策

平台采用四层结构：

1. **通用游戏规格**：记录玩家体验、空间、视角、机制、实体、输入、物理、世界、资产、网络、交付和验收，不包含引擎专属对象。
2. **能力图**：把需求拆成可组合能力，并计算依赖、冲突、成熟度和性能预算。
3. **运行时适配器**：声明支持的能力，提供固定脚手架、运行时桥、构建镜像、测试驱动和打包器。
4. **游戏能力包**：提供平台跳跃、棋盘规则、角色控制器、相机、车辆、导航 AI 等可按需加载的生成与验收知识。

编排器先确定能力，再匹配满足条件且稳定级别最高的适配器。如果没有适配器完整覆盖，系统必须列出缺口并提出可见降级，不能假装完成。

~~~ts
interface RuntimeAdapter {
  id: string;
  capabilities(): RuntimeCapabilityManifest;
  scaffold(spec: GameSpec): Promise<ProjectSnapshot>;
  validateProject(snapshot: ProjectSnapshot): Promise<ValidationResult>;
  build(snapshot: ProjectSnapshot): Promise<BuildArtifact>;
  createTestDriver(artifact: BuildArtifact): Promise<GameTestDriver>;
  package(artifact: BuildArtifact, target: DeliveryTarget): Promise<PackageArtifact>;
}
~~~

## 第一批适配器

| 顺序 | 适配器 | 目的 |
|---|---|---|
| 1 | `web-2d-phaser` | 用三消、平台跳跃和俯视生存证明 2D 生成与多样性 |
| 2 | `web-3d` | 用小型 3D 收集撤离关卡证明场景、相机、碰撞、资产和性能闭环 |
| 3 | `godot-4` | 验证专业引擎工程交付以及更复杂的 2D/3D 项目 |

`web-3d` 的具体渲染和物理组合在技术样条后锁定；选型不能改变通用协议。

## 稳定级别

每项能力和适配器公开以下状态：

- `experimental`：只能在实验工作区选择，不承诺自动修复成功率。
- `preview`：已有黄金游戏和自动验收，但样本与性能覆盖不足。
- `stable`：通过多提示基准、跨设备试玩、回归和成本门槛。
- `deprecated`：停止新建，旧版本仍可构建和导出。

用户看到的是当前项目所需能力的覆盖情况，而不是一张夸大的“支持所有类型”宣传表。

## 结果

正面：

- 三消不会渗入平台核心数据模型。
- 2D 和 3D 共用创作、版本、事件、安全和证据体验。
- 新引擎可以通过受控接口加入。
- AI 的自由度被限制在可测试的边界内。
- 能力成熟度可以真实表达。

代价：

- 必须维护适配器兼容性矩阵和黄金游戏回归。
- 通用规格与引擎能力之间需要显式映射。
- 跨引擎无损转换不作为默认承诺。
- 3D 资产、性能和测试基础设施的成本明显高于 2D。

## 禁止事项

- 不把某个黄金游戏复制成所有项目的隐藏母版。
- 不允许适配器直接创建自己的项目、版本或发布后端。
- 不声称同一份生成代码可以无损运行在所有引擎。
- 不把静态 3D 场景截图计为可玩 3D 支持。
- 不允许未知依赖、任意网络访问或未审计构建脚本进入生成工程。
