# ADR-0003：分离控制平面、游戏交付平面与游戏数据平面

状态：已接受，用于平台架构。  
日期：2026-08-26。

## 背景

游戏不能只存在于创作者工作台的预览框。每个发布游戏需要独立网址、稳定资源托管、可选服务端数据和可回滚版本。同时，生成代码不可信，不能与主站身份、Cookie、数据库和内部 API 处于同一安全边界。

若给每个静态小游戏常驻一台服务器，成本和运维会随项目数量线性增长；若所有游戏覆盖同一组文件，缓存、版本和回滚又不可控。

## 决策

- 工作台、身份、构建和版本组成控制平面。
- 游戏包作为不可变对象存入对象存储，通过 CDN 和独立内容域名交付。
- 每次成功版本拥有永久版本网址；每款发布游戏拥有稳定玩家网址。
- 稳定玩家网址通过 publication 指针原子切换到不可变版本。
- 云存档、排行榜和分析通过项目作用域游戏数据 API 提供。
- 生成游戏永远不获得数据库凭证或平台内部服务令牌。
- 静态游戏不分配常驻专属服务器；动态和实时能力按需启用。

## 结果

正面：

- 游戏是真正可分享、可独立访问的交付物。
- 新发布失败不会破坏线上版本，回滚只需切换指针。
- 静态小游戏可以低成本大规模托管。
- 玩家数据与平台控制数据有清晰安全边界。
- 2D、3D 和未来引擎导出的 Web 包使用同一发布协议。

代价：

- 需要维护独立内容域名、通配 DNS/TLS、CDN 和对象存储。
- 发布必须增加真实网址冒烟检查和缓存策略。
- 游戏数据 API 需要配额、版本兼容和滥用防护。
- 自定义域名会增加所有权验证、证书和客服成本，因此后置。

## 不采用的方案

- **所有游戏与工作台同源**：主站 Cookie、存储和内部接口暴露面过大。
- **发布时覆盖原目录**：无法可靠审计、回滚和控制 CDN 缓存。
- **每个游戏一台常驻服务器**：对大多数静态小游戏成本不合理。
- **客户端直连数据库**：凭证、越权、配额和数据迁移不可控。
