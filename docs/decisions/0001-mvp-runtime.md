# ADR-0001：第一个 Web 2D 适配器采用 Phaser + 纯 TypeScript 规则核心

状态：已接受，用于垂直样条。  
日期：2026-08-26。

## 背景

M0 要用小型 2D 浏览器游戏验证平台闭环，并自动验证输入、状态、胜负、手机布局和性能。AI 如果每次自行实现场景、资源加载、输入、物理、音频和生命周期，项目结构容易漂移，测试也无法复用。

## 决策

- `web-2d-phaser` 适配器采用 Phaser；这不是整个平台唯一或永久默认的引擎。
- 关键玩法规则放在不依赖 Phaser 的纯 TypeScript 模块中。
- Phaser 只负责 Scene、渲染、输入、动画、音频、相机、物理和资源生命周期。
- 平台提供固定项目骨架、运行时桥和测试接口。
- 实施样条时以官方当前 Phaser 4 为兼容基线；锁定精确版本前运行三消、平台跳跃和俯视角移动三个兼容性样例。

Phaser 官方仓库将其定位为桌面和移动浏览器的开源 HTML5 游戏框架，提供场景、加载、输入、物理、动画、相机、瓦片地图和大量示例，并采用 MIT 许可证：[Phaser GitHub](https://github.com/phaserjs/phaser)。

## 选择原因

1. 它是完整游戏框架，不只负责绘制。
2. 场景、输入和物理可以进入统一骨架。
3. 桌面和移动浏览器是原生目标。
4. 官方资料和生态足够丰富，编码模型更容易获得正确 API 上下文。
5. MIT 许可证便于商业产品使用，但仍需保留许可证文本和完成依赖审计。
6. OpenGame、swipi-engine 和 Prompt-N-Click 等生成项目都采用或支持 Phaser，证明它适合受控骨架。

## 备选方案

### PixiJS

优点：

- 2D 渲染灵活、性能强。
- MakePlay 公开说明其 2D 使用 PixiJS。
- 特别适合自定义棋盘和视觉效果。

不选为默认的原因：

- PixiJS 是渲染层，不提供完整场景、玩法物理和通用游戏结构。
- AI 会被迫反复发明更多基础设施。

保留用途：后续专用高性能模板和需要自定义渲染的玩法。

### GDevelop

优点：

- 完整开源编辑器、事件系统和运行时。
- 项目结构可视、可编辑。

不选为默认的原因：

- 嵌入整个编辑器和事件模型远超首版范围。
- 我们当前差异是自动生成与验证，不是建立通用无代码引擎。

保留用途：研究其项目结构、事件编辑、可暂停 Agent 和发布体验。

### Godot

优点：

- 成熟开源引擎，2D/3D 和编辑器完整。

不选为默认的原因：

- Web 构建、编辑器桥、沙箱和部署成本更高。
- 会把第一阶段从浏览器小型游戏扩大成多引擎工作台。

保留用途：产品验证后作为导出或专业模式。

### 原生 Canvas2D

优点：

- 无依赖、构建轻、容易隔离。
- GameSmith 证明可以形成完整工作流。

不选为唯一默认的原因：

- 复杂玩法需要自行维护更多输入、碰撞、相机和资源系统。
- 更容易让模型重复生成基础代码并产生不一致。

保留用途：极小的 grid_logic、UI-heavy 和教学互动游戏。

## 结果

正面：

- 骨架更稳定。
- 测试和调试接口可复用。
- AI 生成范围缩小到规则、场景内容和视觉。
- 三消纯核心可直接成为第一批测试夹具。

代价：

- 第一批 Web 2D 玩法会受到 Phaser 能力和项目结构约束。
- 必须维护运行时升级与兼容性基准。
- 仍需防止所有作品在场景结构和手感上趋同。

## 决策边界

- 三消是 `web-2d-phaser` 的第一个黄金夹具，不是平台的通用母版。
- 3D 不在这个适配器中硬塞实现；它使用独立 `web-3d` 适配器。
- 项目、版本、构建事件、资产清单和验收协议必须位于适配器之上。
- 多运行时总体决策见 [ADR-0002](./0002-multi-runtime-platform.md)。

## 防止模板趋同

- 骨架只提供基础能力，不携带完整角色、关卡和规则。
- 玩法合同决定状态机和机制组件。
- 资产、关卡和反馈从空内容生成。
- 第二阶段必须用非三消的俯视角和平台跳跃样例检查多样性。
