# 产品愿景与能力边界

## 1. 北极星

这个产品不是“三消生成器”，也不是把固定模板换皮的网站。

它要成为一个**开放式 AI 游戏创作平台**：用户用自然语言、参考图和持续指导表达创意，平台把需求转成可执行规格，组合玩法能力，选择合适的 2D 或 3D 运行时，生成并测试真实可玩的游戏。

长期承诺可以表达为：

> 从一分钟小游戏到可探索的 3D 世界，用同一套可理解、可验证、可回退的 AI 制作流程完成。

“开放式”代表能力可以持续增加，不代表任何想法都能一次生成商业成品。平台必须明确告诉用户当前目标能否完成、会降级什么，以及哪些部分尚未验证。

## 2. 三层边界

### 产品愿景

- 不限定游戏类型。
- 同时覆盖 2D 与 3D。
- 可扩展到单机、异步联机和实时多人。
- 可扩展到浏览器、桌面、移动端和专业引擎工程。
- 同一个创作会话可以持续增加玩法、关卡、资产和版本。

### 平台不变量

无论生成哪类游戏，都必须复用：

- 公开的游戏规格和验收清单。
- 可恢复的构建步骤与权威事件流。
- 隔离的代码、资产生成和构建环境。
- 运行时适配器协议。
- 自动测试、真实试玩和性能证据。
- 不可变版本、比较、回滚和发布。
- 每个已发布游戏拥有稳定、独立、可分享的 HTTPS 网址。
- 静态游戏托管和动态游戏数据服务分离，按玩法需要启用服务器能力。
- 资源来源、许可证和成本记录。

### 当前交付切片

- 第一款黄金游戏：2D 三消对战。
- 第一个运行时适配器：Web 2D / Phaser。
- 第一次多样性检查：非棋盘类 2D 游戏。
- 第一个 3D 黄金游戏：小型 3D 收集与撤离关卡。

三消只验证平台最基础的生成与验收链；它不是产品分类、通用代码模板或未来游戏的结构上限。

## 3. 不用“类型列表”限制创作

平台可以识别“平台跳跃”“塔防”“竞速”等常见类型，但真正的生成路由依据是能力组合。

| 能力轴 | 示例 |
|---|---|
| 空间 | 2D 单屏、2D 卷轴、等距、3D 房间、3D 开放区域 |
| 视角 | UI/棋盘、俯视、侧视、第一人称、第三人称、载具跟随 |
| 操作 | 点击、拖动、键盘、手柄、触控、陀螺仪 |
| 移动 | 格子、自由移动、跳跃、飞行、驾驶、轨道 |
| 模拟 | 无物理、街机碰撞、刚体、角色控制器、导航网格 |
| 玩法 | 解谜、战斗、收集、经营、卡牌、叙事、潜行、竞速、生存 |
| 世界 | 单局、房间、关卡、程序生成、持续世界 |
| 角色 | 单角色、多角色、敌人 AI、NPC、队友、群体单位 |
| 网络 | 单机、本地多人、异步、房间制实时多人 |
| 交付 | 浏览器、PWA、桌面包、移动包、引擎工程 |

例如，“第三人称卡通厨房经营 + 夜间怪物防守”不是一个固定模板，而是以下能力的组合：3D 第三人称、角色控制器、交互物、订单经济、波次敌人、昼夜状态和关卡存档。

类型标签只帮助理解需求；能力图才决定运行时、技能、资产管线和测试方案。

## 4. 游戏不是一个工作台里的预览框

生成完成后的游戏必须作为真正的交付物存在：

- 创作者在工作台使用项目网址管理合同、构建、测试和版本。
- 每次成功构建有一个短期、受保护的预览网址。
- 每个不可变版本有一个永久版本网址，可用于审计和回滚验证。
- 每个已发布游戏有一个稳定玩家网址，后续发布只切换它指向的不可变版本。
- 需要存档、排行榜、活动或多人能力时，游戏获得隔离的服务端数据空间。
- 后续可以绑定创作者自己的域名，而不改变版本和发布模型。

独立网址不意味着每款静态小游戏都运行一台独立服务器。静态代码和资源由对象存储与 CDN 托管；只有需要动态数据或实时交互时才调用受控游戏服务。

## 5. 通用游戏规格

每个项目先形成与引擎无关的 `game-spec`，至少包含：

~~~json
{
  "vision": "一句话玩家体验",
  "dimensions": "2d | 3d",
  "runtimeTarget": "auto | web-2d | web-3d | godot-4",
  "perspective": "top-down | side | first-person | third-person | ui",
  "mechanics": [],
  "entities": [],
  "scenes": [],
  "camera": {},
  "input": {},
  "physics": {},
  "world": {},
  "artDirection": {},
  "audioDirection": {},
  "networkMode": "single-player",
  "deliveryTargets": ["web"],
  "hardConstraints": [],
  "acceptanceCriteria": [],
  "nonGoalsForThisVersion": []
}
~~~

`nonGoalsForThisVersion` 只是当前版本的取舍，不能被误解为平台永远不支持的能力。

## 6. 多运行时策略

平台不生成一种万能工程，而是维护统一协议和多种受控适配器：

| 适配器 | 负责的项目 | 路线 |
|---|---|---|
| `web-2d-phaser` | 棋盘、太空射击、俯视动作、轻量经营等 | 第一个交付 |
| `web-2d-custom` | UI 密集、特殊渲染或极轻量玩法 | 按实际需求增加 |
| `web-3d` | 第一/第三人称、小型 3D 关卡、驾驶和空间解谜 | 完成 2D 多样性验证后启动 |
| `godot-4` | 更复杂的 2D/3D、桌面和移动工程交付 | Web 3D 证明后接入 |
| 其他适配器 | Unity、Cocos 等专业或区域化生态 | 由真实用户需求和维护成本决定 |

每个适配器都要声明它能做什么、不能做什么、需要哪些资产格式、如何构建、如何接受测试动作，以及如何读取只读状态。编排器按能力匹配，而不是让模型随意选择框架。

## 7. 3D 生成闭环

首个 3D 黄金游戏选择“小型遗迹收集与撤离”：玩家在一个有限 3D 场景中移动，收集 5 个物品，避开移动障碍，在倒计时内到达出口。

它覆盖最小但完整的 3D 风险面：

- 场景图、模型、材质、灯光和天空。
- 第一人称或简化第三人称相机。
- 键鼠、触控和手柄动作映射。
- 角色碰撞、地面检测、触发器和移动障碍。
- 收集、计时、输赢、重开和存档。
- GLB/glTF 资产校验、纹理和多边形预算。
- 首屏下载体积、稳定帧率、内存和移动端降级。
- 浏览器真实试玩与状态探针。

只有这个闭环能在不同场景重复通过后，平台才能对外宣称 Web 3D 已支持。更复杂的角色骨骼、战斗 AI、载具、开放世界和多人分别建立后续黄金游戏。

## 8. 黄金游戏矩阵

黄金游戏不是商品模板，而是平台能力的回归试卷。

| 顺序 | 黄金游戏 | 证明的能力 |
|---|---|---|
| G1 | 共享棋盘三消对战 | 确定性规则、回合、连消、AI、触控、版本修改 |
| G2 | 2D 太空射击 | 实时输入、弹体、碰撞、波次和即时反馈 |
| G3 | 2D 俯视生存 | 多实体、生成波次、敌人 AI、性能、游戏节奏 |
| G4 | 3D 遗迹收集与撤离 | 3D 场景、相机、碰撞、资产预算、Web 性能 |
| G5 | 3D 小型竞技场 | 第三人称、动画状态、战斗 AI、命中与反馈 |
| G6 | 房间制合作小游戏 | 网络同步、断线恢复、权威状态和反作弊边界 |

新能力只有同时通过专属黄金游戏和已有回归集，才进入平台公开能力目录。

## 9. 分阶段不是缩小愿景

阶段只控制风险与交付顺序：

1. **证明链路**：用三消证明合同、构建、测试、修复和版本。
2. **证明多样性**：用太空射击与俯视生存证明不是换皮模板。
3. **证明 3D**：建立 Web 3D 适配器和第一个 3D 黄金游戏。
4. **证明开放性**：发布运行时适配器、能力包和测试驱动协议。
5. **证明规模化**：增加专业引擎、多人、UGC 分发和创作者生态。

如果某一阶段失败，应修复基础设施或暂缓公开对应能力，不应把长期产品重新定义成三消或三类 2D 游戏。

## 10. 成功与失败的判断

成功不是“生成了很多项目”，而是：

- 同一套规格与版本系统能服务明显不同的玩法。
- 运行时可以增加而不用重写产品工作流。
- 用户能知道某个创意当前是否被完整支持。
- 2D 与 3D 都有真实操作、状态和性能证据。
- 局部修改不会频繁破坏无关能力。
- 新能力通过注册和测试加入，不靠无限增长的总提示词。

以下情况视为产品方向偏离：

- 所有作品最终都映射到少量隐藏模板。
- 为支持新引擎复制整套项目、版本和测试系统。
- 3D 只有静态场景或视频，没有可验证交互。
- 用“理论上能生成”替代真实构建和试玩通过。
- 为追求类型数量而失去版本、回退、安全和成本控制。
