# 游戏 UI 设计与验收方法

本规范将猫叔 UI 设计方法论收敛为本项目的长期工作规则。它用于创作平台界面、游戏内 HUD/菜单、视觉资源规划和已有游戏局部改造。它不改变业务合同，也不替代具体游戏规则、运行时约束或人工视觉评审。

## 每次设计先锁定证据和范围

证据按以下顺序使用：当前项目真实页面、代码、数据和测试；用户明确需求与反馈；平台与标准的一手规则；可访问的真实产品；二手材料；经验假设。事实、推断和待验证假设必须分开。重要决定使用这一行记录：

`证据 → 对当前游戏/玩家的适用性 → 具体决定 → 未采用方案及原因 → 可观察的验证`

先写清玩家此刻的主要任务、入口、成功结果、失败与恢复，再处理视觉表达。没有实测或人工目视证据时，只能写“待验证”或“候选方案”，不得声称更美、更好玩、提升转化或已经通过审美验收。

## 游戏 UI 的项目规则

1. **玩法先于装饰。** 主操作、当前目标、状态反馈和返回路径在最短扫描路径上。HUD 不遮挡高频交互区，背景与装饰不削弱角色、危险、奖励和文字的辨识度。
2. **沿用已有设计语言。** 优先复用当前 token、组件、输入方式、布局和素材气质。成熟的开始、暂停、继续、返回、重试和设置模式保持可预期；独特表达集中在少数与题材或玩法有因果关系的图像、反馈或文案上。
3. **状态来自真实功能。** 只覆盖当前功能实际存在或明确需要的默认、进行中、成功、失败、暂停、中断恢复、禁用等状态。不得为了凑状态矩阵新增商店、权限、关卡、教程或玩法系统。
4. **结构、视觉、决策和流程一起检查。** 结构说明信息顺序；视觉说明主次层级和素材角色；决策说明玩家行动及后果；流程说明进入、反馈、失败、恢复和下一状态。游戏内画面不机械套用 Hero、三卡片或后台表格结构。
5. **输入和文字可用。** DOM 菜单使用正确的按钮、链接和可访问名称；键盘顺序、可见焦点、触控热区和窄屏变化与真实任务一致。动作文字说明结果，错误靠近原因并给出可执行的恢复方式。
6. **资源按角色交付。** 背景、角色、图标、道具和动画先定义用途、比例、适配方式和安全区。位图禁止非等比拉伸；背景按可接受裁切范围 cover，主体 contain 并保留轮廓与透明边缘；sprite sheet 保持网格、帧序、锚点和动作连续性。局部资源替换只改明确目标，其余素材保持不变。
7. **局部改造不推翻原游戏。** 玩法范围只调整指定玩点；资源范围只替换点名图片或动画 clip；美术风格范围调整色彩、材质、插画与表面表达。除非用户明确指定，均保留原玩法、操作、布局、导航、内容和其他资源。
8. **动效表达真实变化。** 动效用于输入响应、移动、命中、成功、失败和状态切换；不靠循环装饰制造完成感。减少动态效果时仍保留等价状态信息。

## 实施与验证

设计参考在编码前锁定，并记录哪些来自项目事实、哪些只是启发。实现后按风险选择验证：类型检查和目标测试；真实 URL、DOM、资源与控制台；鼠标、键盘、触摸、焦点、返回、刷新、错误和重试；手机与桌面画幅、长文案和文本放大；成功、失败、中断恢复和最终产物。

Canvas/WebGL 的几何、溢出、资源加载和运行状态可以自动检查；构图、层级、节奏、素材协调和整体设计感必须通过真实截图或运行画面人工评审。自动测试通过不能证明游戏好看或好玩。未走过的真实路径、未调用的接口、未生成的文件和未测设备必须明确列为未验证。
