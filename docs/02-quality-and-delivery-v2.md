# 二次规划：质量、证据与交付 v2

## 1. 质量原则

平台发布的是可玩的游戏版本，不是生成过程的成功提示。质量闸门必须回答四个问题：

设计与复核同时使用 [统一设计原则](33-game-design-knowledge.md)；官方身份和用户可改造能力分别登记。只供游玩的作品不得出现在创作模板/改造入口中；上架不会自动将尚未完成的质量检查标为通过。

1. 规则是否正确。
2. 玩家是否真的能够完成核心循环。
3. 桌面和手机体验是否清楚、流畅、可恢复。
4. 交付包是否完整、安全、可独立运行。

## 2. 七层质量闸门

### 全游戏共用：表现提升不得增加操作负担

此规则适用于所有官方模板、新生成游戏及后续改造，不表示历史游戏已自动完成复核。生成指令共用 `src/shared/game-presentation-policy.ts`；人工改造也必须按以下清单审核。

- 优化不能删除核心动画：发牌/归位、移动、收集消失、命中和胜利结算必须保留可理解的过程。优先降低重复装饰、粒子密度和无效更新；减少动态效果设置可减弱表现，不能隐藏结果。
- 不以新增按钮、复杂组合操作换取质量；强化现有操作的响应、内容变化和阶段成就感。不能用短周期强制弹窗打断实时玩法。
- 新手模式 AI 必须留出可理解的获胜机会：限制决策频率、采用非完美行动策略，不能把自动最优操作当作公平。双方基础规则保持一致，不靠隐藏瞬移或追赶加速制造竞争；按真人试玩复核胜率，不能只用 AI 控制玩家的测试认定难度合适。
- 输入、规则、渲染分离；固定步长模拟使用帧间插值，HUD 按变化或节流更新；失焦暂停，重开清理输入、计时器和旧实例。
- 每款模板状态、样式、存档和资源生命周期独立；不得脱离平台合同，也不得修改一款破坏其他游戏。
- 性能审核记录设备/GPU、浏览器、画幅、DPR、版本、采样时长及场景，比较平均帧率、帧时间 P95、draw calls、三角形和资源数。覆盖开局、密集交互、结算、连续重开；至少一段正常完整游玩，不以探针快进替代帧率采样。
- 自动化只能证明其覆盖的项目。没有目标设备测量或人工观感复核时，该项标记“待验证”，不能宣布质量达标；无头浏览器帧率不能冒充用户预览帧率。

#### 3D 专项（仅适用于 3D，不硬套给 2D）

- 预算先给近景主角和交互物：清晰轮廓、适量圆角、平滑法线；按用途区分材质粗糙度与金属度。保留画面层次，禁止用高曝光掩盖材质问题。
- 动作对应真实状态，转向、加速、受击、收集可见但不互相干扰；表现层不改写碰撞、控制和公平规则。
- 相机按时间平滑，检查坡道、急弯、建筑遮挡；按实际问题选择抬升、缩距或局部淡化，不能对整批场景无差别透明。
- 渲染倍率、阴影范围与更新频率、动态物体、粒子分别制定预算；可用静态阴影缓存加移动接触阴影，但不能让主体失去接地感。
- 复用材质和几何；重复环境按空间分区合批，保留视锥裁剪；避免全世界一个批次。切换场景释放不用资源，重复重开验证 GPU 资源不持续增长。
- 原创程序化 3D 几何可以作为明确登记的模型来源，不得冒充 AI 生成位图；此例外不解除生成流程已有位图要求、资源追溯与授权约束，也不允许用 SVG/Emoji 顶替核心 2D 美术。

审核结论必须列出：本次改动、前后证据、已通过项目、待验证项目和适用范围。未复核的存量模板留待逐款改造，不能整体标记已达标。

### G0：支持范围与合同完整性

- 能力声明能匹配现有运行时或实验适配器。
- P0 规则、用户硬约束和非目标没有冲突。
- 游戏进度模式、单局时长和输入路径明确。
- 超出平台能力时直接停止，不进入代码生成。
- 模板改造已经标记 R0–R3 级别；R3 自动转入新游戏流程。
- 核心规则变化或新游戏已经生成同类玩法参考档案，并记录来源边界。

### G1：纯规则与不变量

- 状态转换、资源上下限、胜负、计分和重开通过确定性测试。
- 益智游戏使用求解器或状态遍历验证可解性。
- 程序生成游戏固定种子，并覆盖正常、边界和高压种子。
- 实时游戏验证碰撞体、通路净宽、反应窗口和无敌时间。

### G2：静态产物与安全

- HTML、CSS、JavaScript 可以解析和构建。
- 不使用外部脚本、动态执行代码、未授权网络、Cookie 或任意存储。
- 所有资源路径存在，位图签名与资源清单一致。
- 核心美术使用可追溯 AI 位图，禁止 SVG、Emoji 和字符充当主要美术。
- 每个实际引用的位图都能追溯到生成记录、加工记录、当前资源版本和场景绑定；未被引用的历史版本不进入正式包。
- 资源替换失败时保留上一个健康版本，不允许出现资源记录已更新但画面仍引用旧文件的半完成状态。
- 密钥、令牌、私人配置和本机路径不得进入交付包。

### G3：真实玩法场景

每款游戏至少执行：

- 从准备状态正常开始。
- 一次合法动作并产生预期状态变化。
- 一次非法动作且不会破坏状态。
- 一次核心资源获得与消耗。
- 一次主要风险或失败原因。
- 一次通过正常规则到达阶段完成或结算。
- 失败后的重试或检查点恢复。
- 刷新后的进度恢复。

较长游戏可以使用缩短内容的验收场景，但仍必须通过公开动作和真实规则完成，不能只调用 `forceWin`。

### G4：浏览器、输入和性能

最低浏览器矩阵：

- Chromium：每次构建。
- WebKit：正式发布前。
- Firefox：正式发布前。

最低画面矩阵：

- 360×640 手机。
- 390×844 手机。
- 844×390 手机横屏，适用于横屏玩法。
- 1366×768 桌面。
- 1920×1080 桌面抽查。

检查内容：

- 无横向溢出和阻塞性纵向溢出。
- 主要触控目标至少 44×44px。
- 手机控件不遮挡敌人、障碍、棋盘或落点。
- 键盘焦点可见，主要操作不依赖悬停。
- `prefers-reduced-motion`、静音和页面失焦暂停生效。
- 图片、声音和模块无 404，控制台无异常。
- 参考移动设备目标为稳定 50–60 FPS；P95 单帧不超过 25ms。
- 首局必要资源优先控制在 10MB 内，总交付包建议不超过 25MB；非首局资源延迟加载。
- 工作台预览、手机二维码/链接预览、正式发布和开源包必须指向同一不可变构建；不得为不同入口临时拼装不同资源。
- 每次 AI 修改先生成可打开的预览构建，再根据变更影响重新执行规则、资源、视觉和输入检查。

### G5：视觉与声音复核

- 第一视觉焦点与核心操作对象一致。
- 背景不会压过交互主体。
- 危险、奖励、合法、非法、受击和完成至少使用两类信号表达。
- 角色造型、碰撞区域和动画锚点一致。
- 声音具有明确用途、音量层级和静音入口，不以持续尖锐合成音代替完整音效设计。
- 宣传封面与实际游戏风格、角色和玩法一致。

视觉复核不能一次性把所有视觉标准批量通过；每项需要独立结论和截图证据。

### G6：人工体验复核与发布

人工试玩至少回答：

- 30 秒内是否理解目标和第一个动作。
- 核心循环是否在第一局内出现。
- 是否存在会改变后续局面的有意义选择。
- 爽点是否来自规则与反馈结合，而不是单纯堆特效。
- 失败是否公平、可解释并愿意立即重试。
- 手机和桌面是否都能舒适完成一局。

只有 P0、P1 自动验收通过，并完成人工体验和视觉复核后，版本才能正式发布。实验作品必须显示实验标记和已知限制。

工作台不能把“AI 已返回内容”当作修改完成。完成状态至少需要当前变更集、预览构建、受影响验收结果和资源清单使用相同的版本标识。

人工复核同时检查参考研究是否被正确使用：作品应保留成熟规则的可理解性，但不能只是替换名称和图片，也不能复制参考游戏的品牌化表达。

## 3. 品类专属验收包

通用检查只能证明平台协议，不能证明所有玩法。每个能力包需要自己的规则验收：

| 能力包 | 专属检查 |
| --- | --- |
| 棋盘合并 | 一次一并、生成时序、无效滑动、满盘判定、撤销快照 |
| 空间解谜 | 可解性、最短路径、拖放合法性、撤销/重做、提示理由 |
| 实时闪避 | 玩家尺寸、通路净宽、碰撞、预警时间、生成公平性、速度层次 |
| 射击战斗 | 命中、无敌时间、弹体生命周期、敌人组合、输出窗口、Boss 阶段 |
| 路线与构筑 | 选择差异、协同、冲突、种子复现、阶段保存、差异结局 |
| 经营与队列 | 资源守恒、订单队列、产能、等待、失败恢复、软锁检测 |
| 互动叙事 | 选择后果、条件分支、存档、结局可达、回看与跳过 |
| 有限场景 3D | 相机、碰撞、地面检测、穿模、跌出世界、检查点和性能预算 |

新品类必须先有能力包和黄金游戏，才能从实验支持升级为完整支持。

## 4. AI 原创游戏的最低放行标准

AI 原创游戏不能仅通过通用状态机检查。最低需要：

1. 从规则合同生成 5–12 个玩法专属场景。
2. 每个 P0 规则至少有一个确定性断言。
3. `listActions` 返回当前可执行动作，测试器随机组合和按计划执行动作。
4. 正常路径至少完成一次核心循环。
5. 结算逻辑在纯规则层验证，浏览器层再验证表现。
6. 随机内容记录种子和抽样结果。
7. 规则报告绑定当前规格、代码和资源哈希。
8. 真人试玩确认核心爽点后，才能移除实验标记。

## 5. 数据闭环

匿名质量数据只记录与玩法改进有关的聚合信息：

- 会话开始、完成、失败、退出。
- 单局时长和关卡耗时。
- 失败原因分类。
- 重试、提示、撤销、暂停和恢复次数。
- 关键机制的使用次数与成功率。
- 难度、输入方式、视口和平均帧率。
- 程序生成种子、关卡版本和规则版本。

禁止记录自由文本输入、私人内容、完整按键流或可识别个人的信息。数据用于发现设计问题，不能代替人工试玩。

## 6. 交付物

每个正式版本必须包含：

```text
game/
├─ index.html
├─ styles.css
├─ app.js
├─ assets/
├─ game-manifest.json
└─ _studio/
   ├─ GAME_SPEC.json
   ├─ RULES.json
   ├─ REFERENCE_DOSSIER.json
   ├─ ACCEPTANCE_PLAN.json
   ├─ QUALITY_REPORT.json
   ├─ ART_REVIEW.md
   ├─ ASSET_PROVENANCE.json
   └─ quality/
```

交付包应满足：

- 无需工作台和数据库即可独立运行。
- 不包含密钥、本机绝对路径或私有配置。
- 所有运行资源本地落盘。
- 有不可变版本 ID 和内容哈希。
- 可以通过标准静态服务器启动。

## 7. 发布与回滚

- 构建成功生成不可变版本。
- 发布只切换稳定玩家网址指向，不修改旧版本。
- 新版本失败时稳定网址继续指向上一个健康版本。
- 回滚只切换版本指针，不重新生成。
- 任何规则、代码或资源变化都必须产生新版本并重新执行受影响验收。
