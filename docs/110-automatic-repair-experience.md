# 自动恢复与修复经验运行时

日期：2026-09-15。本说明记录生成链路如何自动处理可恢复故障，并把已复验的修复经验用于后续制作。它描述当前工作树实现，不代表已经过真实付费构建或发布。

## 恢复边界

- 图片与代码产物错误在同一 build 内做针对性修复并重跑同类验收。达到单轮预算只表示本轮有界循环结束；代码、失败签名和检查记录保留，界面明确归为平台尚未解决，不要求用户修改透明边距、代码或验收合同。
- 明确收到 HTTP 429（排除 `insufficient_quota`）或 5xx、以及 DNS/连接建立前失败时，文字策划/审核、代码和图片请求在原请求边界按 250 毫秒、1 秒有界退避。制作阶段的代码生成与规则审核每次物理请求共用同一个 build 请求预算；图片每次尝试计入同一资源的三次预算。确认前的策划请求属于独立阶段，沿用最多两次请求边界，不计入制作阶段 build 预算。流式策划只有在尚未向界面输出任何内容时才重试明确的 429/5xx；已经输出部分内容时不重放。取消会中断退避。超时、流中断、普通 `TypeError` 等结果不确定错误不重放，也不盲目重跑整个 production job，以免重复付费、重复项目或重复 build。
- 服务重启只自动恢复尚未开始的 queued job。creating job 的结果不确定时保留同一回执并停止重复调用，等待按 requestId 核对已有项目/构建。
- 浏览器已实际确认所有可见玩法动作与唯一 Canvas 共用一个带稳定唯一 id 的非根容器、且页面没有另一棋盘声明时，系统可只给该源 HTML 节点补充 `data-game-board`。这条修复不移动控件、不执行历史代码，也不改变验收条件；同一 build 会重新执行静态、浏览器和规则审核，三者全部通过后才记录 `repair-game-board-marker` verified 经验。根容器、多个 Canvas、重复 id、已有另一棋盘或复验失败均不会晋升成功经验。
- 跨 build 自动复验只接受零模型检查点。`sourceBuildId`、审核源码 SHA-256 与新 build 在数据库事务内持久化，进程重启后执行器仍从数据库恢复专用模式；运行时再次核对同项目、合同、零图片路线、源码写入前后哈希及完整规则审核回执。任何漂移直接失败，不回退策划、图片、代码或审核 provider。
- 凭据、账户权限、余额/额度和配置缺失需要用户处理；系统不得自动换 key、放宽安全规则或降低核心玩法门槛。

## 经验记录与消费

`src/server/repair-experience.ts` 在 artifact root 下维护 `_repair-experience/repair-experience-v1.jsonl`。每条记录只有：规范版本、时间、失败签名、有限错误码、适用范围、平台维护的修复策略 ID、结果和复验类型。

适用范围由模板、运行时、设计合同版本、机制指纹、结束模式、失败策略和资源路线组成。失败原文、provider 请求/响应、堆栈、本地路径、密钥和任意生成代码不写入经验库。签名只由脱敏、归一化后的错误形状计算。

- `verified` 经验只有在对应候选通过产物/浏览器或规则审核后才写入。下一次同范围制作的首次代码输入会收到至多三条低优先级预防参考；同签名再次失败时还会精确注入对应成功策略。
- `failed` 记录不能晋升为成功规则，只在相同签名出现后提醒不要原样重复同一候选路径。
- 注入文本明确标为“不可信修复经验参考”，只提供平台策略建议，不能覆盖当前用户合同、系统规则或验收证据，也不会执行历史任意代码。

## 自动测试证据

- `src/server/repair-experience.test.ts`：失败不晋升且不泄露原文/路径/key、不同运行时不复用、同范围成功可消费。
- `src/server/build-orchestrator-repair.test.ts`：第一个任务修复并复验后，第二个同范围任务的首次 code 输入已经包含成功经验；同类失败后也按签名进入针对性修复输入。
- `browser-quality` 与 `deterministic-artifact-repair` 测试：覆盖运行时动态创建操作控件的三消结构；未标记时拒绝且不执行动作，结构化建议只指向 `#stage`，精确补标后正常动作产生稳定棋盘变化。根容器、多 Canvas、重复 id、脚本伪标签和已有另一棋盘均拒绝自动修复。
- `studio-repository` 与 orchestrator guard 测试：零模型 token 与 build 原子持久化，进程内存丢失后仍可读取；绑定检查点复验时代码与审核 provider 均为零调用，源码哈希漂移时同样为零调用。
- `transient-retry`、`design-contract` 与 `image-generator` 测试：真实 provider 包装在 429/5xx 后按原边界恢复，额度错误不重试，退避可取消；规则审核在共享预算只剩一次时收到 503 只发出一次物理请求，第二次发送前即停止；流式策划在首段内容前可从 503 恢复且只交付成功尝试的内容，已有部分输出后不重放；`tests/production-jobs.test.ts` 证明整单 503 不会盲目重跑。
- `tests/build-failure.test.ts`：修复预算耗尽归为 `AUTO_REPAIR_EXHAUSTED`，不要求用户处理技术产物。

本轮没有外呼模型、启动服务、创建 production job、部署或发布。自动测试只能证明编排和数据边界，尚未证明真实 provider 故障后的完整恢复或某个游戏已经交付。
