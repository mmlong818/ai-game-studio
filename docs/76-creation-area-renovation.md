# 游戏创作区正式改造

## 审核标准

非专业用户以最少操作获得完成度高的小游戏。减少强制决策，而不是删除质量步骤；方案、资源、构建、验证、发布仍在现有平台完成。不能把本地关键词匹配或预置来源说成完成了 AI 分析、外部研究或实机验证。

## 当前有效规则（2026-09-06 真实验收轮）

本节优先于下方历次改造记录，旧记录仅保留变更背景。

- 实时方案与制作共享经过校验的结构化合同；确认后不再调用模型重新策划，不以关键词或静态模板替代。
- 已完成方案在同一浏览器标签会话内可跨刷新复用；进行中的预览尚不支持跨整页刷新恢复，不应宣称服务端预览任务已实现。
- 制作提交前保存幂等请求编号；服务端先持久化回执，再执行工作。进度断线与刷新仅查询原任务，结果未知不暗中重付费。
- 制作中保留站点框架，制作区无另建、修改、重新生成等按钮；完成后原地显示跨源隔离试玩，不自动发布。
- 当前真实子阶段在首屏显示；模型代码流仅展示接收数量与阶段，不展示源码或虚构百分比。等待动画尊重减弱动态偏好，计时不是完成度。
- 创建阶段并发最多2项，其余真实排队。模型输出中断不盲目重试，明确验收错误才允许有界修正。
- 失败后的修正必须读取上一版完整代码（页面、样式和逻辑），不能只读取HTML空壳或从头另做一款。
- 静态检查只核查接线与安全，不能把语法风格当成行为证明；别名和方法简写必须兼容，真实动作、教学、结算仍由浏览器验收。
- 教学必须取自确认方案的真实玩法，不允许“核心循环待细化”等占位进入成品。
- 用户确认方案、代码通过、浏览器通过、实际玩通是不同证据层级。任何未完成项不得写成已完成。
- 记忆翻牌须额外通过无调试接口的正常点击检查；教学安全暂停不能冻结翻牌、错配盖回等即时反馈。
- 同项目图像要求、模型、画幅和运行时一致且文件复验合格时，修复版本复用已有图像，保存原始来源与生成时间，另记复用来源，不重复调用生图服务。

验收证据目录：`dogfood-output/creation-real-qa/`。生成式游戏能力验收迁移原则见 `generated-game-acceptance-capabilities.md`；固定20关的历史约束尚未完成全面迁移，不应声称支持所有游戏类型的专用验证。

## 2026-09-06 第一轮：创作入口与状态真实性

- 首页直接呈现描述输入框，填写后一步进入现有 ReviewScreen，不再先选模式再打开空白输入页。
- 改造现有游戏保留为次入口，沿用官方可改造游戏过滤，原版不受影响。
- 三个可编辑灵感。已有输入时需要确认替换；取消保留原文。沿用草稿保存与返回调整。
- 不展示技术参数选择；保留生成前的方案确认，不触发付费生成。
- 方案中的预设“通过”改为“待验证”，列出玩法规则、新手帮助、难度节奏、资源结算与跨设备流畅度。此列表是审核要求，不是已经执行的证据。
- 使用现有 React/CSS 与站点配色，独立样式限制在创作入口；桌面双栏、手机单栏。

验证：71 个测试文件 / 316 项通过，应用 TypeScript 检查通过。浏览器核对 1264px 桌面及 390px 手机布局，实际点击灵感到达方案页。覆盖新建、改造、改为新游戏、替换保护、返回编辑与进入原工作台；未运行付费完整生成。

## 后续工作顺序（尚未完成）

### 第九轮：真实流式输出与长方案创建修复

- 方案预览向模型请求 stream，服务端将实际正文增量转为 NDJSON 转发，前端即时呈现已形成的字段内容；完整校验后才开放确认。断流/失败不会把片段当成完成方案。
- 制作页通过持续流接收服务端任务/构建状态快照；断开只重连读取，不重新提交。服务端每 750ms 检查持久化状态变化，不伪造百分比。
- 当前制作步骤推送不是游戏代码或图像的逐字生成流；预览方案的文本才来自模型 token 增量。
- 修复完整方案写入 vision 导致超过 280 字的错误：只裁剪展示简介，项目 idea 保留完整确认文本。
- 流式能提前展示输出，不保证降低模型首字延迟或总生成时长。

### 第八轮：服务端接管创建与构建，保留页面框架

- 恢复制作页的站点导航框架；仅去除制作区域内的另建、重试等流程操作。本节取代第七轮隐藏顶栏的规则。
- Web 一次提交 /api/production-jobs。服务端先持久化任务与输入，返回任务编号，再独立执行方案分析、项目创建、构建启动；浏览器不再串联 createProject/startBuild。
- 创建阶段的 queued/creating/building/failed 状态及失败原因保存在数据库，页面通过只读接口恢复。重复任务编号不会再次执行。
- 浏览器关闭不取消已接收任务；服务进程重启将未完成的创建任务标记为失败，不自动重试模型调用。并非检查点续跑。
- 旧的不存在项目地址不会自动重建，历史已丢失错误无法追溯恢复。

### 第七轮：制作页只展示进程

- “把想法做出来”页只展示阶段、步骤和完成/失败结果；移除另建游戏、重新制作、修改输入、项目链接与试玩，制作记录直接展开。
- 在该页隐藏顶栏操作，避免误点切换创作流程。浏览器本身的返回/关闭不拦截，已提交任务照常在服务端运行。
- 完成结果保存在“我的项目”；失败不自动重试。原项目工作台能力不删除，但不在进度页提供入口。
- 本节取代此前简洁制作页提供修改意见与另建入口的设计。

### 第六轮：方案返回保留与等待

- 当前页面会话按完整描述与模板约束复用真实模型方案，最多保留 12 项；返回修改后内容未变，无需再次生成。进行中的同一请求也复用。
- 修改输入或主动重新生成才请求新结果；请求失败不缓存。过期响应仍不覆盖新描述。
- 这是会话内缓存，整页刷新或关闭浏览器后不保证保留；不缓存 API Key，不写固定方案。
- 前端方案组件等待从 1000ms 缩短为 250ms；加上描述输入层的 1500ms，首次自动提交等待约 1750ms。
- 预览使用单次尝试，不再出现两轮 90 秒的隐式超时重试。制作和质量审核仍保留原重试策略。

### 第四轮：实时策划取代固定灵感方案

- 灵感按钮只提供可编辑描述，不提供预写方案。创作页改用 LiveDesignReview，经 /api/design-preview 实时调用已配置的文字模型生成策划。
- 新游戏使用自由策划通道，不按本地关键词选出的模板拼装固定说明；改造游戏仅把原玩法作为约束交给模型。
- 原地显示生成中、失败和生成结果。输入变更后立即禁用旧方案确认，延迟提交新分析并忽略过期响应；支持主动重新生成。
- 无密钥或模型失败明确报错，禁止回退固定方案，未生成成功不得继续制作。
- 页面明确告知方案分析消耗文字模型额度，确认前不生成图片。确认的模型文本原样传到制作项目，不再调用本地 readableDesign 作为生产回退。
- 本节替代前几轮“本地分析不消耗额度”的说明。更改描述触发新分析，已经送达模型的请求不保证取消计费。

### 第三轮：修改意见可靠性

- 修改意见使用 clientMessageId，数据库主键冲突校验确保相同意见重放仅保存一次，且不会重复生成确认消息；相同标识配不同内容或项目会拒绝。
- 未提交意见按项目保存为浏览器草稿。刷新恢复文字与同一标识；收到服务端已保存记录后清理草稿，不自动启动制作。
- 业务提交错误与读取错误分开显示，后续读取成功不再掩盖保存失败；保存失败不得继续启动构建。
- “返回方案”改为“用当前草稿另建游戏”，明确这个操作创建新项目，不误导为修改当前项目的已确认方案。当前项目的变更仍通过试玩页修改意见提交。
- 验证：16 项相关前端测试与独立数据库恢复/重复意见测试通过，生产构建通过；未进行付费模型生成。

### 第二轮落地：确认方案 → 服务端制作 → 同页试玩与修改

- 输入停顿后在输入区域下方就地展示方案，不抢焦点、不自动滚动、不开始付费制作；显式点击继续才提交。
- 人类可读方案与提交内容复用 readableDesign：操作、示例、结束条件、新手帮助、节奏、反馈、美术与奖励进入项目描述，避免展示一套、制作另一套。
- 简洁制作页改用服务端项目、构建和消息接口，不再走浏览器本地生成与本地验证链。项目地址保留 production 参数，刷新只读取任务，不自动重试付费生成。
- 创建请求携带 UUID；已落库的同一 ID 重放返回已有项目，不同方案复用 ID 会拒绝。并发落库有锁，但尚不承诺创建前模型分析的跨进程幂等计费。
- 最近一次成功构建由服务端独立查询：新构建失败、排队或执行时仍可试玩旧版，刷新也能恢复；不自动发布。
- 用户修改意见先保存再启动新版制作，制作记录默认折叠。保存意见不等于实现，成功构建不等于趣味性验证。
- 服务启动会把中断任务标为失败，用户可以显式重新制作。当前不是检查点续跑；初次项目创建尚未返回时关闭页面，回来可能只能等待项目落库，再显式开始构建。
- 这轮未进行付费完整生成，也未实现每条意见与验收证据的逐条绑定。模板改造继续受既有服务端模板能力限制，不声称已支持任意源码局部编辑。

验证：14 项前端相关测试、1 项独立数据库恢复测试通过；浏览器确认输入框与方案共存且无需跳页；前后端 TypeScript 与生产构建通过。浏览器测试仅使用本地描述分析，没有触发模型或图像生成。

1. 策划整合：候选机制及关系、参考证据、关卡节奏、新手帮助与结算标准形成一份可执行合同；区分自动建议、用户确认与已验证事实。
2. 资源准备：资源缺口、生成/复用方案与授权记录直接进入构建，不让用户手工补素材清单。
3. 制作工作台：把技术步骤收纳为默认自动流程，暴露真实阶段、失败原因、重试与取消；保留高级检查入口。
4. 试玩反馈：让用户直接说哪里不好玩，修改受影响部分，已有版本可回退，质量证据决定是否允许发布。
5. 端到端验收：实际走通新建和改造各一款，从描述到生成、验证、试玩、反馈及发布；付费验证前明确范围。

第一轮不代表以上流水线已经全部实现，也不改变模型设置、官方游戏、数据库与远端仓库。
