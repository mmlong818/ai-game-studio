# 二次规划：模板改造与同类游戏研究

## 1. 目标

用户不应该面对一个完全空白的输入框，也不应该因为提出“再加经营、开放世界、联机和剧情”等天马行空的要求，就让成熟模板失去核心规则。

平台采用两条创作路径：

1. **模板改造**：从已经验证的玩法出发，优先换世界观、换风格、换内容、调节节奏和增加一种小机制。
2. **新游戏设计**：先从现有玩法中提取有效机制，再研究真实同类游戏，形成有依据但不照搬的规则组合。

## 2. 模板改造的四个级别

| 级别 | 用户意图 | 默认处理 | 是否重新研究 |
| --- | --- | --- | --- |
| R0 表现改造 | 换世界观、角色、画风、声音、文案 | 保持全部核心规则，直接生成新表现方案 | 复用模板参考档案 |
| R1 内容与调节 | 换关卡、调整速度、目标量、提示和难度 | 只使用已登记参数，不改变规则结构 | 通常复用已有档案 |
| R2 小规则扩展 | 增加一种敌人、能力、障碍或资源 | 一次只增加一种机制，补规则和专属测试 | 强制研究最接近的同类机制 |
| R3 核心重写 | 改主要动作、胜负、进度类型或组合多个系统 | 停止按原模板改造，转入新游戏流程 | 强制重新研究和原型验证 |

判断是否进入 R3 的问题：

- 玩家反复执行的主要动作是否变了？
- 胜利或失败条件是否变了？
- 主要资源循环是否变了？
- 游戏从关卡制变成经营、肉鸽、叙事或沙盒了吗？
- 是否需要原模板没有的相机、物理、AI、网络或存档能力？

任何一项为“是”，都不能只在旧模板上继续堆代码。

## 3. 固定改造建议的展示方式

确认模板后，工作台先显示 3–5 张与该玩法匹配的建议卡：

- **换世界观**：改变地点、故事包装、角色身份和收集对象。
- **换视觉风格**：从平台支持的风格中选择，并生成新的 AI 位图体系。
- **换内容包**：替换关卡、敌人、障碍、题面、路线或事件池。
- **调节手感与难度**：从该模板已登记的安全参数中选择。
- **加入一种小机制**：只显示已有规则包和测试器能承载的扩展。

每张建议卡都必须同时说明：

1. 玩家会看到什么变化。
2. 哪些核心规则保持不变。
3. 需要新增哪些资源。
4. 是否增加制作风险和验收时间。

自由输入仍然保留，但系统先把文字归入 R0–R3，再决定继续改造还是转入新游戏。

## 4. 成熟模板的固定建议基线

| 玩法 | 必须锁定的核心 | 优先建议 | 允许的一种小机制 | 必须转新游戏的要求 |
| --- | --- | --- | --- | --- |
| 俄罗斯方块 | 方块下落、移动旋转、整行消除、堆到顶失败 | 换材质世界观、任务关、速度档、模式包装 | 垃圾行、限时或特殊任务三选一 | 自由建造、角色战斗、经营资源 |
| 图片拼图 | 拼块来源、拖放、正确位置吸附、全部完成 | 换图片主题、块数、旋转、参考图强度 | 限时或分区整理 | 拼块变成物理战斗或开放探索 |
| 打砖块 | 挡板反弹、球与砖碰撞、清场目标 | 换场景、砖阵、球和挡板、章节主题 | 一种特殊砖或一种主动能力 | 改为自由射击、塔防或平台动作 |
| 华容道 | 固定占格、合法腾挪、目标块到出口 | 换人物世界观、题库、步数挑战、提示方式 | 锁块或单向格二选一 | 自由拖放、实时追逐或战斗 |
| 迷宫 | 连通路径、墙体阻挡、入口到出口 | 换世界观、地图包、雾、冰、钥匙门 | 一种地形规则 | 开放世界、生存建造或多人竞速 |
| 贪吃蛇 | 连续移动、转向限制、吃食物增长、自撞失败 | 换生物、场景、食物、场型和速度 | 金色食物或一种障碍规则 | 射击战斗、经营养成或自由停走 |
| 2048 | 全盘滑动、相同数字一次一并、移动后生成 | 换符号和世界观、目标、难度、撤销次数 | 一种特殊格或任务限制 | 单块拖动、战斗棋盘或复杂经济 |
| 太空射击 | 移动、弹体、命中、波次和生命 | 换机体世界观、敌人包、弹幕、Boss 主题 | 一种主动能力或一种敌人 | 经营基地、开放星图或实时多人 |
| 多格拼块 | 旋转、合法放置、无重叠覆盖目标 | 换轮廓主题、拼块包、提示和评价 | 限时或固定块二选一 | 自由绘制、物理堆叠或战斗 |
| 方块填阵 | 三选拼块、合法放置、横竖消行、无处可放结束 | 换材质、棋盘主题、旅程/无尽、连击反馈 | 一种特殊块 | 改为下落方块、实时对战或经营 |
| 区域逻辑 | 行列区域配额、相邻限制、逻辑可解 | 换符号、版面、星数、提示表达 | 一种额外逻辑约束 | 随机猜测、实时操作或战斗 |
| 肉鸽麻将 | 自由牌判定、成对消除、牌阵可解、路线与遗物 | 换牌面世界观、路线、遗物和事件包 | 一类事件或一组遗物协同 | 改成传统麻将对局、实时战斗或开放经营 |
| 3D 收集 | 角色移动、相机、碰撞、收集和出口 | 换世界、角色、收集物、危险物和路线 | 一种移动能力或一种动态危险 | 开放世界、载具群或复杂骨骼战斗 |
| 3D 竞技场 | 移动、攻击、命中、敌人 AI、波次结算 | 换场景、武器表现、敌人包和强化 | 一种武器或一种敌人行为 | 联机竞技、大型团战或持久世界 |

建议卡不是把用户限制在换皮。R2 允许小幅创新，但必须一次只改变一个可以独立解释、实现和测试的机制。

## 5. 新游戏的研究优先顺序

### 第一步：拆解用户意图

把描述拆成：

- 主要动作。
- 操作对象。
- 主要资源。
- 风险与收益。
- 成功、失败或持续目标。
- 镜头与输入。
- 单局和长期进度。
- 用户明确不能改变的要求。

### 第二步：先查内部机制库

平台从现有玩法中检索已经验证的要素，例如：

- 2048 的全盘滑动和一次一并。
- 射击游戏的预警、弹体和无敌时间。
- 迷宫的可达性、钥匙门和检查点。
- 肉鸽麻将的路线三选一、遗物协同和种子恢复。
- 虫虫攀枝的三路线避障、速度层次、头部拾取和冲刺破障。

内部机制必须以能力 ID 复用，不能复制某款游戏的整段运行时代码后再随意改写。

### 第三步：搜索真实同类游戏

核心规则变化或新游戏至少研究 2 个、最多 4 个参考：

- 一个最接近主要机制的规则参考。
- 一个在输入和反馈上成熟的参考。
- 必要时增加一个移动端或长期进度参考。
- 如果准备借鉴实现结构，再增加一个许可证明确的开源参考。

资料优先级：

1. 官方规则、官方说明书和原作者说明。
2. 官方产品页和开发者公开说明。
3. 原作者仓库或许可证明确的开源实现。
4. 实际试玩录像、商店说明和高质量分析，仅作为补充观察。
5. 聚合文章和搜索摘要只用于发现来源，不能作为最终规则依据。

### 第四步：形成参考锁

每个项目只锁定少量明确参考：

- `mechanicsReference`：核心规则和失败边界。
- `controlsReference`：输入、反馈和移动端适配。
- `progressionReference`：关卡、难度、资源或复玩结构。

不同参考的机制不能直接相加。必须写清楚哪些采用、哪些调整、哪些拒绝，以及组合后是否出现输入冲突、资源冲突或节奏冲突。

## 6. 参考档案格式

```json
{
  "id": "REF-PROJECT-001",
  "queryIntent": "三路线高速闪避和冲刺破障",
  "internalCandidates": ["lane-dodge", "boost-resource", "checkpoint-recovery"],
  "references": [
    {
      "title": "参考名称",
      "url": "https://example.com/official-rules",
      "sourceType": "official-rules",
      "verifiedAt": "2026-09-01",
      "observedRules": ["主要动作", "失败条件", "风险收益"],
      "doNotCopy": ["品牌", "角色", "视觉识别", "音乐", "文案"],
      "license": null
    }
  ],
  "adopted": ["采用的设计要素和原因"],
  "adapted": ["如何改造成适合本项目的规则"],
  "rejected": ["拒绝的要素和原因"],
  "compatibilityRisks": ["输入、资源、节奏和实现风险"]
}
```

如果来源用于规则观察，`license` 可以为空，但不得复制代码和媒体。如果要复用实现，许可证、版权声明和实际复制范围必须明确。

## 7. 网络研究门槛

### 不需要每次重新搜索

- R0 世界观和视觉替换。
- R1 使用模板已经登记的难度与内容参数。
- 没有改变核心规则，并且模板参考档案仍然完整可访问。

### 必须搜索或刷新

- R2 增加新的玩法机制。
- R3 改变核心循环、胜负或进度模式。
- AI 原创新游戏。
- 现有参考失效、来源边界不清或实现许可发生变化。
- 用户明确要求以某款真实游戏为参考。

网络不可用时：

- 有已核验参考档案：可以继续使用缓存，并记录核验日期。
- 没有参考档案：项目保持实验状态，不能声称已经完成同类研究。

## 8. 官方资料校准示例

官方 Tetris 说明把核心动作描述为旋转、移动和下落，完成无空格横行进行消除，超过顶部边界时结束。这类资料用于锁定不可随意改变的玩法骨架；视觉主题、关卡包装和模式可以变化，但不能把核心规则改掉后仍称为原模板改造。参考：[Tetris 官方玩法说明](https://play.tetris.com/about)。

2048 原作者页面明确展示方向输入、相同数字接触后合并、重新开始和继续游戏；原作者仓库同时提供 MIT 许可证信息。平台应分别记录“规则观察”和“代码许可”，不能把两者混为一谈。参考：[2048 官方页面源码](https://github.com/gabrielecirulli/2048/blob/master/index.html)、[2048 原作者仓库与许可证说明](https://github.com/gabrielecirulli/2048/blob/master/README.md)。

MDN 的网页游戏控制资料将触控、鼠标/键盘和手柄视为不同控制环境，说明同一个核心动作在不同设备上需要独立输入适配，而不是简单把桌面按钮缩小到手机。参考：[MDN 网页游戏控制机制](https://developer.mozilla.org/en-US/docs/Games/Techniques/Control_mechanisms)。

## 9. 放行检查

模板改造在生成前必须回答：

- 当前改造属于 R0、R1、R2 还是 R3？
- 核心锁定规则有哪些？
- 用户要求中哪些可以直接完成？
- 哪些要求需要转入新游戏流程？
- 新机制是否只有一种，并拥有独立测试？

新游戏在生成前必须回答：

- 复用了哪些内部已验证机制？
- 研究了哪些真实同类游戏？
- 每个参考分别解决规则、输入、反馈还是进度问题？
- 哪些内容明确不会复制？
- 组合后的核心循环是否能在目标单局时长内出现至少两次？
- 平台是否具备所有关键能力和验收器？

未回答这些问题，不进入正式代码生成。
