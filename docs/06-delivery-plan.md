# 交付路线与首轮任务

## 1. 交付策略

产品目标是开放式多类型、2D/3D 游戏生成；交付上先完成一条可评审的垂直链，不先搭建看似完整但不能生成游戏的平台外壳。

顺序：

1. 把三消项目变成第一个平台黄金夹具，而不是通用游戏母版。
2. 建立与引擎无关的玩法合同、运行时适配器合同和验收 DSL。
3. 建立可恢复编排与统一事件流。
4. 让系统完成一次规则修改并自动回归。
5. 用太空射击和俯视生存证明多样性，再接入 Web 3D 黄金链。

## 2. M0：黄金链，10 个工作日

目标：不追求开放式生成，先证明“合同 → 构建 → 测试 → 版本”完整闭环。

### 第 1—2 天：协议和夹具

- 建立 monorepo 和最小 Web/Worker 边界。
- 定义 game-spec、acceptance、asset-manifest Schema。
- 把星梦对决规则转成 TypeScript 黄金夹具。
- 固定三消种子棋盘和关键场景。

验收：

- Schema 校验能指出字段路径和修复方法。
- 现有 8 项规则测试在迁移后继续通过。

### 第 3—4 天：运行时壳

- 创建 Phaser grid_logic 骨架。
- 实现 mount、pause、resume、restart、destroy。
- 实现 getDebugState 和 dispatchTestAction。
- 实现桌面点击、键盘和手机滑动映射。

验收：

- 三消核心不依赖 Phaser。
- DPR=1、2、3 下棋盘命中和布局一致。
- 重开能取消旧异步动画和 AI 任务。

### 第 5—6 天：构建与事件

- 创建 build、build_step、build_event。
- Worker 使用租约领取步骤。
- SSE 断线续传。
- 保存文件快照和构建产物。
- 把成功构建上传对象存储并生成短期预览网址。

验收：

- 刷新浏览器不会丢失真实进度。
- 重复请求不会执行同一步两次。
- UI 与数据库事件顺序一致。
- 预览网址使用 HTTPS，且无法读取主站 Cookie 和存储。

### 第 7—8 天：试玩与证据

- Playwright 打开隔离预览。
- 执行玩家交换、AI 行动、连消、扣分、结算、重开。
- 保存截图、控制台和状态证据。
- 失败项映射到 acceptance。

验收：

- 至少 M3-01 至 M3-10 自动判定。
- 失败不能由模型自然语言声明覆盖。

### 第 9 天：局部修改

- 输入“基础伤害 5 → 8”。
- 生成变化合同和影响范围。
- 只失效相关规则、测试和发布包。
- 创建新版本。

验收：

- 区域权限和连消归属测试仍通过。
- 原版本仍可打开。

### 第 10 天：完整回归和评审

- 从新建项目走到第二个可玩版本。
- 检查安全边界、日志脱敏和版本恢复。
- 记录耗时、成本、失败和人工介入。

验收：

- 一条脚本或测试任务可重复演示整条链。
- 所有未验证项明确列出。

## 3. M1：封闭样条，4—6 周

目标：让少量真实用户从自然语言开始，而不是从预制合同开始。

范围：

- 中文想法抽取。
- 最多三个澄清问题。
- 玩法合同确认。
- 代码生成和限次修复。
- 程序化占位资源。
- 三消和一个非三消骨架。
- 工作台三栏布局。
- 版本、回滚和公开链接。
- 每款游戏的稳定玩家网址和不可变版本网址。
- 云存档与排行榜的项目作用域数据 API。
- 基础配额、审核和运营诊断。

退出条件：

- 20 个提示形成可重复基准集。
- 至少 70% 能进入可玩预览。
- 每个失败有明确类别，不出现大量“未知”。
- 成本和时间分解到步骤。
- 5 名不懂代码的用户能独立完成首次创建和一次修改。

## 4. M2：封闭 Alpha，6—10 周

范围：

- grid_logic、top_down、shooter 三类骨架。
- 图片和音频生成。
- 风格锚点和局部重生成。
- 只读源码与版本差异。
- PWA 包和分享卡。
- Firefox、WebKit 回归。
- 30—50 名目标用户测试。

退出条件：

- 三类玩法均有至少 10 个测试提示。
- 修改回归率和自动修复成本达到可接受区间。
- 用户能区分“规则相同的换皮”和“真正不同的玩法”。
- 安全和许可证审计完成。

## 5. M2 基准：20 个首轮 2D 提示集

### grid_logic：8 个

- AI 对战共享棋盘三消。
- 固定步数的宝石竞速。
- 推箱子加机关。
- 连线消除与技能冷却。
- 记忆翻牌对战。
- 五子棋变体。
- 颜色排序。
- 教学答题棋盘。

### top_down：6 个

- 竖屏海底躲避。
- 双摇杆生存。
- 单指追逐和收集。
- 小型塔防。
- 俯视角竞速。
- 教学知识射击。

### shooter：6 个

- 波次生存射击。
- 编队敌机。
- 移动目标。
- 武器强化。
- 倒计时挑战。
- 首领战。

每个提示都要有：

- 原始自然语言。
- 期望玩法合同。
- 关键硬约束。
- 自动验收。
- 禁止出现的退化。

## 6. M3：Web 3D 垂直样条，8—12 周

目标：不复制产品工作流，新增 `web-3d` 运行时适配器并交付第一款真实可玩的 3D 黄金游戏。

范围：

- 与引擎无关的 3D game-spec 字段和能力匹配。
- 3D 场景、相机、控制器、碰撞、触发器和音频空间。
- GLB/glTF 资产清单、加载校验和性能预算。
- 小型遗迹收集与撤离黄金游戏。
- 桌面和移动端真实试玩、状态探针、性能与降级报告。
- 与 2D 共用项目、时间线、版本、回滚、证据和发布。

退出条件：

- 至少 10 个 3D 场景提示能够构建，且 7 个以上进入可完成的可玩预览。
- 相机、移动、碰撞、收集、输赢和重开均有自动证据。
- 3D 失败能归因到规格、资产、场景、运行时、性能或测试，不大量落入“未知”。
- 新增 3D 没有复制一套项目、版本和事件后端。
- 现有 2D 黄金游戏回归通过。

## 7. M4：开放能力平台

范围：

- 运行时适配器 SDK 和能力清单。
- Godot 等专业引擎工程适配器。
- 可安装的玩法技能、资产管线和测试驱动。
- 第三人称战斗、载具、复杂 AI、程序世界等 3D 能力包。
- 异步和实时多人黄金游戏。

任何新能力先进入内部实验目录；通过自己的黄金游戏和全量回归后，才对用户显示为“稳定支持”。

| SPEC-002 | acceptance DSL | 三消 12 项验收可表达 |
| RUNTIME-000 | runtime adapter contract | 能力声明、脚手架、构建、测试和打包接口完整 |
| RUNTIME-001 | Phaser adapter | 生命周期和输入在桌面/手机可测 |
| RUNTIME-002 | debug bridge | 状态只读、动作白名单、发布默认关闭 |
| FIXTURE-001 | 迁移三消纯核心 | 原有 8 项规则测试全部通过 |
| FIXTURE-002 | 三消 Phaser 适配 | 完成一局和重开 |
| BUILD-001 | 一次性构建沙箱 | 无外网、有限额、产物可提取 |
| EVENT-001 | build_event + SSE | 断线续传、顺序稳定、无假进度 |
| TEST-001 | Playwright 试玩 | 玩家→AI→结算→重开全路径证据 |
| VERSION-001 | 不可变版本 | 新修改不会破坏旧预览 |
| DEPLOY-001 | 对象存储与 CDN 发布 | 构建包原子部署，资源无 404，失败不影响线上版 |
| URL-001 | 三类游戏网址 | 预览、不可变版本、稳定玩家网址职责和生命周期可验证 |
| URL-002 | 域名隔离 | 游戏来源无法读取主站 Cookie、令牌和存储 |
| DATA-001（P1） | 游戏数据 API | 项目作用域云存档有配额、版本兼容和权限测试 |
| DATA-002（P1） | 排行榜 | 成绩限流、幂等、赛季和可信级别可验证 |
| RELEASE-001 | 原子发布与回滚 | 稳定网址切换失败时仍服务上一健康版本 |
| CHANGE-001 | 变化合同 | 伤害参数修改只失效相关产物 |
| UI-001 | 新建与合同原型 | 不懂代码用户能完成确认 |
| UI-002 | 制作工作台原型 | 时间线、预览、证据三部分清楚 |
| SECURITY-001 | 预览隔离 | 生成游戏无法读取主站会话与存储 |
| OBS-001 | 成本与耗时记录 | 每步可汇总，不记录密钥 |

## 9. 定义完成

任何“可玩版本”必须同时满足：

- 构建成功。
- 运行时合同存在。
- 基础规则测试通过。
- 浏览器真实流程通过。
- 没有未处理控制台错误。
- 手机目标画幅可操作。
- 关键验收有状态或截图证据。
- 资源来源与许可证元数据完整。
- 安全扫描通过。
- 文件快照不可变。
- 稳定玩家网址和不可变版本网址均可通过 HTTPS 打开。
- CDN 资源无 404，冷启动、缓存和版本切换通过检查。
- 启用服务器数据的游戏通过权限、配额和数据隔离测试。
- 发布失败不会替换上一健康版本，回滚不需要重新生成。
- 未验证项明确列出。

“模型说已完成”不属于完成证据。

## 10. 风险台账

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 骨架导致换皮 | 不同提示产生相同场景和节奏 | 骨架只提供机械能力；加入多样性基准 |
| 平台被首个样例锁死 | 规格和数据表出现三消专属字段 | 通用规格只描述能力；三消字段留在能力包和游戏项目内 |
| 2D 与 3D 形成两套产品 | 3D 需要复制项目、版本和时间线 | 固定运行时适配器协议；只替换生成、构建和测试驱动 |
| 3D 只能展示不能玩 | 只有场景截图，没有控制和结算证据 | 3D 黄金游戏强制真实操作、状态探针和性能预算 |
| 自由生成破坏结构 | 频繁改入口、依赖和构建脚本 | 限制可写目录和依赖白名单 |
| 修复循环耗尽预算 | 同一错误重复出现 | 错误指纹、最多 2—3 次、回退成功版 |
| 测试过于脆弱 | 视觉小改导致大量失败 | 规则用状态探针，视觉只检查几何与关键截图 |
| 测试被游戏迎合 | 只在测试种子工作 | 固定夹具 + 随机种子 + 隐藏回归集 |
| 素材不一致 | 角色每张图外观变化 | 风格锚点、派生关系和局部重生成 |
| 许可证污染 | 产物来源缺失或模型不允许商用 | 资源清单强制来源，发布前策略检查 |
| 沙箱逃逸 | 生成代码尝试外网或宿主访问 | 网络默认拒绝、一次性容器、独立预览来源 |
| 事件状态不一致 | UI 显示通过但数据库失败 | 单一权威 build_event |
| 游戏网址与版本混淆 | 更新草稿意外改变线上游戏 | 稳定网址只指向 publication，不直接指向草稿构建 |
| 玩家数据越权 | 一个游戏读取另一游戏存档 | 项目作用域令牌、数据库角色隔离和边界测试 |
| 静态游戏成本失控 | 每个小游戏常驻一台服务器 | 静态包走对象存储和 CDN，动态服务按需启用 |
| CDN 缓存旧资源 | 新版本 HTML 引用了旧文件 | 内容哈希文件名、不可变缓存和原子入口切换 |
| 用户不懂测试 | 证据面板被忽略 | 默认显示结论和影响，技术证据按需展开 |

## 11. 阶段决策门

完成 M0 后只做三种判断：

- **GO**：闭环稳定，失败可定位，成本可接受，进入 M1。
- **NARROW**：链路有效但开放生成太不稳，暂时只公开已通过黄金游戏的能力，同时继续建设扩展协议。
- **STOP**：即使固定黄金样例也无法稳定构建、测试或回退，先修基础设施，暂停扩展新能力。

阶段决策只改变公开节奏和投入顺序，不把长期产品改写成三消或固定三类游戏生成器。

下一阶段的首个代码提交应只包含 STUDIO-001、SPEC-001、SPEC-002 和最小测试，不同时引入模型调用、图片生成和社区功能。
