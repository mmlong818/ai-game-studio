# 三消黄金流程提取

> 参考项目：E:\codex\ai-match3-duel  
> 项目状态：本轮重新运行 npm.cmd run check，8 项规则测试全部通过，结构检查通过。

## 1. 为什么把三消作为第一个黄金样例

它不是简单的“棋子能消除”演示，而是同时覆盖：

- 共享棋盘和区域操作权限。
- AI 与玩家的回合状态机。
- 合法交换和非法回退。
- 多段消除与归属。
- 伤害、生命值和结算。
- 无解棋盘重建。
- 鼠标、触控和滑动。
- 动画、音频和可访问性。
- PWA、离线包和 Android APK。
- 规则单元测试与页面结构检查。

这些能力足以验证平台最重要的生成、测试、修改、打包和版本链路。

## 2. 从最初想法到成品的完整流程

### 阶段 1：把自然语言变成硬规则

原始核心意图：

- 玩家和 AI 在同一个三消局面中对抗。
- 玩家只能操作下半区。
- AI 只能操作上半区。
- 消除攻击对方。
- 一次行动引发的连消归行动发起者。

规则化后形成：

- 8×8 棋盘、6 类棋子。
- 区域只限制交换，不限制匹配、下落和连消。
- 非法交换立即回退，不消耗行动。
- 玩家行动完整稳定后才交给 AI。
- 每组 3 枚得 5 分，每多一枚翻倍。
- 任一方积分归零结束。
- 初始积分可在 100—1000 中按 100 调整。

可复用能力：**约束抽取器、歧义澄清器、玩法合同生成器**。

### 阶段 2：把规则做成纯逻辑

game-core.js 把重要规则从界面中分离：

- 创建带种子的随机数。
- 归一化起始分数。
- 判断相邻和区域归属。
- 不修改原棋盘的交换。
- 横向、纵向匹配分组和去重。
- 查找双方合法走法。
- AI 选择走法。
- 计分和对手扣分。
- 消除、下落和补充。
- 创建无初始匹配且双方都有走法的棋盘。
- 连消预演。

可复用能力：**生成游戏必须把关键规则放进可测试的纯模块，不允许全部埋进动画回调**。

### 阶段 3：实现真实用户体验

app.js 负责：

- 创建和渲染棋盘。
- 根据回合禁用不可操作区域。
- 显示当前行动方、分数、伤害和战斗日志。
- 交换、非法交换、消除、下落、粒子和连消反馈。
- WebAudio 程序化音效。
- AI 行动高亮和延迟。
- 点击两枚棋子与滑动换位。
- 新手说明和初始积分选择。
- PWA 安装入口和服务工作器。
- 尊重 prefers-reduced-motion。
- 用游戏版本号中断已经过期的异步动画。

可复用能力：**平台运行时负责生命周期、输入、音频、缩放和异步任务取消**。

### 阶段 4：建立验证

规则测试覆盖：

1. 初始分数范围和步进。
2. 玩家与 AI 的区域操作权限。
3. 横纵匹配合并且不重复。
4. 新棋盘没有预消除且双方都有合法走法。
5. 有效交换产生消除且原棋盘不被修改。
6. 计分公式。
7. 首消与连消都归行动者并攻击对方。
8. 分数不会扣成负数。

结构检查覆盖：

- 棋盘、AI 禁操作提示、玩家区提示。
- 新手引导、结算、积分范围。
- 回合与战斗信息。
- 移动端布局、安全区和减少动画。
- AI/玩家都进入真实执行流程。
- 消除动画和粒子。
- 滑动手势。
- PWA 清单、图标和离线缓存。
- 双方合法走法保证。

可复用能力：**玩法验收 + 页面结构 + 浏览器真实流程三层验证**。

### 阶段 5：交付多种运行形态

- 网页本地服务。
- PWA 发布目录。
- 可安装的 Android 离线 APK。
- GitHub Release 下载。

可复用能力：**构建目标与游戏逻辑分离，成功版本可以派生不同发布包**。

## 3. 平台应抽取的可复用协议

### 3.1 游戏规格

文件：game-spec.json

- 核心承诺。
- 玩法类型。
- 操作。
- 硬约束。
- 状态和胜负。
- 规则参数。
- 非目标。
- 验收标准。

### 3.2 运行时合同

每个生成游戏实现：

~~~ts
interface GeneratedGame {
  mount(container: HTMLElement, services: GameServices): Promise<void>;
  pause(): void;
  resume(): void;
  restart(): Promise<void>;
  destroy(): void;
  getDebugState(): SerializableGameState;
  dispatchTestAction(action: TestAction): Promise<TestActionResult>;
}
~~~

### 3.3 资源清单

每个资源记录：

- 逻辑角色，例如 player_ship、board_background、match_sfx。
- 文件类型、尺寸、帧数和透明背景要求。
- 生成输入摘要。
- 风格锚点。
- 来源、许可证和内容哈希。
- 被哪些场景或对象引用。

### 3.4 验收 DSL

~~~yaml
- id: MATCH3-OWNER-01
  given: game.phase == player
  when:
    action: swap
    from: [4, 1]
    to: [4, 2]
  then:
    - board.changed == true
    - phase.eventually == ai

- id: MATCH3-CASCADE-01
  given: seeded_board == cascade_fixture_01
  when:
    action: swap
    actor: player
  then:
    - cascade_count >= 2
    - all_damage_owner == player
    - ai_score_decreased == total_damage
~~~

### 3.5 构建事件

每一步都写入统一事件：

- 阶段。
- 动作名称。
- 用户可见摘要。
- 公开参数摘要。
- 状态。
- 输入和输出产物。
- 测试证据。
- 错误分类。
- 重试次数、耗时和成本。

## 5. 作为首个生成样条的用法

### 样条 A：复现合同

输入原始自然语言需求，让系统生成玩法合同；与已确认合同比较，检查硬约束是否丢失。

### 样条 B：从骨架生成

使用 grid_logic 骨架和程序化资源生成可玩版本，通过 M3-01 至 M3-10。

### 样条 C：局部修改

用户提出：“把每组 3 枚的基础伤害从 5 调成 8，但不要改变连消归属和区域权限。”

平台必须：

- 生成变化合同。
- 只修改计分参数和对应测试。
- 重跑计分、伤害、连消、区域和完整回合流程。
- 生成新版本，不覆盖旧版本。

### 样条 D：视觉替换

用户提出：“从星梦主题改成深海生物发光主题，规则不变。”

平台必须：

- 保持纯规则模块内容哈希不变。
- 只使资源、资源引用和视觉截图验收失效。
- 不重新生成或修改区域、计分和 AI 逻辑。

## 6. 不能误用的部分

- 当前三消项目是一个黄金夹具，不应成为所有生成游戏的隐藏母版。
- 复用的是协议、测试方法和运行时能力，不是把所有游戏换皮成三消。
- MakePlay 页面记录提供的是公开工作流证据，不是可复制的内部系统提示词。
- Android APK 属于后续发布能力，不应阻塞首版网页生成闭环。
