# 借鉴 GDevelop 的游戏能力平台化开发目标

> 状态：已完成（2026-09-03，阶段 A—F 全部通过退出验收）
> 制定日期：2026-09-03
> 实施版本：1.1（与既有 1.0 运行和数据保持隔离）
> 产品定位：AI 单人网页小游戏制作平台
> 关联文档：`docs/00-product-definition-v2.md`、`docs/06-creation-loop-capability-plan.md`、`docs/33-game-design-knowledge.md`、`docs/55-adding-an-official-game.md`

## 1. 目标

本轮开发不把平台改造成通用游戏 IDE，也不整体接入 GDevelop。目标是吸收 GDevelop 最适合 AI 创作平台的结构化能力，让 AI 可以基于稳定的场景、对象、行为、规则和资源修改游戏，而不是继续直接拼接或重写大段运行时代码。

所有新增工程协议和能力模块归属平台 1.1。1.0 项目继续走现有生成、运行、发布和存档路径；只有明确迁移并通过回归检查的项目才切换到 1.1，禁止原地批量改写旧项目。

完成后，平台应同时具备两种体验：

- 对普通用户：仍然只需描述需求、试玩、继续提意见和发布，不需要学习事件表、对象树或代码。
- 对平台内部：每次创作和改造都有明确对象、规则、资源、影响范围、自动检查和可回滚版本。

核心结果是把当前以“整款游戏模板”为主的复用方式，升级为三级结构：

```text
官方游戏
  └─ 玩法模板
       └─ 可组合能力模块
```

## 2. 研究结论与采用边界

GDevelop 将项目结构、运行引擎、扩展能力和编辑器分开；项目由场景、对象、行为、事件、变量和资源组成，事件最终生成运行代码。它还将对象、行为、条件、动作和表达式作为扩展能力提供，并在导出阶段分析场景、资源与扩展依赖。

本平台采用其中的架构思想和可独立验证的实现方法，不追求项目文件兼容，也不复制其编辑器交互。

研究依据：

- [GDevelop 技术架构](https://github.com/4ian/GDevelop/blob/master/Core/GDevelop-Architecture-Overview.md)
- [GDevelop 扩展机制](https://github.com/4ian/GDevelop/blob/master/newIDE/README-extensions.md)
- [GDevelop 导出与依赖分析](https://github.com/4ian/GDevelop/blob/master/newIDE/docs/How-are-exporters-and-platforms-working.md)
- [GDevelop 官方与实验扩展仓库](https://github.com/GDevelopApp/GDevelop-extensions)
- [GDevelop 代码许可](https://github.com/4ian/GDevelop/blob/master/LICENSE.md)
- [GDevelop 资产商店许可](https://gdevelop.io/page/asset-store-license-agreement)

### 明确采用

- 编辑结构与游戏运行时分离。
- 场景、对象、实例、行为、规则、变量和资源的统一工程模型。
- 可组合、可声明、可单测的玩法能力模块。
- “条件—动作”形式的内部规则表达。
- 预制对象和场景组件。
- 资源清单、引用追踪、依赖裁剪和完整打包。
- 开发态调试、性能观测和有限热更新。
- 稳定、实验、项目专用三级能力治理。

### 明确不采用

- 不整体嵌入 GDevelop、GDJS、C++ Core 或 WebAssembly 桥接层。
- 不复制完整桌面 IDE、事件表、代码编辑器和复杂属性面板。
- 不在当前阶段支持任意 JavaScript 插件或未经审核的社区扩展。
- 不扩展原生 iOS、Android、桌面、多人与广告内购能力。
- 不以兼容 GDevelop 项目文件为目标。
- 不直接搬运 GDevelop 资产商店的图片、音频或模板。

## 3. 总体成功标准

本计划只有同时达到以下结果才算完成：

1. 一款游戏可以由统一工程数据完整描述，并从该数据生成可运行网页产物。
2. 至少四类玩法不再各自重复实现移动、碰撞、计分、触控和状态流程。
3. AI 修改游戏时，先产生结构化变更集，再生成产物，不直接以自由代码修改作为默认路径。
4. 每个玩法能力模块自带自动检查，组合进游戏后自动加入对应验收。
5. 删除或改名对象、规则和资源时，系统能发现引用并拒绝产生悬空依赖。
6. 发布包和开源包仅包含实际使用且来源清楚的资源，并可在无远程依赖时独立运行。
7. 用户仍能通过一句话完成改造，不因底层能力增强而承担额外编辑复杂度。
8. 现有官方游戏的可玩行为、发布地址和版本证据保持兼容，迁移过程中不整体停机重写。

## 4. 目标架构

### 4.1 游戏工程 `GameProjectV3`

`GameProjectV3` 是创作、修改、预览、验收、发布和打包共同使用的真相来源，至少包含：

| 区域 | 必要内容 |
| --- | --- |
| `metadata` | 游戏 ID、名称、版本、玩法类型、状态、目标视口 |
| `scenes` | 游戏、菜单、暂停、结算等场景及切换关系 |
| `objects` | 玩家、危险、奖励、背景、界面、特效和辅助对象 |
| `instances` | 对象实例的位置、尺寸、层级、锚点和实例覆盖参数 |
| `behaviors` | 对象绑定的能力模块及参数 |
| `rules` | 条件、动作、执行顺序和规则作用域 |
| `variables` | 全局、场景、对象和持久化状态 |
| `resources` | 位图、音频、字体、模型、动画和派生文件 |
| `controls` | 键盘、鼠标、触控和可选手柄映射 |
| `presentation` | 摄像机、震动、粒子、转场、音频反馈和响应式布局 |
| `acceptance` | 场景探针、能力探针、设备检查和人工复核项 |

所有场景、对象、实例、行为、规则和资源必须使用稳定 ID。用户可读名称可以修改，内部引用不能依赖显示名称或文件名。

### 4.2 能力模块 `MechanicModule`

能力模块是平台最小的可复用玩法单元。每个模块必须声明：

- 唯一 ID、版本、稳定级别和适用对象类型。
- 用户能理解的能力名称与体验目标。
- 输入、输出、可调参数、默认值和安全范围。
- 运行时实现及所需资源。
- 与其他模块的依赖、冲突和执行顺序。
- 自动探针、性能预算和移动端要求。
- AI 可以修改的参数，以及必须重新设计规则才能修改的参数。

第一批能力模块固定为：

1. 游戏开始、暂停、重开、胜利和失败状态机。
2. 键盘、指针和移动端触控输入。
3. 位置、速度、加速度、转向、边界和摄像机跟随。
4. 碰撞、受伤、无敌帧、收集与销毁。
5. 计分、生命、倒计时、关卡进度和最高分。
6. 对象生成、难度递增、离屏回收和对象池。
7. 屏幕震动、粒子、命中特效、音乐和音效反馈。
8. 本地存档、继续游戏和版本迁移。

### 4.3 内部规则 `GameRule`

规则使用“条件成立后执行动作”的结构表达。它是 AI、构建器和验收系统使用的内部格式，不要求普通用户直接编辑。

```json
{
  "id": "collect-water-drop",
  "when": {
    "type": "collision",
    "source": "player.headHitbox",
    "target": "waterDrop"
  },
  "then": [
    { "type": "addScore", "value": 1 },
    { "type": "playEffect", "effect": "waterBurst" },
    { "type": "playSound", "sound": "collectDrop" },
    { "type": "destroy", "target": "waterDrop" }
  ]
}
```

每种条件和动作必须来自受控注册表，具有参数结构、类型校验、运行实现和测试生成方式。第一阶段禁止在规则中嵌入任意脚本。

### 4.4 预制组件 `GamePrefab`

预制组件用于复用多个对象、行为、规则和资源插槽组成的完整功能。首批组件包括：

- 开始、暂停、重开和结算界面。
- 分数、生命、倒计时 HUD。
- 移动端虚拟控制与安全区适配。
- 收集物、障碍组、受伤反馈和奖励反馈。
- 教学提示与首次游玩引导。
- “边玩边改”固定按钮和意见浮层。

预制组件只定义结构、行为和资源插槽；游戏核心美术继续使用来源明确的 AI 位图，不用固定 SVG 充当游戏美术。

### 4.5 资源与授权 `ResourceManifest`

每项资源至少记录：

- 稳定资源 ID、用途、格式、尺寸、内容哈希和当前版本。
- 原始文件、加工步骤和派生文件。
- 使用它的场景、对象、动画、规则或组件。
- AI 生图提示词、模型、生成时间和来源说明。
- 是否允许进入发布包、开源包或模板。
- 加载策略、失败替代方案和性能预算。

构建前必须检查缺失引用、未使用资源、外部地址、禁止格式、重复大文件和授权不明资源。涉及直接采用 MIT 代码时保留许可与版权说明；GDevelop 名称、标志和资产商店内容不作为可自由复用代码处理。

### 4.6 开发态观测 `RuntimeInspector`

运行中的游戏至少向工作台提供：

- 当前场景、游戏状态和最近状态切换。
- 玩家位置、速度、碰撞框和输入状态。
- 活跃对象数量、生成与销毁统计。
- 最近触发的规则和碰撞双方。
- 资源加载错误和当前音频状态。
- 帧率、长帧、内存趋势和对象峰值。

工作台面向用户只展示开发进度、明确问题和试玩结果；详细状态主要供 AI 和质量系统使用。

## 5. 开发阶段与退出条件

### 阶段 A：工程模型与迁移通道

目标：建立 `GameProjectV3`、稳定 ID、引用索引和版本迁移，不改变普通用户流程。

交付物：

- 工程结构及运行时校验器。
- 旧项目到新结构的兼容适配层。
- 对象、规则和资源引用索引。
- 改名、删除、复制时的引用安全检查。
- 能读取新工程并生成最小可运行游戏的编译入口。

退出条件：

- 同一工程连续序列化两次结果稳定。
- 悬空对象、规则或资源引用会在构建前失败并指出来源。
- 至少一款黄金游戏能够从新结构生成，玩法结果与迁移前一致。

### 阶段 B：能力模块与自动探针

目标：把跨游戏重复逻辑从整游戏生成器中抽出，形成受控能力库。

交付物：

- `MechanicModule` 注册表和运行时装配器。
- 第一批八类通用能力。
- 模块依赖、冲突和参数范围校验。
- 模块随附的功能、手机和性能探针。

退出条件：

- 至少四类黄金游戏共享通用状态、输入、碰撞、计分和移动端能力。
- 任一能力参数越界都会在生成前被拒绝或修正。
- 新游戏加入能力后，无需手写即可获得该能力的基础验收。

### 阶段 C：结构化规则与 AI 变更集

目标：让 AI 默认修改对象、参数、资源和规则，而不是直接重写产物代码。

交付物：

- 条件、动作和规则注册表。
- 规则解释、校验和运行代码生成。
- 自然语言需求到结构化变更集的生成流程。
- 变更影响分析、受影响测试选择和整组回滚。

退出条件：

- 收集、受伤、胜负、计分和生成规则可以完整结构化表达。
- 用户每次改造都能显示普通语言版本的“改了什么、影响什么”。
- 资源、对象或规则变化会让相关旧证据失效并自动重验。

### 阶段 D：预制组件与多玩法迁移

目标：用能力和规则组合出可靠组件，并逐步迁移官方游戏。

交付物：

- 首批 HUD、控制、状态、收集、障碍、反馈和边玩边改组件。
- 组件资源插槽和响应式布局规则。
- 官方游戏迁移清单和逐款回归报告。

退出条件：

- 新游戏可以主要通过模板、组件和能力模块组装完成。
- 组件在桌面和手机参考视口均不遮挡核心玩法。
- 迁移游戏保持原有公开地址、存档兼容和发布状态。

### 阶段 E：调试、性能与草稿热更新

目标：缩短“用户提意见—AI 修改—重新试玩”的等待，并提高问题定位精度。

交付物：

- `RuntimeInspector` 协议和状态快照。
- 最近规则、碰撞、输入、音频和资源错误追踪。
- 帧率、长帧、内存与对象数量预算。
- 只覆盖安全变更的草稿热更新。
- 审核和发布时的完整冻结构建。

退出条件：

- 常见的碰撞过大、不可通行、输入失效、资源失败和性能退化可以被数据定位。
- 安全参数和资源替换可以在草稿试玩中快速生效。
- 热更新从不替代审核构建；发布结果仍可复现并绑定完整证据。

### 阶段 F：能力治理与有限开放

目标：让能力库可以持续扩展，同时不牺牲安全和发布质量。

交付物：

- `stable`、`experimental`、`project` 三级能力状态。
- 版本兼容、升级迁移和弃用机制。
- 权限、资源、网络和持久化能力声明。
- 扩展审核与晋级标准。

退出条件：

- 只有稳定能力能默认进入官方游戏和公开模板。
- 实验能力有明确隔离、风险提示和回退路径。
- 项目专用能力经过多游戏验证后可以无破坏地晋级。

## 6. 现有代码的落点

| 现有区域 | 调整目标 |
| --- | --- |
| `src/shared/official-games/` | 继续作为官方成品游戏唯一登记来源，不承担所有底层玩法实现 |
| `src/domain/templates.ts` | 保留用户可理解的玩法模板，逐步改为引用能力和组件组合 |
| `src/server/game-artifact.ts` | 从综合型生成器拆为工程编译入口、模块装配和产物封装 |
| `src/domain/probe.ts` | 保留游戏级探针，补充能力模块探针注册与组合机制 |
| `src/server/browser-quality.ts` | 拆分通用运行检查、能力检查、设备检查和具体游戏体验检查 |
| `src/server/build-orchestrator.ts` | 接入工程校验、依赖收集、最小受影响测试和冻结构建 |

建议新增的边界目录为：

```text
src/shared/project-schema/   统一工程结构、稳定 ID 和引用类型
src/shared/mechanics/        能力模块声明与注册表
src/shared/rules/            条件、动作和规则结构
src/shared/prefabs/          官方预制组件声明
src/server/game-compiler/    工程到网页产物的编译与装配
src/server/runtime-inspector/开发态观测和调试协议
```

这些目录是责任边界，不要求一次性建立全部空壳；只有某一阶段开始实现时才创建对应目录和代码。

## 7. 迁移策略

采用纵向切片，不进行全量重写：

1. 先选择一款同时包含移动、碰撞、收集、反馈和移动端操作的黄金游戏贯通阶段 A 至 C。
2. 第二款选择棋盘或逻辑游戏，验证工程模型不只适用于动作游戏。
3. 第三款选择射击或跑酷游戏，验证生成、对象池、速度感和性能预算。
4. 第四款选择 3D 游戏，验证同一工程模型可以由不同运行时适配。
5. 四类通过后再批量迁移其他官方游戏。

每次迁移都必须保留旧实现作为可回退健康版本，直到新实现通过规则、浏览器、手机、视觉和真实试玩检查。

## 8. 质量门槛

每次开发交付至少通过：

- 工程结构和引用完整性检查。
- TypeScript 类型检查与单元测试。
- 能力模块合同测试。
- 浏览器启动、输入、胜负、重开和关键规则探针。
- 桌面与手机参考视口检查。
- 资源清单、授权来源和离线打包检查。
- 受影响游戏回归测试。
- 至少一次真实试玩判断；速度感、美术一致性和操作爽点不能仅由静态探针判定。

若某项只能人工判断，必须标记“待复核”，不能以构建成功代替体验通过。

## 9. 主要风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 过度抽象导致开发停滞 | 只从真实黄金游戏抽取已出现两次以上的通用能力 |
| 为兼容旧游戏形成两套永久体系 | 每个阶段都指定迁移对象、删除条件和退出标准 |
| AI 生成规则仍然不可控 | 条件和动作只能来自类型化注册表，禁止默认执行任意脚本 |
| 模块组合产生冲突 | 模块声明依赖、互斥、执行顺序和参数范围，构建前校验 |
| 热更新掩盖最终构建问题 | 草稿热更新与审核冻结构建严格分离 |
| 资源授权或密钥泄漏 | 构建前扫描来源、远程依赖、凭证和包内敏感文件 |
| 平台界面重新变复杂 | 底层结构默认不暴露，用户仍以自然语言和试玩为主 |

## 10. 第一实施切片

第一实施切片只做能够证明方向正确的最小闭环：

1. 定义 `GameProjectV3` 的场景、对象、实例、资源和行为最小结构。
2. 定义状态机、输入、二维移动、边界、碰撞、收集、计分七个能力模块。
3. 定义碰撞、输入、计时三种条件，以及移动、计分、销毁、播放反馈、切换状态五种动作。
4. 将“虫虫攀枝”或当前质量最高的同类动作黄金游戏迁移为首个样板。
5. 用同一工程生成桌面与手机产物，自动执行能力探针。
6. 证明“头部碰到水滴—加分—爆开—消失”能由结构化规则表达、运行、测试和回滚。

第一切片完成的证据必须包括：工程 JSON、生成产物、桌面与手机试玩截图、自动探针结果、资源清单、前后版本变更集和回滚结果。只有这些证据齐全，才进入第二类游戏迁移。
