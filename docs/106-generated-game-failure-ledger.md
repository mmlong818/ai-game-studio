# 生成游戏失败台账与复盘

更新时间：2026-09-11。本文记录可重复出现、会阻断制作或发布的问题。它是工程记忆，不是上线声明；实际发布状态仍以数据库和正式审核为准。

## 使用规则

修复生成链路、质量门禁、重试或恢复流程前，先查本台账。发现同一失败签名时，先判断它属于模型执行、平台确定性能力、标准过严，还是流程规则缺失，不应只增加一次模型重试。

状态分四栏记录：

- **实现已改**：当前工作树或已发布代码中已有实现；必须注明是否仍未提交。
- **自动测试过**：定向测试或类型检查通过，不等于真实制作成功。
- **真实成功验证**：真实构建已越过对应阶段，或完整游戏已交付；必须写清验证边界。
- **未闭环**：仍需真实制作、发布或产品规则修正。只有完整交付成功才能关闭“无法上市”问题。

## 问题台账

### P0-00：没有资源实现策略路由，所有生成游戏被强制位图化

- **分类**：产品架构/流程规则缺失。
- **证据**：当前 `generatedBlueprint` 要求 `sprites` 至少 2、最多 5 个；规划提示称这些主体会在代码前生成透明位图。代码合同明确禁止用 Canvas 路径、圆形、多边形或渐变绘制主体。编排器在 asset 阶段要求 AI 服务存在、AI cover 非空、背景存在、每个 planned sprite 都落盘，否则构建中断；代码扫描又要求加载全部蓝图资源。本项目因此固定生成 cover、background、escape-arrow、stone-block、exit-gate、collision-spark 六张图片。用户输入只要求复刻参考玩法，`spriteAnimation:auto` 表示平台在适用时自动选择，并不能证明用户明确要求 AI 图片或动画。
- **本项目可程序化程度**：箭头是带方向语义的几何交互件，可用路径、描边、纹理/文字标签和位移补间绘制；石块是棋盘阻挡格；出口是边界缺口/方向刻线；火花是短时粒子；棋盘背景也可由颜色、网格和低频纹理生成。这些都服务精确碰撞、方向与状态反馈，程序绘制通常比位图更直接。封面可由通过验收的运行时截图加标题卡生成。本次没有做视觉 A/B，不能断言零生图一定更美，但可以确认它足以表达核心规则且绕开本项目所有图片/Sprite 硬失败。
- **用户影响**：本可先交付的核心玩法被扩成六项图片生成、透明主体、逐帧图集、边缘和九参数绘制合同；前四次停在图片，后三次停在动画证明，形成额外模型用量和十多轮无效代码修复。
- **实现已改**：尚无策略路由。当前工作树的图片 repair、presentation 和 registry 只改善 bitmap 路线，不能解决“是否应该生图”的上游决策。
- **自动测试过**：无零生图 generated game 端到端 fixture。
- **真实成功验证**：无。
- **未闭环**：在已确认方案中增加小型、可消费的 `assetImplementation: procedural | bitmap | hybrid`（也可按槽位声明）。允许蓝图 `sprites` 在 procedural 路线为 0；dynamic art、AI key、alpha/edge/minSourcePixels、Sprite runtime 和“必须加载全部位图”检查只对 bitmap 槽位启用。程序槽位必须声明形状语义、状态、命中区域、颜色/纹理及无障碍冗余，仍接受布局和真实玩法验收。
- **建议执行顺序**：先用规则判定器选择策略：几何棋盘、方向符号、连线、粒子、抽象卡牌优先 procedural；角色表演、题材插画、写实背景或用户明确要求美术时选 bitmap；混合游戏只生成真正需要的少数资源。代码先生成并验证核心循环，封面在运行时通过后由确定性截图/卡片合成；只有用户明确选择或视觉合同要求时才调用 AI cover。
- **预防/验收**：加入零图片箭头棋盘 fixture，未配置图片 key 也能完成 analyze→code→test→delivery，artifact 中没有动态图片 receipt，三档视口玩法/方向/碰撞/帮助通过；另保留 bitmap/hybrid fixture，证明用户明确要求图片时现有质量门禁仍生效。策略变更必须进入 cache identity 和用户可见的制作范围，但不能把 procedural 槽位塞入图片 fingerprint。

- **用户影响**：同一资源反复生成、消耗时间和可能的模型用量，游戏没有更接近可玩交付。
- **实现已改**：当前未提交工作树把边缘接触降为 warning，并保留结构、透明度和帧合同的硬校验；图片单资源有受限自动修复次数。
- **自动测试过**：Sprite 与 image generator 定向测试已覆盖 warning、逐帧校验和预算。
- **真实成功验证**：`ad12…` 和 `cb4…` 在有边缘提醒时真实越过 asset 阶段。这只验证门禁不再误停，不代表最终游戏成功。
- **未闭环**：需要一条完整真实制作到交付；若 warning 对实际视觉有影响，应通过试玩或可测主体边界修正，不能恢复为无条件硬失败。
- **预防/验收**：失败签名连续两次出现应停止同样的付费重生，优先程序化 padding/contain 或把问题转入可审查 warning。资源硬门禁只保留会破坏解码、透明主体、帧网格或交付尺寸的条件。

### P0-02：生成代码丢失动画合同，平台曾要求模型手工复写元数据

- **分类**：模型执行问题 + 平台确定性能力缺口。
- **证据**：`b649…` 第二轮把简写对象传入 `create`，运行时读取 `animation.clips` 时报错；最终产物也使用 `{idle:{start,frames…}}` 这类不完整合同并吞掉异常。后续多轮持续出现“没有九参数 drawImage”或“只绘制单帧”。
- **用户影响**：图片已成功生成，但游戏无法证明动画播放，六轮代码重写仍失败。
- **实现已改**：当前未提交工作树会从蓝图注入 `__FORGE_SPRITE_SPECS__`，完整有效的调用参数优先；缺失或畸形参数按精确资源路径恢复，未知资源仍报错。URL query/hash 已兼容。
- **自动测试过**：覆盖未知资源不误配、完整合同优先、fallback 后 `play` 推进帧与九参数绘制。
- **真实成功验证**：`cb4…/app.js` 已真实包含两份完整注册合同，生成代码调用 helper；phone-standard 游戏态没有最终 Sprite 失败，证明注入和活动游戏态消费至少发生过。完整构建仍失败，不能标记关闭。
- **未闭环**：需要修复 P0-03 的采样状态后重新跑一条真实构建，确认三档视口在适用游戏态均观察到帧推进。
- **预防/验收**：动画元数据由平台按 asset id 注入；代码模型只选择 clip 和绘制位置，不再手工复写 frame grid。禁止空 `catch` 隐藏 helper 初始化错误，错误应进入可分类报告。

### P0-03：验收在首屏要求局内 Sprite 已绘制，导致正确的按状态显示被判失败

- **分类**：标准适用范围错误 + 验收流程缺口。
- **证据**：`cb4…` 最终报告中 phone-small 和 desktop-wide 的合同证据仅为“首屏可开局”，却对仅在游戏画布中绘制的箭头和火花执行 `collectSpriteSheetRuntimeFailures`。同一报告的 phone-standard 会进入 playing/result，且没有最终 Sprite 失败。产物注册表、helper 调用和九参数手工切片均存在。`ad12…` 六轮也稳定呈现 phone-small/desktop-wide 缺绘制，而活动的 phone-standard 多数轮次已通过。
- **用户影响**：质量门禁把“首屏没有局内对象”误当成动画实现错误；模型重写无法稳定解决状态不匹配，最终阻断上市。
- **实现已改**：当前未提交工作树让三档视口在 idle 布局截图后都进入 playing，并按常态动画至少两个帧周期采样。含 `idle/run` 的资源未绘制或不推进仍硬失败；纯 `hit/effect` 资源未触发时写入 `observations`，不伪称已经验证，一旦观察到绘制仍要求至少两个 source rect。
- **自动测试过**：browser-quality 定向测试覆盖常态完全不画、事件未观察的记录和事件只画单帧；类型检查通过。
- **真实成功验证**：对 `294ad9f9…` 的独立副本离线重跑后，三档动画误报全部消失，新增 phone-small/desktop-wide playing 截图；报告明确记录 collision-spark 事件未触发、未验证。该运行没有修改历史产物或启动模型，不等于真实新 build 成功。
- **未闭环**：离线副本仍正确保留五项真实失败：教学第 2 步未完成、信号序列错误、刷新恢复失败、第 9 关第 2 步未完成和机制复演错误。事件型资源还需要蓝图声明可触发事件或确定性动作探针，才能从“未观察”升级为通过。
- **预防/验收**：fixture 必须包含“菜单中不绘制、开局后播放”的动画，三档视口均通过；同时保留“开局后仍不绘制”和“时钟不推进”的负例。

### P0-04：修复循环记不住稳定失败签名

- **分类**：流程规则不全。
- **证据**：`b649…`、`ad12…`、`cb4…` 各记录六轮 `artifact-rejected`。同一 phone-small/desktop-wide 动画缺绘制跨 18 个代码轮次重复，三次都停在 sequence 3 code，sequence 4/5 未运行。跨 build 没有项目级失败签名、已尝试手段或“不再重复同策”的持久状态。一般流程还会在资源回写和 manifest 冻结后运行最终浏览器验收；该层失败不能回流代码修复，但本项目没有走到该层，不能把它写成本次根因。
- **用户影响**：用户只能再次点击制作；系统重复整段代码生成与验收，无法说明为什么上一轮修法无效。
- **实现已改**：继续制作按钮和失败说明已在当前未提交工作树补齐，但没有项目级问题记忆或失败签名断路器。
- **自动测试过**：UI 覆盖 code-only system repair 的文案、点击和旧失败不覆盖新任务；没有覆盖跨 build 去重和最终验收回流。

- **未闭环**：将标准化失败签名、适用状态、尝试过的确定性修复与结果写入项目/build 记录。相同签名连续出现时，停止同策略模型重写，转为平台修复或人工产品决策。另为最终验收增加独立 fixture，判断哪些最终资产问题可安全回到局部修复。
- **预防/验收**：测试同一签名跨轮次和跨 build 的累计、策略去重、预算停止、成功后清除；原失败 build 保持不可变，新 build 不被旧 terminal job 覆盖。

### P1-03：UI、资源与布局规划过去缺少同一可消费合同

- **分类**：流程规则不全；不是当前失败链的直接根因。
- **证据**：当前三次 code 失败的 `GEN-BROWSER-LAYOUT` 均通过，因此不能把本项目失败归因于“完全没有 UI 规划”。旧蓝图只描述资源文件/动画，缺少逻辑显示尺寸、区域、锚点、安全区和源图主体像素的统一消费路径。
- **用户影响**：模型容易混淆源像素、逻辑画布尺寸与响应式视口，资源验收和代码布局难以对齐。
- **实现已改**：当前未提交工作树增加 `region`、`fit`、归一化 `anchor`、`logicalSize`、`safeInsetRatio`、`minSourcePixels`，并接入资源处理、代码提示和浏览器逻辑上限检查；布局字段不进入付费图片缓存 identity。
- **自动测试过**：schema、fingerprint、transform metadata、浏览器采样均有定向测试。
- **真实成功验证**：没有完整真实交付。`ad12…`/`cb4…` 只证明资源阶段可继续，不能证明规划合同闭环成功。
- **未闭环**：用下一次无付费 fixture 验证 plan → asset metadata → runtime draw → browser report 的同一字段链；region 是语义规划，不能写成像素级位置硬验收。

### P1-04：`minSourcePixels` 默认值和语义仍需真实小动画校准

- **分类**：标准风险。
- **证据**：当前工作树默认值是 64，不是早期讨论中的 128；校验对象是 provider 草稿中每帧透明主体 alpha bbox 的短边，而非最终 `frameWidth × frameHeight`。这避免把目标帧格直接当源像素，但细长主体即使足以无放大交付，也可能因短边不足被拒。

## 与持续编码 Agent 工作流的差距

用户观察到普通 Codex 可在十几分钟内复刻相同参考，而造界多次仍不可用。本次没有做受控 A/B，也没有测量 Codex 的实际耗时，因此不能把“十几分钟”写成平台基准或断言模型能力差异。代码和产物能确认的是工作流差异：

1. **造界是多次整文件结构化输出，不是能操作工作区的持续 Agent。** `GameCodeGenerator.requestGame` 向兼容 Chat Completions 的 endpoint 发送 system/user messages，要求 strict JSON schema 返回完整 HTML。修复轮虽然带入上一版完整源码，但仍要求模型重新输出整份 HTML；模型不能自己打开浏览器、检查 DOM/Canvas 记录、编辑一个函数并复跑定向检查。
2. **模型看见的是文字合同和合并后的错误长串。** 当前 browser audit 在平台外部运行，截图和 Canvas probe 数据写入产物；修复请求只收到拼成一条的 failure reason。它没有直接获得截图、可查询的 DOM 状态、逐视口运行轨迹或精确失败函数位置。本项目 P0-03 的“首屏状态不适用”因此被反复翻译成“请让 Sprite Sheet 绘制”，整文件重写无法修正平台采样时机。
3. **参考输入没有形成可执行的浏览器研究证据。** 用户输入含参考 URL，但当前项目合同保留的是玩法描述和生成后的设计约束；本次产物没有可核实的参考页面截图、交互轨迹或源码分析交给代码生成器。不能据此判断模型是否准确看过参考站点。
4. **平台合同显著扩大了单次复刻范围。** 项目同时要求 18 关递进、安全教学、机制复演、连续失败帮助、刷新恢复、键鼠触控、三档画幅、真实位图和动画证明。`build_steps` 的 analyze 文本列出 13 条验收标准，浏览器报告实际覆盖合同、布局、视觉、错误、教学、递进、变化和帮助。这些可能是合理产品要求，但不是“先得到可玩的参考核心循环”的最短路径；它们把任何一项失败都变成整份游戏不能交付。
5. **已有代码复用不等于重新策划。** 普通同项目、无修改 directions 的继续制作会保留已确认 `designProfile`，并可恢复上一版完整源码；本项目 `cb4…` 也恢复了图片检查点。问题在于复用后仍走相同的整文件模型修复与同一误用门禁，而非每次必然重新设计项目。

目标工作流应让一个受控执行器在隔离工作区内读取当前源码、蓝图、资源 metadata、截图和 probe 记录，选择最小文件/函数修改，运行对应视口与状态的定向检查，再提交差异给平台的安全扫描和发布门禁。确定性的动画 registry、资源变换、状态导航和失败签名由平台工具完成；模型负责玩法实现和需要判断的局部修改。可先分两层交付：核心参考循环通过必需门禁后形成可玩 checkpoint，再逐项补教学、关卡、帮助和视觉复核。是否更快、更省调用，必须用同一确认方案、同一模型预算和同一验收标准做未来 A/B，本文不预设结果。

## 产品结论与关闭条件

当前游戏没有因为“标准严格所以应该放行”而失败；真正问题是硬标准应用在错误状态、相同失败没有形成项目记忆、确定性元数据曾交给模型猜。动画在实际游戏态必须推进仍是合理发布要求，不能直接删除。

本项目关闭条件：

1. 三档视口先进入动画适用的游戏/事件状态，再观察正确 source rect 和至少两个帧；首屏不绘制局内对象不失败。
2. 同一失败签名不再触发六轮同策略重写；报告显示已尝试策略、停止原因和后续责任方。
3. 资源检查点按 fingerprint 复用；任何重新生成在开始前准确提示范围与可能模型用量。
4. 一次真实构建完成 code、test、delivery，产生不可变版本；之后才可把本项目“无法上市”标记关闭。当前工作树修改和 mock 测试均不满足这一条件。

- **本轮落地**：`creationMode` 明确区分 `reference-replica` 与 `original-demo`；`referenceEvidence` 逐项记录 `observed/inferred/unknown`、claim、source。设计预览调用前会读取公开 HTTP/HTTPS 页面的标题、描述、正文规则文本，并索引 iframe/embed/script/link/img；在相同 SSRF、内容类型、大小和总时限边界内，最多跟进一小组公开文本 HTML/JS/CSS/JSON。证据 JSON 直接进入设计请求，解析结果只采用服务端采集的证据，不接受模型输出覆盖 observed。嵌入玩法交互、完整关卡、混淆代码、登录或付费资源仍明确 unknown；脚本文本不会执行，也尚不具备自动逆向或资源下载能力。参考模式本地丢弃模型擅自生成的 campaign/blueprint；无参考初次制作即使输入含扩关意向也先生成单局、无进度存档，扩关需绑定当前版本的显式 demo 审核。
- **浏览器执行边界**：浏览器验收现有全流程硬总时限；超时主动关闭浏览器和静态服务，并以 `BrowserTimeoutError` / `BROWSER_TIMEOUT` 明确分类，避免构建长期停留在 running。`campaign:null` 的单局 demo 不再强制 `setLevel`、难度变体、`runtimeSignature` 或 `mechanicsActive` 等递进探针；仍验证真实 start/play、胜负策略、重玩和自然核心操作。显式玩法机制仍由实际操作、静态合同和规则审核验证，不能用缺少调试字段替代玩法故障判断。
- **尚未具备**：系统不会自动操纵或逆向嵌入游戏，也不会绕过登录、付费或访问限制；没有自动下载参考资源。公开页面摘要不能证明实际玩法。抓取失败时保留 unknown，不能据此自由编造关数或机制。用户审核 demo 后的扩展审批由独立 review gate 负责。

### 2026-09-12：公开参考页面可读不等于平台已经试玩

- **分类**：能力边界 + 流程门禁。
- **真实证据**：对 Piece of Cake 公开页的文本检查取得 How to Play 与 Controls，确认页面描述了合并相同物品和拖动操作。受限 Playwright 检查看到一个公开游戏 iframe 和公开脚本 URL 索引；主站截图停在 “Preparing your game…”。随后在同一无 Cookie、无持久 profile、私网请求拦截的上下文直接打开公开 iframe，30 秒和 300 请求预算内仍未出现可见 Canvas，截图仅为加载背景。因为资源预算之后阻断了 31 个请求，这只能证明本次受限检查没有加载到可确认的运行画面，不能断言原游戏不可访问。
- **实现已改（当前未提交工作树）**：新增独立公开参考浏览器检查。初始网址、重定向与子资源均执行 DNS/私网校验；禁止下载与 WebSocket，限制请求数、时间和证据数量；仅记录去查询参数的网址、Canvas/iframe、公开脚本索引、两时点画面变化、控制台错误和截图。iframe、页面加载、脚本请求或画面变化都不能单独标记为玩法已验证；通用检查不执行猜测式点击。
- **流程规则**：外部参考即使已有公开文字，只要 `canClaimPlayable=false`，就在策划模型调用前返回 `REFERENCE_GAMEPLAY_UNVERIFIED`。界面以中性能力说明告知“已读介绍/本次未确认实际玩法”，请用户描述玩法；只有用户明确选择 `user-approved-original-demo` 且提供去掉 URL 后仍有效的玩法描述，才转为原创单局。可信 `sourceProjectId` 仍以服务端仓库中的已确认合同为准，客户端不能提交检查结果冒充已试玩。
- **自动测试过**：私网在启动浏览器驱动前拒绝；只有 iframe 的加载壳保持 `not-observed`；文字规则加可见运行画面最多标为 `runtime-viewed`，永不标为 `gameplay-verified`；外部未试玩参考的 planner 调用数为 0；明确同意前输入不会触发第二次请求。
- **真实门控验证**：Piece of Cake 原文经正式 design-preview 返回 `REFERENCE_GAMEPLAY_UNVERIFIED`，`done=false`，摘要为 `public-browser / not-observed / description-read / canClaimPlayable=false`；没有创建 project、build 或图片任务。
- **未闭环**：若未来要声明 `gameplay-verified`，必须为特定游戏建立可审查的操作协议，记录明确控件、动作、状态变化和胜负证据；不能用通用点击、动画变化或 iframe 存在代替实际试玩。公开源码和资源只可在许可与访问边界内分析，不绕过登录、付费、验证或其他访问控制。
