# 产品需求与工作流

## 1. 当前判断

需求类型：想法驱动，已经进入范围塑形与执行交接阶段。

价值判断：**TEST**。长期方向已经明确为开放式 2D/3D 游戏创作平台；仍需用分阶段黄金游戏验证成功率、单位成本和扩展能力。阶段验证决定能力何时公开，不把平台重新缩成三消或固定模板产品。

## 2. 需求简报

### 背景

现有 AI 游戏生成产品已经证明用户愿意用自然语言表达创意，但行业常见问题仍是规则被误解、等待过程不透明、修改破坏旧功能、生成结果只能演示不能稳定玩。

### 目标用户

第一用户：

- 有游戏点子但不会写代码的中文创作者。
- 需要快速制作互动内容的教师和内容创作者。
- 希望验证轻量玩法的独立开发者。

首版不服务大型工作室完整生产管线。

### 核心问题

用户能描述想要的体验，却不知道如何把它变成：

- 可执行的玩法规则。
- 可复现的项目结构。
- 可验证的完成标准。
- 能持续修改而不崩坏的版本。
- 可在手机和电脑直接分享的游戏。

### 预期价值

用户无需理解游戏引擎，也能在一次会话中得到适合当前目标的第一版可玩游戏，并能看到它为何被判断为“可玩”。浏览器是最先交付的目标，后续可扩展到 3D 和专业引擎工程。

### 成功信号

- 70% 以上的受测用户能在首次会话进入可玩预览。
- 首次可玩预览中位时间不超过 8 分钟。
- 至少 60% 的首次预览通过基础冒烟和核心规则测试。
- 用户提出一次局部修改后，至少 80% 的既有验收项保持通过。
- 每个成功版本的成本和失败原因都能被追踪。

这些是首轮目标，不是已验证的行业基准。

## 3. 产品承诺

> 说玩法，不用说技术。第一版必须能玩，修改必须有证据，失败必须能回退。

用户得到的不是一段代码，而是：

- 一份可编辑的玩法合同。
- 一条可理解的制作时间线。
- 一个可直接试玩的版本。
- 一份逐项测试结果。
- 一条可继续修改或回退的版本线。
- 一个属于这款游戏、可直接分享的稳定 HTTPS 网址。
- 按玩法启用的存档、排行榜、分析或多人服务器能力。

## 4. 设计原则

1. **核心冲突先于素材**：先回答玩家反复做什么、对抗什么、何时结束。
2. **硬约束不被默认值覆盖**：用户说过的控制权、胜负和平台要求进入合同。
3. **只问影响实现的歧义**：最多三个关键问题，不做长问卷。
4. **平台负责重复工程**：输入、缩放、音频、生命周期、存档和测试不让模型每次重写。
5. **生成声明不算证据**：只有构建、规则探针和真实浏览器流程通过才算完成。
6. **修改永远形成新版本**：草稿失败不能破坏已发布版本。
7. **展示动作和结果，不展示思维链**：公开计划、工具动作、产物、错误和理由。
8. **愿景开放、能力分级**：产品不限制游戏类型；每项 2D、3D、网络或引擎能力必须通过对应黄金游戏后再对外标为可用。
9. **交付必须能离开工作台**：预览通过不等于发布完成；玩家网址、资源托管、数据权限、监控和回滚都必须就绪。

## 5. 端到端工作流

~~~mermaid
flowchart LR
    A[用户描述游戏] --> B[抽取硬约束与歧义]
    B --> C[最多 3 个关键澄清]
    C --> D[玩法合同与验收清单]
    D --> E[能力分类与运行时适配器选择]
    E --> F[生成玩法逻辑与场景]
    F --> G[规则单元测试]
    G -->|失败| H[限次修复]
    H --> G
    G -->|通过| I[生成资产计划与风格锚点]
    I --> J[生成并集成资源]
    J --> K[隔离构建]
    K --> L[真实浏览器试玩]
    L -->|失败| M[诊断与限次修复]
    M --> K
    L -->|通过| N[可玩版本]
    N --> O[自然语言修改]
    O --> P[变化合同与影响分析]
    P --> F
    N --> Q[部署不可变版本]
    Q --> R[切换稳定游戏网址]
~~~

### 为什么先验证规则再生成正式素材

MakePlay 的公开流程强调先定设计和资源方向，再实现并测试；这点应该保留。但我们进一步加入“程序化占位版本”，先验证核心循环，避免在错误玩法上浪费图片、音乐和等待时间。

顺序因此是：

1. 定玩法与视听方向。
2. 用稳定骨架和占位资源完成 P0。
3. 通过规则测试。
4. 生成正式资源。
5. 集成后做全量浏览器试玩。

## 6. 玩法合同

玩法合同是用户、编排器、代码生成器和测试器共同使用的公开协议。

~~~json
{
  "title": "星梦对决",
  "promise": "玩家和 AI 在同一棋盘上轮流三消，用连消攻击对手",
  "dimensions": "2d",
  "runtimeTarget": "web-2d",
  "archetype": "grid_logic",
  "coreLoop": [
    "观察共享棋盘",

    "结算本次行动引发的全部连消",
    "扣除对手积分",

  },
  "hardConstraints": [

    "AI 只能操作上半区",
    "共享重力和跨区匹配",

  ],
  "endCondition": "任一方积分归零",

    "在线多人",
~~~

这是第一款黄金游戏的合同，不是通用合同的类型上限。通用规格还必须容纳 3D 场景、相机、物理、实体、世界结构和不同交付目标，详见[产品愿景与能力边界](./00-product-vision.md)。

## 7. 用户控制

### 构建前

- 接受系统推荐。
- 修改玩法合同。
- 查看明确不做的内容。
- 查看预计时间和额度区间。

### 构建中

- **排队补充**：当前阶段完成后合并。
- **立即纠偏**：安全停止当前阶段，保留已成功产物，重新规划下游。
- **暂停**：不再启动新步骤，运行中的原子任务收尾。
- **取消本次版本**：回到上一个成功版本。

### 构建后

- 试玩。
- 查看逐项验收和证据。
- 用自然语言修改。
- 查看文件和资源变化。
- 命名版本、比较、回滚或发布。
- 查看玩家网址、版本网址、访问状态和服务端数据用量。

## 8. 平台范围与交付切片

平台范围包括开放式玩法、2D/3D、多运行时和后续多人能力。下面的 P0—P3 是交付顺序，不是产品类型边界。

### P0

- 中文想法输入和一张参考图。
- 关键澄清与玩法合同。
- 通用游戏规格、能力分类和运行时适配器协议。
- `web-2d-phaser` 运行时壳；首个实现使用 grid_logic 能力包。
- 纯 TypeScript 规则核心。
- 代码和程序化占位资源生成。
- 实时构建事件。
- 隔离预览。
- 单元测试、结构检查和 Playwright 试玩。
- 限次自动修复。
- 不可变版本、回滚和网页发布。
- 平台服务器、PostgreSQL、对象存储、CDN 和独立游戏网址。

### P1

- shooter、top_down 等非棋盘能力包，证明平台不是三消换皮。
- 游戏数据 API：匿名玩家标识、云存档和休闲排行榜的受控接口。
- 正式图片和音频生成。
- 风格锚点、资源局部重生成和替换。
- 只读源码与版本差异。
- PWA 下载包。
- 分享卡、基础访问统计和异步排行榜。

### P2

- `web-3d` 运行时适配器与第一个 3D 黄金游戏。
- 3D 场景、相机、角色控制器、物理和资产性能预算。
- 2D/3D 共用的版本、证据和发布流程。

### P3

- Godot、GDevelop 或 Unity 等工程适配器。
- 多人、完整场景编辑器和运行时能力包 SDK。
- 社区、重混、评论、创作者主页和收益。
- 团队协作、品牌工作区和素材市场。

### 明确不做

- 无限制安装依赖。
- 生成代码直接访问外网、主站 Cookie 或用户令牌。
- 一次生成商业成品的宣传。
- 自动无限重试。
- 把模型思维链当作透明度功能。

## 9. 需要通过样条验证的问题

1. 用户是否愿意确认玩法合同，还是更偏好直接采用推荐值？
2. 受控骨架能否在提高成功率的同时避免“只是换皮模板”的感觉？
3. 测试结果、截图和回放中，哪种证据最能增加普通用户信任？
4. 第一次可玩和第一次满意之间平均需要多少轮？
5. 每个成功版本的模型、资产、构建和试玩成本分别是多少？
