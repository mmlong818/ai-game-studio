# 二次规划：产品定义与边界

## 1. 正式定位

产品名称暂定为 **AI 单人网页小游戏制作平台**。

一句话定义：

> 用户用自然语言说明想做的游戏，平台把创意转成可检查的游戏设计与规则合同，生成可独立运行的网页小游戏，并通过自动测试、真实试玩、人工复核和版本发布形成可交付作品。

平台的核心价值不是“快速生成一个看起来像游戏的页面”，而是降低从创意到可靠可玩版本之间的设计、实现和验收门槛。

## 2. 目标用户

### 主要用户

- 没有完整编程能力，但能描述玩法目标的独立创作者。
- 需要快速验证玩法原型的游戏策划、产品经理和视觉创作者。
- 希望制作活动小游戏、品牌互动小游戏或个人作品的内容团队。
- 需要以浏览器网址分享作品的教师、学生和社区创作者。

### 用户的核心任务

1. 用一句话或一段话说明玩家做什么、如何成功、希望有什么感觉。
2. 在生成前确认平台理解的玩法和限制。
3. 试玩真实版本并用普通语言提出修改。
4. 看到每项修改是否落实，以及哪些规则仍未验证。
5. 获得一个稳定网址和一份包含全部资源的可移植交付包。

## 3. 当前支持范围

### 游戏范围

- 单人游戏。
- 浏览器直接运行，不要求安装客户端。
- 2D Canvas、DOM/UI 密集玩法，以及有限场景 Web 3D。
- 单局约 30 秒至 30 分钟；更长体验必须支持恢复。
- 键盘、鼠标/触控板和手机触控中的至少两种完整输入路径。
- 有明确核心循环，并能定义完成、失败、阶段结束或持续挑战状态。

### 优先支持品类

| 能力组 | 典型玩法 | 当前策略 |
| --- | --- | --- |
| 棋盘与逻辑 | 俄罗斯方块、2048、华容道、区域逻辑 | 成熟模板优先，强调确定性与可解性 |
| 直接操作解谜 | 拼图、拼块、拖放整理 | 成熟模板优先，强调触控和空间可读性 |
| 即时动作与街机 | 射击、打砖块、贪吃蛇、高速闪避 | 模板与 AI 原创并行，强调手感、碰撞和公平窗口 |
| 轻量旅程与构筑 | 肉鸽麻将、短局卡牌、路线选择 | 受控扩展，强调存档、种子和资源取舍 |
| 轻量经营与模拟 | 单屏经营、时间管理、订单循环 | P1 能力，需要资源和队列规则合同 |
| 互动叙事 | 短篇分支、探索对话、结局收集 | P1 能力，需要章节和选择后果合同 |
| 有限场景 3D | 收集、撤离、小型竞技场、空间解谜 | 实验支持，按性能和相机能力放行 |

## 4. 明确不在当前承诺中的内容

以下需求可以记录为未来方向，但当前不能被包装成已经完整支持：

- 实时多人、房间匹配、断线重连和反作弊。
- MMO、开放世界和持续在线世界。
- 大型 3D 骨骼动画、复杂载具和高精度物理模拟。
- 原生 iOS、Android、主机或桌面商店包。
- 用户自定义脚本插件、UGC 市场和多人协作编辑。
- 付费、广告、抽卡、真实货币经济和运营活动系统。
- 需要可信服务端裁决的竞技排行榜。

遇到超出边界的创意时，系统必须给出三种明确结论之一：

1. **完整支持**：已有成熟运行时与专属测试。
2. **实验支持**：能生成，但需要专属规则探针和真人试玩后才能发布。
3. **暂不支持**：关键能力缺失，停止构建并说明原因，不生成伪成品。

## 5. 产品支柱

### 5.1 规则可信

- 用户说过的胜负、操作和限制进入带 ID 的规则合同。
- 规则不是只写在说明文档里，必须能映射到状态、动作和断言。
- 修改后重新验证受影响规则，同时保留未受影响的证据。

### 5.2 真正可玩

- 自动验收必须执行真实合法动作。
- 强制胜负只能用于验证结算页面，不能证明游戏可通关。
- 随机和程序生成游戏必须验证公平性、可达性或可解性。

### 5.3 体验完整

- 目标、输入、反馈、失败原因、重试和进度恢复形成闭环。
- 视觉、声音和动效服务规则判断，而不是只做装饰。
- 桌面和手机都能完成核心循环，手机控件不遮挡关键游戏区域。

### 5.4 证据透明

- 每个版本保留规则测试、浏览器路径、截图、错误、性能和人工复核。
- 设计、代码、资源和验收报告通过哈希绑定，旧报告不能复用到新代码。
- 不能验证的项目显示为待确认或失败，不允许自动标绿。

### 5.5 可持续扩展

- 新品类通过能力包、运行时适配器和黄金游戏加入。
- 不把所有创意偷偷映射成少数模板。
- 不让一条无限增长的提示词承担所有游戏类型。

### 5.6 有依据地改造

- 现有模板默认提供换世界观、换视觉风格、换角色与内容、调节节奏和增加一种小机制等固定建议。
- 用户提出跨类型或大幅改规则的需求时，先判断是否已经改变模板核心，不直接把所有要求塞进原运行时。
- 新建游戏先从现有能力库寻找可复用机制，再研究 2–4 个真实同类游戏的规则、输入、节奏和失败恢复。
- 研究只吸收设计方法和经过许可的代码结构，不复制品牌、角色、美术、音乐、文案或受保护的界面识别。

### 5.7 创作与验证闭环

- AI 生成的角色、场景、特效和界面位图必须直接进入项目资源库，绑定实际使用位置并记录来源，不能停留在下载后再手工导入。
- 用户应能从画面选中对象，在层级和属性中看懂它的名称、作用、位置、尺寸、碰撞、层级和动画，而不需要阅读代码。
- 每次 AI 修改都生成独立变更集，自动构建桌面与手机预览，并重新检查受影响的规则、资源和画面。
- 平台只在当前预览构建和对应证据都完成后显示“修改完成”；构建失败、资源缺失或证据过期时必须保留失败状态。
- 预览、正式发布和开源交付包使用同一份不可变构建，避免工作台内看见的版本与玩家实际拿到的版本不一致。

## 6. 产品成功指标

### 生成质量

- 支持范围内首次构建通过率达到 70% 以上。
- 一次自动修复后的通过率达到 90% 以上。
- P0 规则必须 100% 有证据，不接受跳过。
- 局部修改后，未受影响验收项保持通过的比例达到 95% 以上。

### 玩家体验

- 发布版本的核心循环完成率达到 95% 以上。
- 手机端不存在阻塞操作的遮挡、横向溢出或小于 44px 的主要触控目标。
- 失败页面能说明失败原因和下一次可尝试的策略。
- 参考设备上首屏可交互时间和运行帧率满足交付预算。

### 用户价值

- 用户可以在不阅读代码的情况下确认玩法合同和验收结果。
- 从确认合同到首个可玩版本的时间可观测、可解释。
- 每个发布作品都能脱离工作台独立运行和打包迁移。
- 用户不写代码也能选中游戏对象，完成受控的资源替换和安全属性调整。
- 每次 AI 修改都有可打开的桌面/手机预览、影响说明和当前验收结论。
- AI 位图从生成、加工、绑定到打包全程可追溯，正式构建不存在远程资源依赖。

## 7. 关键产品决定

1. 产品名称和对外说明统一使用“AI 单人网页小游戏制作平台”。
2. “所有游戏”是长期扩展方向，不是当前能力承诺。
3. 成熟模板负责高成功率，AI 原创通道负责探索新玩法，两者使用不同放行标准。
4. 不再把固定 20 关作为全部游戏的共同前提。
5. 发布质量由规则正确、真实可玩、体验完整和资源合规共同决定。
6. 模板小改复用已有参考档案；核心规则变化、跨品类组合和 AI 原创新游戏必须经过同类玩法研究。
7. 吸收成熟游戏 IDE 的资产、场景和预览闭环，但不把代码编辑器、引擎目录和构建参数暴露给普通用户。
