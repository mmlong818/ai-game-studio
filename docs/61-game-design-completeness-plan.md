# 游戏设计完整性方案

> 状态：实施中；D0 合同与校验、D1 普通项目持久化、D2 十三类成熟/通用 2D 模板、三类 3D 模式、AI 自由生成及两款样板的可执行教学已完成；八类非实时模板已接入变化情境复验，十二类成熟 2D 模板已接入难度与失败辅助运行时门禁，D5 确认页摘要已接入
> 重点缺口：新手帮助、机制教学、难度递进、失败恢复、内容节奏和可执行验收。

## 1. 根因

游戏设计系统必须把用户的一句话创意补全成可玩的设计，而不是把专业策划表格交还给用户填写。平台应提供有依据的默认核心循环、教学、节奏、难度、失败恢复与复玩目标；工作台只展示普通人能判断的结果与关键取舍，高级设计参数按需展开。

`GameDesignContractV1` 是单个项目的设计结果，不是策划知识本身。其上游由 [游戏设计知识系统](63-game-design-knowledge-system.md) 提供通用能力、机制关系、玩法模式、参考证据和持续评分；策划整合器先检索与组合知识，再生成合同，避免每次从空白上下文临场设计。

现有 `designProfile.onboarding`、`progression` 和 `difficultyCurve` 已表达设计意图，但多数仍是模板文案；`GameProjectV3` 只描述场景、对象、行为、规则、变量、资源和基础验收，没有完整表达：

- 玩家何时、通过什么动作学会哪条规则。
- 教学是否验证玩家真的完成过目标动作。
- 难度由哪些独立维度构成，何时引入、练习、组合和考核。
- 连续失败后给什么提示、辅助或检查点。
- 有限关卡、无尽、回合和章节应采用怎样不同的节奏。
- 设计目标如何变成运行时统计和发布门禁。

下一版不再只生成“新手引导文案”和三个倍率，而是生成可执行的 `GameDesignContractV1`。

## 2. 设计合同

```ts
interface GameDesignContractV1 {
  playerPromise: string;
  audience: { experience: "first-time" | "casual" | "experienced"; accessibilityNeeds: string[] };
  session: { targetMinutes: number; restartSeconds: number; firstMeaningfulChoiceSeconds: number };
  loops: { instant: LoopSpec; tactical: LoopSpec; session: LoopSpec; longTerm?: LoopSpec };
  mechanics: MechanicLearningSpec[];
  onboarding: OnboardingStep[];
  difficulty: DifficultyPlan;
  assistance: AssistancePolicy;
  failureRecovery: FailureRecoveryPolicy;
  replay: ReplayPlan;
  contentPlan: LevelBeat[] | EndlessPhase[] | ChapterBeat[] | RoundBeat[];
  metrics: DesignMetric[];
  acceptance: DesignAcceptance[];
}
```

它是设计真相来源，GameProjectV3 负责实现。两者通过稳定的 mechanic、rule、scene、level 和 acceptance ID 关联。设计合同不能塞进自由文本字段，也不能把所有游戏强制成二十关。

## 3. 新手帮助设计

每条核心机制使用统一学习循环：

```text
说明目标 → 聚焦相关对象 → 安全尝试 → 检测正确动作 → 给出反馈 → 移除提示 → 在变化情境复验
```

### 3.1 OnboardingStep

每一步至少包含：

- `teachesMechanicId`：本步只教学一个主要概念。
- `trigger`：首次进入、首次遇到对象、连续失败或停滞触发。
- `presentation`：短文案、目标高亮、手势、幽灵动作或可选演示。
- `safeState`：教学时暂停哪些威胁，保留哪些真实规则。
- `requiredAction`：玩家必须真实完成的动作，不能只点击“知道了”。
- `successSignal`：哪个运行事件证明已经学会。
- `dismissal`：完成后渐隐，可重看，可跳过。
- `deviceVariants`：键盘、指针、触控分别显示正确方式。

### 3.2 教学原则

- 首次可操作前只说明目标和一个主要动作，不展示整页说明书。
- 教学必须发生在真实玩法中，但首个尝试降低失败压力。
- 已经通过操作证明会用的玩家不重复弹窗。
- 提示不遮挡目标、玩家、危险和主要触控区。
- 所有教程可重看；跳过后仍可通过暂停菜单找到帮助。
- 无文字也能通过高亮、运动、图标和声音理解关键反馈；文字用于解释原因。

### 3.3 最小新手流程

1. 进入即显示一句话目标。
2. 第一个交互对象出现在安全、清晰的位置。
3. 提示一个动作并等待玩家真实执行。
4. 立即显示动作结果和目标进度。
5. 第二次在略有变化的情境中不显示完整提示。
6. 玩家成功后才引入危险、计时或资源压力。

## 4. 难度递进设计

难度不能只用 `speedMultiplier`、`densityMultiplier` 和 `goalMultiplier` 同时上涨。每款游戏先声明独立难度维度：

- 认知：信息量、隐藏信息、规划深度、相似干扰、记忆负荷。
- 操作：速度、精度、同时输入、反应窗口、镜头控制。
- 空间：场地大小、障碍密度、路线数量、可用空间。
- 资源：生命、时间、撤销、提示、弹药、经济和恢复机会。
- 组合：同时活跃的机制数量、敌人/机关协同关系。
- 惩罚：失败损失、检查点距离、重新尝试成本。

每个维度取 0–5 档，并声明安全范围、变化原因和对应验收。首次引入机制时，只允许一个主要维度上升；不得在同一节点同时增加新规则、速度和惩罚。

## 5. 机制课程与节奏

每个机制经历五个阶段：

1. **介绍**：无压力看见并完成一次。
2. **练习**：相同规则、不同题面，建立稳定操作。
3. **变化**：改变空间、资源或目标，迫使玩家理解而非照抄。
4. **组合**：与已经掌握的机制共同出现。
5. **掌握**：以技巧目标或可选挑战验证，不阻塞首次通关。

有限战役可使用既有 1–4、5–8、9–12、13–16、17–20 五阶段，但实际关数由内容计划决定；短战役可压缩为 5–8 关，无尽模式改用时间阶段，章节/回合模式按叙事或系统节点推进。

`LevelBeat` 至少记录：教学机制、复习机制、场景变化、难度向量、资源预算、目标、失败条件、技巧目标、提示、预期时长和前置掌握证明。

## 6. 失败辅助与防挫

失败后必须回答：发生了什么、为什么、下一次可改变什么。

`AssistancePolicy` 按强度递进：

1. 第一次失败：只解释原因。
2. 同原因连续失败：突出相关规则或危险预警。
3. 多次失败或长时间停滞：提供方向性提示。
4. 玩家主动请求：展示一步建议、幽灵演示、检查点或临时辅助。
5. 仍无法完成：允许降低单一难度维度，但明确标记，不偷偷改变规则。

辅助使用不能羞辱玩家；首次通关与技巧评价分离。无尽游戏在结束后给出局内复盘，长局必须有检查点或状态恢复，短局重试应在目标时间内完成。

## 7. 动态难度边界

首版不做隐藏式动态难度。系统只做：

- 创建时可选轻松、标准、挑战。
- 游戏内可显式调整辅助项。
- 根据匿名聚合数据提出设计修订，不在玩家背后修改敌人命中、掉落或胜负规则。
- 自动检测难度断崖并阻止发布，但调参结果仍由设计者确认。

后续若引入自适应，必须可解释、可关闭，并保持同一种子和难度设置可复现。

## 8. 设计验收

新增验收类型：`onboarding`、`progression`、`solvability`、`assistance`、`content-variation`。

自动检查至少包括：

- 新玩家路径无需预存档即可完成首次教学。
- 每个教学步骤都能收到 `successSignal`，且提示完成后消失。
- 键盘和触控展示不同但等价的操作说明。
- 新机制在第一次高压力使用前至少有一次安全成功。
- 相邻内容的难度向量没有未经说明的多维跳升。
- 关卡不是只改三个数值；每个阶段包含结构变化或机制变化。
- 提示、检查点、撤销和重试真实可用并正确计数。
- 随机/程序生成内容通过批量种子可达性、公平性或可解性检查。

人工检查至少包括：30 秒能否理解目标、提示是否打断、失败是否公平、是否出现有意义选择、是否愿意立即重试。

## 9. 工作台设计

默认创作体验为三步：`描述想法 → 确认一页游戏提案 → 试玩完整首版`。确认页允许用户用自然语言修改，不要求逐字段填写。系统只在目标玩家、核心规则或题材安全边界存在互相冲突且会显著改变作品时提问；其余缺省项由设计合同自动补齐并说明采用了什么假设。

设计确认页新增四张卡，不向普通用户暴露全部内部字段：

- **玩家先学什么**：展示前 60 秒教学顺序和可跳过策略。
- **如何逐步变难**：展示机制引入与主要难度维度，不只显示“轻松/标准/困难”。
- **失败时如何帮助**：展示提示、撤销、检查点和降难度边界。
- **内容如何保持变化**：展示关卡/阶段的结构变化和复玩目标。

制作工作台把设计项与资源缺口关联。例如某关首次引入护盾敌人时，自动要求护盾正常、受击、破裂三种视觉状态和对应音效。

## 10. 实施切片

1. D0：新增 `GameDesignContractV1` Schema、ID 引用校验和设计缺口报告。
2. D1：把现有 `designProfile` 迁移为合同草稿，模板文案仅作为默认输入。
3. D2：实现 `OnboardingStep` 运行时和探针，先接入 2048 与虫虫攀枝。
4. D3：实现难度维度、机制课程和内容节奏校验，替代通用三倍率作为唯一依据。
5. D4：实现失败原因、分层提示、帮助重看和显式辅助。
6. D5：工作台展示教学、难度、辅助和内容变化，并生成资源槽位。
7. D6：将设计验收接入不可变构建和发布门禁。

## 11. 完成标准

- 任一新游戏在构建前都有可检查的前 60 秒新手流程。
- 核心机制都有介绍、练习、变化、组合或明确排除理由。
- 难度变化能解释“哪一维、为什么、如何验证”，不再只是笼统加速加量。
- 连续失败时系统能提供与真实失败原因匹配的帮助。
- 设计合同可以确定性生成资源需求和验收项。
- 删除教学步骤、制造难度断崖或缺少失败恢复时，发布稳定失败。

## 12. 2026-09-05 实施结果

- 已建立 `src/shared/game-design-contract/` 和 `GameDesignContractV1`，覆盖玩家承诺、目标用户、会话预算、三层循环、机制课程、可执行教学、六维难度、内容阶段、失败辅助与设计验收。
- 已实现跨 GameProjectV3 的稳定引用检查，并能报告：悬空规则、未教学核心机制、缺少介绍阶段、无设备提示、首次高压引入、相邻多维难度突刺、失败辅助顺序错误和验收引用错误。
- GameProjectV3 与平台验收类型已加入 `onboarding/progression/solvability/assistance/content-variation`。
- 已建立 2048 与虫虫攀枝两份可执行样板合同，验证安全教学、真实动作完成信号、难度节奏和分层失败辅助。
- 已实现通用教学计划与状态归约器，支持开始、真实成功信号、错误信号拒绝、跳过、重看、完成状态恢复和未知步骤过滤。
- 2048 已接入首个运行时纵向切片：首局使用低压力练习局面；错误方向不推进；真实右滑和左滑合并分别产生 `board-slid`、`equal-merged-once`；完成状态持久化，玩家可重看或跳过。
- 2048 教学计划写入 `_studio/ONBOARDING_PLAN.json`，真实浏览器证据写入 `_studio/ONBOARDING_QUALITY_REPORT.json`，并作为不可变构建的额外发布门禁。
- 虫虫攀枝已接入第二个运行时纵向切片：随机生成在教学期暂停，换道避障、头部吸收露珠和按住冲刺破树脂均使用既有真实碰撞结果；错误纵向输入不启动压力，未冲刺撞树脂会安全重试而非惩罚。
- 两个样板现在都支持完成状态恢复、跳过和重看；虫虫固定版本同样归档 `ONBOARDING_PLAN.json` 与真实浏览器证据，并由合同一致性和固定版本静态门禁检查。
- 十二类成熟 2D 模板均从项目设计合同生成并归档教学计划；落块旋转、拼图拖拽、挡板移动、移块、走格、转向、滑动合并、移动后射击、拼块放置、候选排除与配对等动作都只在真实玩法成功时发出对应信号。
- 试玩静态门禁会逐步核对合同要求的每个 `successSignal` 是否存在于运行时；落块、挡板和贪吃蛇另有真实键盘浏览器验证，覆盖完成、刷新恢复、重看和跳过。
- 修复了教学卡片隐藏时仍拦截开始按钮的样式缺陷；二十关、阶段 D/E 多局与迷宫路线回归验收均恢复通过。
- `signal-hunt` 已登记为知识库中的“限时目标捕获”已验证模式，不再被固定三消游戏共用的服务器通道错误映射；其合同使用 `target-acquisition` 与 `target-collected` 真实成功信号。
- `signal-hunt` 首次捕获前暂停倒计时，真实点击后恢复时间压力；落块、打砖块、贪吃蛇和太空射击也会在首次教学动作前冻结自动掉落、发球、移动或敌人生成。
- 四类实时模板和通用信号捕获均有真实浏览器安全等待证据；深度玩法验收会显式跳过已独立验证的教学，再检查弹幕、聚光、碰撞、模式与二十关流程。
- 3D 知识映射已按最终模式区分第三人称收集、竞技场射击和立体书旋转迷宫；项目创建先完成模式推断，再持久化对应策划知识和教学合同，避免竞技场误拿收集合同。
- Three.js 收集与竞技场分别以真实 `player-moved`、`shot-fired` 完成教学；PlayCanvas 立体书按真实 `cell-entered`、`world-rotated` 两步完成。教学期间冻结计时、敌人或自动节拍压力，完成后恢复正常玩法。
- 三类 3D 模式均把教学计划写入不可变产物，支持完成状态恢复、重看和跳过；静态探针、真实浏览器教学证据、手机/桌面深层试玩及立体书 20 关求解回归均已覆盖。
- AI 自由生成通道现在向模型提供完整 `GameDesignContractV1` 与逐字确定的教学信号，不再只提供旧设计摘要；平台在生成代码之前注入统一教学控制器和非技术教学浮层。
- 自由生成代码必须在正常玩法处理器成功后调用每个合同信号，并在教学活跃时冻结自动计时、敌人推进或生成压力；缺少信号、安全暂停、`pressureClock` 或真实动作探针都会在静态/浏览器门禁中拒收并把具体原因反馈给模型重做。
- 2D 与本地 Three.js 3D 自由生成产物均已通过真实浏览器的安全等待、动作完成、刷新恢复、重看、跳过和完整胜负重开状态环；构建集成测试证明错误首稿不能发布，第二轮修正后才可完成不可变构建。
- 2048、华容道、迷宫、拼图、方块放置、多格拼块、区域逻辑和麻将肉鸽现在会在第 9 关复验首关教学过的核心机制；关卡阶段、目标倍率和密度已发生变化，复验仍必须通过原有真实玩法处理器产生合同信号。
- 普通构建已接入 `CONTENT-VARIATION-REHEARSAL` 门禁并归档 `_studio/VARIATION_QUALITY_REPORT.json`；只在首关教学脚本中成立、后续变化关失效的作品不能进入稳定版本。
- 十三类成熟 2D 模板（含通用信号捕获）会实际采样全部 20 关：逐关检查目标、速度和密度倍率不倒退且没有突跳，并在第 1、5、9、13、17 关比较模板专属运行结构；五阶段只改通用倍率、没有真实结构变化时构建失败。
- 难度证据归档为 `_studio/DIFFICULTY_QUALITY_REPORT.json`，并以 `PROGRESSION-RUNTIME` 进入不可变构建验收。
- 十三类成熟 2D 模板已实现统一连续失败辅助：第 1 次解释本次真实失败原因，第 2 次突出相关规则，第 4 次提供方向提示；帮助明确展示、不暗中调难度，刷新后保留，成功后清零。
- 失败辅助合同、状态和浏览器证据分别归档为 `_studio/ASSISTANCE_PLAN.json` 与 `_studio/ASSISTANCE_QUALITY_REPORT.json`，并以 `ASSISTANCE-RUNTIME` 进入不可变构建验收。
- 普通实际项目创建时现在会根据知识库匹配结果编排完整 `GameDesignContractV1`，与项目 UUID 绑定并写入版本规格；成熟模板引用已验证玩法，库外实验玩法明确保留研究任务，不伪装为已匹配。
- 构建和重新构建会重新校验合同并归档 `_studio/GAME_DESIGN_CONTRACT.json`；试玩探针把该文件纳入专业设计文档门禁，避免后续版本静默丢失合同。
