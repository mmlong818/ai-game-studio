# 3D 收集闯关最佳模板：参照、边界与重构合同

更新时间：2026-08-30

## 1. 目标

把现有“平地上捡齐若干碎片、碰一次检查点、走到门口”的 Web 3D 演示，改造成可以复用的短关卡模板：玩家无需掌握复杂镜头也能到达终点；愿意探索的玩家可以通过隐藏收集、路线风险和时间评价获得更高完成度。

本模板不是复刻任一商业游戏，也不使用其美术、角色、关卡或代码。参照只用于确定可验证的玩法结构、控制职责和工程边界。

## 2. 可追溯参照

### 2.1 Super Mario 3D World：主线终点、检查点与进阶收集分层

任天堂官方手册把普通关卡明确拆成检查点和终点：触发检查点后，失败可从该处继续；抵达终点才完成关卡。手册同时把坠落、危险和时间耗尽列为失败来源。官方访谈进一步说明，固定方向和距离的镜头用于降低迷路风险；抵达终点是所有玩家的主目标，隐藏收集承担进阶挑战。

来源：

- [Super Mario 3D World 官方手册](https://csassets.nintendo.com/noaext/image/private/t_KA_PDF/manual-WiiU-Super_Mario_3D-World)
- [Iwata Asks：Super Mario 3D World 的镜头与进阶收集](https://www.nintendo.com/en-gb/Iwata-Asks/Iwata-Asks-Super-Mario-3D-World/Super-Mario-3D-World/3-An-Instinctively-Good-Feeling-/3-An-Instinctively-Good-Feeling--829583.html)

采用：

- 终点是通关条件；每关的三枚星砂是评价与探索目标，不再强迫新手全部收集。
- 至少一个中途检查点；坠落或触碰危险时从最近检查点恢复，而不是整局立刻结束。
- 默认镜头自动保持方向、距离和前视空间；镜头操作只能提供额外观察，不能成为通关前提。

不采用：

- 生命数、角色能力、绿星、旗杆、具体动作和任天堂关卡内容。
- 把“商业作品存在的做法”直接当作本项目数值结论；移动、跳跃、镜头弹性仍以本模板实测为准。

### 2.2 Godot 官方 3D Platformer Demo：角色控制必须是独立系统

Godot 官方资产库的 3D Platformer Demo 使用 KinematicBody，并明确把角色运动作为 3D 平台玩法的核心实现；示例为 MIT 许可。

来源：[Godot 3D Platformer Demo](https://godotengine.org/asset-library/asset/125)

采用：

- 输入、角色速度、重力、落地、跳跃、碰撞和恢复组成独立的角色控制层，不把视觉精灵位置直接当作全部规则。
- 渲染循环只消费稳定的角色状态；关卡和碰撞数据不能散落在装饰网格中。

不采用：

- 不移植 GDScript 或 Godot 场景；平台运行时仍是本地 Three.js。

### 2.3 Three.js 官方 Octree 示例与 Rapier 文档：胶囊碰撞和 move-and-slide 是正确边界

Three.js 官方 Octree 文档和 FPS 示例使用世界空间结构配合胶囊体处理静态场景碰撞。Rapier 官方角色控制器文档说明，成熟的运动修正要覆盖障碍停止、斜面滑动、台阶、贴地和移动平台，并建议角色使用胶囊、球或长方体等稳定形状。

来源：

- [Three.js Octree 文档](https://threejs.org/docs/pages/Octree.html)
- [Three.js 官方 Octree 游戏示例](https://threejs.org/examples/games_fps.html)
- [Rapier JavaScript Character Controller](https://rapier.rs/docs/user_guides/javascript/character_controller/)

采用：

- 当前版本先用单一胶囊近似和明确的台面/障碍碰撞数据实现可测试的 move-and-slide、落地和坠落恢复。
- 关卡生成同时产生可见网格与碰撞描述，避免“看得见却能穿过”或“看不见却被挡住”。
- 记录未来接入 Rapier 的接口边界，但本轮不新增依赖，也不声称已经使用 Rapier。

### 2.4 Open Runner：Web 3D 的移动端、性能和玩法配置分层

Open Runner 是 MIT 许可的 Three.js 开源跑酷项目，公开描述了移动端控制、自适应性能、收集物、障碍、道具，以及按关卡配置拆分实体、物理、渲染和管理器的结构。

来源：[Open Runner](https://github.com/CollinEMac/open-runner)

采用：

- 手机控制和性能档不是附加项，而是模板合同的一部分。
- 关卡由数据蓝图驱动；收集物、危险、检查点、移动平台和出口使用角色明确的实体配置。

不采用：

- 不复制无限跑酷、自动前进、磁铁、敌人或其代码；它不等于本模板的短关卡结构。

## 3. 当前实现审计

现有版本具备 Three.js、本地资源、第三人称相机、键盘与触控、检查点、出口、20 关 UI、性能分档、暂停和发布证据，但仍不是成熟收集闯关：

- 20 关共用同一张平地和同一组坐标，只改变碎片数量与倒计时。
- 跳跃只改变角色精灵高度，障碍碰撞不读取高度，实际不能越过低障碍。
- 检查点固定在起终点直线上，几乎不构成路线或恢复价值。
- 没有平台高度、沟壑、危险、坠落、复位、移动平台、支路和隐藏收集。
- 世界轴移动与镜头没有形成明确关系；没有加速、减速、跳跃缓冲或离台宽容。
- 全部碎片是硬通关条件，主线路径和探索评价没有分层。
- 自动验收主要依靠调试接口直接收集和瞬移，不能证明角色真实走、跳、落地、触发检查点与复位。

## 4. 最佳模板合同

### 4.1 单关闭环

每关必须真实完成：

1. 从起点进入可读主路线；
2. 至少完成一次移动或跳跃判断；
3. 激活中途检查点；
4. 抵达终点完成关卡；
5. 三枚星砂用于一至三星评价，其中至少一枚位于可选支路或风险位置。

终点不再要求三枚星砂全部收集。二星、三星分别由收集和剩余时间等可测条件决定。

### 4.2 角色与镜头

- 固定步长更新角色规则，渲染使用插值；慢帧不能增加移动距离或穿透风险。
- 水平移动采用加速和减速，不瞬间满速；斜向输入归一化。
- 低障碍可以真实跳过；角色落在台面上才恢复跳跃。
- 提供短时跳跃缓冲和离台宽容，具体时长由真实试玩验证，不把行业常见数字当作事实。
- 移动方向以镜头平面方向为参照；默认镜头自动保持可读距离和前视空间。
- 手机使用左侧虚拟摇杆和右侧独立跳跃键；按钮不覆盖角色、检查点、出口和主要落点。

### 4.3 失败与恢复

- 坠落、危险接触或时间耗尽是不同失败来源。
- 坠落与普通危险扣除一次容错并从最近检查点恢复；恢复过程有短暂无敌和明确视听反馈。
- 时间耗尽才结束本局；终章可提高危险密度，但不得用镜头盲区制造不可预判失败。

### 4.4 20 关与五章

| 章节 | 关卡 | 新机制与压力 |
| --- | --- | --- |
| 认识路径 | 1–4 | 平面移动、低台跳跃、检查点、首条可选支路 |
| 跨越沟壑 | 5–8 | 坠落恢复、窄桥、分岔路线、连续跳跃 |
| 世界会动 | 9–12 | 往返平台、升降台、节奏门、检查点后的组合段 |
| 风险探索 | 13–16 | 危险地面、巡航障碍、需要观察的隐藏星砂、限时支路 |
| 归航试炼 | 17–20 | 多机制组合、两段检查点、可读但更紧的落点与最终长路线 |

每关必须拥有不同的蓝图签名、主路线长度、平台组合、检查点和星砂位置；允许多关共同强化同一机制，不要求每关都引入新机制。

### 4.5 视觉与声音

- 沉稳高级模板采用深青石、雾蓝远景和暖金导航色；暖金只服务星砂、检查点激活、出口和关键落点。
- 角色、星砂、检查点、出口、危险和移动平台必须使用不同轮廓、明度和运动语言，不只靠颜色区分。
- 保留真实位图角色和环境纹理；程序化几何负责稳定的空间和碰撞，不冒充外部 3D 模型。
- 收集、落地、检查点、复位、出口分别有声音与短反馈；环境音乐不掩盖动作提示。

## 5. 验收

- 20 个蓝图签名唯一，五章机制标记完整。
- 手机 390×844 与桌面 1280×720 首屏不溢出，游戏区不被帮助、设置和长说明遮挡。
- 真实键盘路径完成首关：移动、跳过低障碍、收集至少一枚星砂、激活检查点、抵达终点。
- 真实触控路径至少证明摇杆持续移动与跳跃键独立工作。
- 人为坠落后从最近检查点恢复，位置、容错、短暂无敌和计时状态一致。
- 刷新恢复当前关卡、检查点、已收集星砂与剩余时间；返回启动页不暗中覆盖进度。
- 末关同时出现移动平台、危险、两个检查点和三枚不同风险等级的星砂，并保持可完成。
- 自动完成至少三局、触发两种失败；记录帧档、慢帧降级、暂停和后台停渲染。

## 6. 证据边界

- 任天堂资料证明其公开的目标、检查点、失败与收集分层，不证明本模板采用相同数值会得到相同体验。
- Godot、Three.js、Rapier 和 Open Runner 证明可用的工程边界与公开实现方向，不自动证明本项目已经正确实现。
- 本模板是否放行，只由本项目的真实移动、碰撞、恢复、手机触控、帧节奏、视觉复核和发布闸门决定。
