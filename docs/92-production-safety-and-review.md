# 制作安全与审核权限

更新：2026-09-07。本文描述代码行为，部署和验收结果以实际运行记录为准。

## 原方案与费用边界

- 修改生成必须带上当前已确认方案和修改意见，未提出修改的规则应保留。方案服务没有返回有效结果时停止，不进入代码或图片生成。
- 代码规则审核必须逐条返回完整结果。审核不可用不等于通过，也不授权重新付费生成代码。
- 允许一次针对缺失规则的外层定向修正；修正后仍缺规则，停止生图与交付。代码生成还受共享请求次数上限约束。这是请求次数限制，不是金额预算。
- 生成过程的错误与审核记录进入 `_studio/GENERATION_ATTEMPTS.jsonl`；最终逐条结果进入 `RULE_FIDELITY.json`。
- 复用同项目上一版代码且规则清单未变时，可复用该版已全部通过的规则审核，不再调用审核模型；条件与边界见 [93](93-rule-audit-reuse.md)。未通过或不完整的审核不能复用。
- 图片按封面、动态资源分组保存成功检查点。只有同项目、模型、完整计划、画幅和运行时匹配且字节校验通过才复用。未知结果及失败组不能假定已成功，不自动重试外部付费请求。
- 检查点位于产物根目录的 `_image-checkpoints/<projectId>`，项目删除时一并清理。它不是公开资源，也不是美术审核证据。

## 正式审核与发布

普通创作者可以私下试玩、修改和查看审核记录，不能从创作页自行批准美术审核。

服务端使用独立环境变量 `STUDIO_REVIEW_TOKEN` 配置平台审核凭据。仅平台审核端持有该值，并通过 `x-studio-review-token` 请求头提交正式审核；不得放入前端构建变量、浏览器存储或公开文档。未配置时正式审核请求被拒绝。若还配置了 `STUDIO_ACCESS_TOKEN`，一般访问认证也必须满足，审核凭据不能绕过一般访问控制。

凭据代表“已配置的平台审核端”，**不是实名审核员身份**。服务器写入 `reviewer_id`，不采信请求正文自报身份。历史无可信身份的记录标为未验证；不修改其原始历史。

两个公开发布 API 都在数据库事务内重新检查最新审核：必须通过且带服务端审核身份。后续未通过或未验证的记录会使旧的通过记录不再足以发布。现有已发布版本不因此被静默撤回。私下试玩不需要发布。

部署者需要配置审核凭据并建立可信审核端，才能进行新的正式审核与发布；本次开发不替用户创建凭据，不代替真人做美术批准。

## 仍有边界

不承诺第三方调用严格一次计费、金额级预算、多活调度或任意玩法的完整自然通关。关卡合同检查使用调试接口验证解锁和状态机，不应称为玩家完整游玩。记忆翻牌最终v5另有手机与桌面各七关连续正常点击通关的独立证据，不能外推至其他生成游戏。
