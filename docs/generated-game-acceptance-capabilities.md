状态：通用声明式能力合同仍为设计提案；记忆翻牌的无调试接口真实点击验收已接入运行时。来源：2026-09-06 真实创作验收中的花园记忆翻牌样本。

2026-09-07 更新：有限关卡数量、真实难度维度、无失败策略及无限模式抽样已接入；最终合同同步见[真实链路修复](91-real-creation-closure.md)。下文固定二十关冲突仍适用于legacy路径；完整独立能力合同、无限内容长期供给与其他类型自然输入验收尚未完成。

已落地：翻牌类样本必须在普通游戏地址（无 probe）通过首次配对、教学期间错配自动盖回、继续翻牌检查。该检查实际拦截了一份调试探针全部通过、但教学期间错配冻结的生成物；修正版本 `c610f7f5-b0f6-466c-80f0-9afad252960f` 通过，并由主审核使用普通点击完成首关、结算、重玩和帮助。其他类型仍不能据此宣称已完成专用自然操作验收。

## 必须解决的冲突

补充已落地回归：先错配→正确配对→再错配必须按平台接受状态推进教学，不能在信号被接受之前本地永久去重。第9关教学复演需先通过公开“重看”控件重置教学，再验证正常玩法处理器产生全部信号。最终真实样本574a4dec-76b6-4496-911f-b4d98d0cfa3b通过，并以普通点击完成手机端首关、重玩与帮助。

用户确认的样本是第一关 6 对牌、逐渐增加到 12 对、不倒计时、不失败。当前 `game-generator.ts` 的运行时合同与规模边界却强制 20 关、速度／密度／目标三倍率、固定第 9 关教学、失败钩子与连续失败帮助；`browser-quality.ts` 的 `inspectGeneratedGameInBrowser` 又按同一固定规则验收。生成代码可能忠实实现玩家需求却被拒绝，也可能为通过验收加入用户明确不要的失败或倒计时。

原则：验收应证明游戏遵守设计，而不是强迫游戏改成验收脚本偏好的类型。无法证明的项应是未验证，不能通过虚假钩子补齐。

## 两层合同

1. 平台不可关闭的底线：隔离／安全扫描、禁止未授权网络请求、资源可加载且许可来源明确、真实开始与重开、无运行异常、移动端无横向溢出、可见可触达操作、至少一次正常输入造成实际状态变化、实际加载画面与资源、关键状态可恢复或明确说明不保存、结果可试玩。声明不能禁用这些检查。
2. 按玩法启用的能力：关卡、无限模式、失败、时间压力、敌人、教学、成长、结算。生成前由服务端基于确认方案冻结；不能由被验收的生成代码自报“我不需要这项”来绕过。

每项能力记录 `required | forbidden | not-applicable`、确认方案中的依据及解析置信。未明确的设计细节由策划阶段补足；生产阶段不能擅自增加关数、失败条件或复杂操作。互相矛盾的字段在代码生成前失败，并给出具体冲突。

## 建议的声明式数据

新增版本化 `acceptanceCapabilities`，与完整确认方案共同持久化、序列化并计算哈希；提示词、静态探针、浏览器检查都读取同一份数据。下列是样本目标，不是已经实现的接口：

```json
{
  "schemaVersion": "game-acceptance-capabilities-v1",
  "mode": "campaign",
  "failure": { "policy": "forbidden", "reason": "确认方案：不失败" },
  "timePressure": { "policy": "forbidden", "reason": "确认方案：不倒计时" },
  "progression": {
    "policy": "required",
    "levelCount": null,
    "dimensions": [{ "key": "pairCount", "first": 6, "maximum": 12, "trend": "nondecreasing" }],
    "sampleStrategy": "first-boundary-final"
  },
  "onboarding": { "policy": "required", "actions": ["reveal-card", "resolve-pair"] },
  "completion": { "policy": "required", "predicate": "all-pairs-matched" },
  "assistance": { "trigger": "explicit-request", "failureStreak": "not-applicable" }
}
```

`levelCount: null` 表示尚未明确，绝不代表 20。可在策划中形成明确的 6→7→…→12 七关建议，只有该建议进入确认合同后才能据此验收；也可以确认多关维持同一对数的布局递进。不能让测试自行决定关数。

`dimensions` 仅列此玩法真实存在的难度变量：翻牌是对数、图形相似度、布局；赛车可以是路线与对手表现；射击才可能有速度／密度。对数递增不能同时夹带缩短翻牌观察时间这种未确认压力。

## 浏览器验收如何执行

统一结果为 `passed | failed | not-applicable | unverified`。`not-applicable` 必须有服务端合同依据，不算通过项，也不计入通过率分子。必须能力 `unverified` 不得自动发布。

对花园翻牌，至少执行：

- 开局通过正常点击或键盘开始，检查 12 张牌形成 6 对；验证没有倒计时显示或暗中时间淘汰。
- 正常揭开一张牌再揭开另一张，核实不匹配时确实翻回、已匹配牌不会重新参与配对；不以 `getState()` 文案变化冒充真实牌面变化。
- 持续执行不匹配动作，跨越翻回等待周期，确认仍可继续且没有 `lost`、扣命、强制重开。有限时长测试结合代码规则审计，只能声明已覆盖场景，不声称穷尽所有路径。
- 从探针只读牌面身份来制定解法，逐张使用正常用户输入完成全部匹配；不能直接 `forceWin()` 作为玩法可完成证据。
- 完成时出现真实胜利反馈，下一关数量／布局符合冻结合同，最终不超过 12 对。按实际确认关数选择第一关、规则变化边界关与最后一关，不硬编码第 9／20 关。
- 首次教学可以完成和跳过；需要跨关复习时选实际存在的后期关卡。不要求无时间压力的游戏创造一个假的压力时钟。
- `forceLose()`／连续四败帮助在本样本记为不适用，并检查正常游戏中没有偷偷加入失败。允许保留内部测试工具，但不能要求工具制造合同禁止的产品状态。
- 手机与桌面各至少一套真实输入；布局、控制、胜利画面截图；运行错误、资源请求与交互耗时单独记录。

`forceWin`／`setLevel` 等调试入口只负责复现场景、缩短状态准备；其调用不得替代核心操作通路。可用固定种子与只读局面信息帮助自动玩家求解，调试模式必须与正式玩法共用处理器且不在正常 URL 暴露。

## 最小迁移边界

第一步只接入 `template: generated` 新产物，既有官方游戏与 20 关模板保持原有严验收，避免质量退化。旧 generated 产物继续使用 legacy 验收合同，不通过推测擅自免检。

1. 在确认方案旁新增服务端校验后的能力合同，不覆盖原 profile；优先支持明确的 `failure.policy`、`timePressure.policy`、关数及离散难度变量。
2. `game-generator.ts` 从能力合同组装可选运行时要求，去掉通用段落里的固定 20 关／三倍率／必败要求。安全、资源、输入底线仍无条件注入。
3. `inspectGeneratedArtifact` 静态检查与 `inspectGeneratedGameInBrowser` 同时读取冻结合同。不允许只松浏览器检查而保留矛盾提示词。
4. 审核报告归档能力合同哈希、每项检查、实际输入序列、截图与未验证项。无法求解的游戏标记未验证并阻止自动发布，不凭“页面打开了”认定可玩。
5. 增加正反对照：无失败翻牌通过正常解法；偷偷加倒计时／错误关数／空实现／直接伪造成功信号均应失败；有失败的动作游戏仍须验证失败原因及失败帮助，不能因新增条件化规则免检。

不在本轮顺手修改所有旧模板、拓展任意测试脚本执行权限、相信模型自评得分，或为了过测试重新生成一款与确认方案不符的游戏。
