# M0 实现参考锁

## 设计简报

为不懂代码、希望快速做出单人网页小游戏的创作者设计创建工作台。

- 主要目标：从一个成熟玩法出发，在可控范围内完成改造；如果需求改变核心循环，则清楚转入新游戏设计。
- 主要风险：空白提示词让用户提出无限范围的需求，平台却继续生成一个无法验收的作品。
- 平台：桌面与手机网页。
- 路径：直接实现第一条可运行链路。

## 研究结论

1. Canva Magic Design 先根据用户内容推荐模板，再让用户选择并定制；本项目采用“先选玩法起点，再选择改造方向”的顺序。
2. GDevelop 将游戏模板和能力示例分开陈列；本项目把“完整玩法模板”和“可复用机制”分成两层数据。
3. Scratch Starter Projects 强调从可改造项目开始；本项目保留自由描述，但不再让空白输入框成为默认入口。
4. MDN 将触控与桌面控制视为不同输入环境；本项目在规格阶段就显示手机版适配要求。

## 参考锁

- 主方向：高对比、浅色、偏工具型的创作工作台。
- 必须保留：单一橙色行动色、左侧步骤轨道、正文高可读性、核心规则常驻可见、手机端单列布局。
- 只借用：模板优先的创建顺序、Starter Project 的改造心智、能力示例与完整模板分层。
- 颜色角色：橙色只用于主行动、选择状态和焦点；绿色只表示验证通过；红色只表示阻断或越界。
- 媒体策略：M0 不用游戏截图冒充成品；玩法卡以规则摘要呈现。正式游戏封面和游戏内美术必须由 AI 生成位图提供。
- 拒绝：紫色渐变、暗色默认、装饰性卡片堆叠、空白大输入框、用缩小桌面布局代替手机布局。

## 决策记录

| 决策 | 来源 | 作用 | 原因 |
| --- | --- | --- | --- |
| 先选择玩法模板 | Canva、GDevelop、Scratch | 创建入口 | 降低空白输入造成的范围漂移 |
| 固定建议优先于自由输入 | 用户要求、产品规划 | 改造步骤 | 把用户带到可交付的变化上 |
| R0–R3 即时显示 | 产品规划 | 风险反馈 | 在开始制作前暴露范围变化 |
| 核心规则常驻右侧 | 用户要求、规则合同 | 决策保护 | 让用户知道哪些内容不会被改坏 |
| 手机端改为单列 | MDN 控制机制、本地工艺规范 | 响应式布局 | 防止侧栏遮挡和触控区域过小 |
| 不展示虚构封面 | AI 位图约束、媒体真实性原则 | 模板列表 | 避免占位图被误认为实际游戏品质 |
