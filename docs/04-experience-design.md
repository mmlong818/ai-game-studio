# 网站体验与界面设计

> 历史体验规格。本文记录 2026-08-26 的设计输入，不代表当前页面实现；当前产品规则见 [开发文档导航](README.md)，已实现界面以代码和浏览器测试为准。
> 当前产物是可进入原型阶段的体验规格，不是最终视觉稿。  
> Refero MCP 当前不可用，本轮界面依据官方竞品工作流、本地 refero-design 规范和真实三消案例建立。

## 1. 设计简报

我们正在设计一个**响应式 AI 游戏制作平台**，服务**不懂代码但有游戏想法的中文创作者**，帮助他们**从一句想法走到有测试证据的 2D 或 3D 游戏**。浏览器 2D 是第一条交付链，不是产品的最终边界。产品应像**可信、专注、有创作能量的数字工作室**，而不是聊天机器人或儿童模板站。

用户雇用这个产品完成的工作：

> 把我说不完整的玩法想法变成一款我能亲手玩、继续修改、放心分享的游戏。

最大顾虑：

- “AI 做出来的东西只是看起来像，实际上不能玩。”
- “我不知道它做了什么，也不知道为什么卡住。”
- “改一个地方会不会把之前正常的部分弄坏？”
- “是不是所有作品只是同一个模板换皮？”

第二天应该记住：

> 这里不是承诺生成，而是把每一版做到能玩，并给证据。

## 2. 说服层

| 元素 | 内容 | 界面落点 |
|---|---|---|
| 三秒钩子 | “说玩法，不用说技术。第一版必须能玩。” | 首页首屏主标题 |
| 叙事顺序 | 想法 → 玩法合同 → 制作 → 试玩证据 → 版本 | 首页直接演示一条真实构建带 |
| 反对意见 1 | AI 可能生成坏游戏 | 展示逐项测试、浏览器截图和失败修复 |
| 反对意见 2 | 修改可能破坏旧版本 | 每次修改形成新版本，可回滚 |
| 反对意见 3 | 只是模板换皮 | 展示玩法合同差异和规则模块，不宣传“无限模板” |
| 信任信号 1 | 真实三消样例通过 8 项规则测试 | 首页案例和工作台测试面板 |
| 信任信号 2 | PWA、移动滑动和 Android 包均有实际产物 | 案例产物清单 |
| 信任信号 3 | 明确列出未验证项 | 构建报告和发布确认 |
| 紧迫感 | 不制造虚假倒计时 | 无 |
| 记忆点 | “可玩证据带” | 所有项目页顶部的核心状态带 |

首页不能使用虚构用户、虚构融资数字或没有来源的“成功率”。首轮最可信的证明是我们自己完成并重新验证的三消案例。

## 3. 信息架构

~~~text
/
├─ /new                         新建游戏
├─ /projects                    我的游戏
│  └─ /projects/:projectId
│     ├─ /brief                 想法与关键澄清
│     ├─ /contract              玩法合同
│     ├─ /studio                制作工作台
│     ├─ /assets                资源与来源
│     ├─ /tests                 验收与证据
│     └─ /versions              版本与回滚
├─ /deployments                 发布、网址和运行状态
└─ 独立游戏域名                 玩家公开游戏，不暴露工作台
~~~

首版不单独建设社区首页、素材市场和复杂账户后台。

## 4. 首页

### 首屏

不是“左文字 + 右抽象 AI 插画”。首屏本身就是一个可理解的制作演示：

~~~text
┌──────────────────────────────────────────────────────────────────┐
│ AI 游戏工坊                                      登录   我的游戏 │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  说玩法，不用说技术。                                             │
│  第一版必须能玩。                                                 │
│                                                                  │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │ 做一个玩家与 AI 共用棋盘的三消对战……                      │  │
│  │                                                [开始制作] │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
│  想法 ━ 玩法合同 ━ 核心规则 ━ 资源 ━ 浏览器试玩 ━ 8/8 通过      │
│                                         [直接试玩星梦对决]       │
│  当前已验证：Web 2D 黄金链 · 路线：多玩法 → Web 3D → 引擎工程  │
└──────────────────────────────────────────────────────────────────┘
~~~

输入框下方只提供三类高质量示例：

- 一分钟反应或益智。
- 竖屏单手动作。
- 教学互动或知识对战。

不展示十几个类型标签，避免把首页变成模板市场。

### 证明区

使用真实案例拆解：

1. 用户原话。
2. 系统保留的硬约束。
3. 生成的玩法合同。
4. 实际文件和发布包。
5. 通过与失败过的测试。
6. 一次修改如何只影响对应规则。

这比普通的三列功能卡更能回答“它是否真的工作”。

## 5. 新建流程

### 第一步：表达想法

- 一个主输入框。
- 可选参考图。
- 可选语音转文字后置。
- 输入时实时抽取“可能的核心循环”和“仍缺的信息”，但不打断用户。

推荐文案：

> 说清楚玩家反复做什么、怎么输赢，以及你最不愿被改掉的一条规则。

### 第二步：关键澄清

最多三个问题，每个问题必须满足“不同答案会改变核心玩法、平台或成本”。

~~~text
你说“AI 对战”，更接近哪一种？

[轮流操作同一局面 · 推荐]
双方会互相改变对方下一步，规则更容易看懂。

[双方同时行动]
节奏更快，但移动端和结果归属更复杂。

[各玩各的最后比成绩]
实现最稳，但对抗感较弱。
~~~

系统推荐项放第一，并用普通后果解释，不暴露内部工程偏好。

### 第三步：玩法合同

合同分成四块：

- **游戏承诺**：一句话说明玩家会得到什么体验。
- **必须遵守**：用户硬约束。
- **第一版包含**：P0。
- **这次不做**：明确范围。

下方是验收清单和预计消耗。主按钮使用具体文案“按这份合同开始制作”，不写模糊的“继续”。

## 6. 制作工作台

### 6.1 桌面布局

~~~text
┌────────────────────────────────────────────────────────────────────────────┐
│ 星梦对决  v3  ● 正在试玩    想法—合同—核心—资源—构建—试玩—可玩  额度  发布 │
├──────────────────┬────────────────────────────┬────────────────────────────┤
│ 指令与制作记录    │ 可玩预览                   │ 合同 / 测试 / 资源 / 文件  │
│                  │                            │                            │
│ 你：把基础伤害…  │  ┌──────────────────────┐  │ 本次变化                   │
│ 变化合同 ✓       │  │                      │  │ 5 → 8                      │
│ 修改规则核心 ✓   │  │     当前游戏画面      │  │ 不应变化                   │
│ 单元测试 8/8 ✓   │  │                      │  │ 区域权限、连消归属         │
│ 浏览器试玩 4/5   │  └──────────────────────┘  │                            │
│ 移动端布局修复中 │                            │ 验收                       │
│                  │ [桌面] [手机] [重新开始]   │ M3-01 ✓ ... M3-12 待检查   │
│ [描述下一次修改] │                            │                            │
└──────────────────┴────────────────────────────┴────────────────────────────┘
~~~

### 6.2 可玩证据带

顶部不是假进度条，而是由后端事件计算的阶段带：

- 未开始：空心。
- 执行中：短促脉冲和真实步骤名称。
- 通过：显示测试数量。
- 失败：显示失败类型和最近成功版本。
- 跳过：说明原因，例如“P0 使用程序化音效，未生成音乐”。

点击任何阶段会筛选左侧时间线和右侧证据。URL 保存所选阶段。

### 6.3 指令与制作记录

把用户消息和系统动作放在同一时间轴，但视觉上明确区分：

- 用户指令。
- 计划/变化合同。
- 工具动作摘要。
- 产物。
- 测试。
- 错误和修复。

默认只显示可理解摘要，例如：

> 验证手机竖屏：开始按钮被底部安全区遮挡。

展开后显示：

> viewport 390×844，DPR=3；按钮底部超出安全区 18px。

原始日志继续放在三级详情中，并过滤令牌、绝对内部路径和环境变量。

### 6.4 右侧检查器

四个页签：

- **合同**：硬约束、变化范围和非目标。
- **测试**：验收、截图、回放、浏览器环境。
- **资源**：图片、音频、字体、来源、许可证和派生关系。
- **文件**：首版只读，显示本次变化和构建状态。

测试失败时自动切到测试页签，但不抢走正在输入文本的焦点。

## 7. 失败与恢复

### 可自动修复

显示：

- 失败发生在哪个阶段。
- 用户能理解的原因。
- 第几次修复。
- 修复会重新运行哪些测试。
- 当前仍可玩的版本。

### 达到上限

~~~text
这次修改没有达到可发布标准。

仍可使用：v3（12 项验收全部通过）
未完成：手机 DPR=3 时结算弹窗超出安全区
已尝试：2 次自动修复

[回到 v3]  [保留草稿查看详情]
~~~

不使用“未知错误，请重试”结束流程。

## 8. 版本和发布

版本列表应突出：

- 来自哪条用户指令。
- 改了哪些合同项。
- 哪些测试通过。
- 预览截图。
- 父版本。
- 是否已经公开。

发布创建不可变快照并部署到独立游戏来源。后续修改只发生在草稿分支，稳定玩家网址继续指向已发布版本，直到用户明确更新。

发布完成卡必须显示：

- 稳定玩家网址，可复制、打开和生成二维码。
- 当前指向的版本与发布时间。
- 永久版本网址，便于复核和回滚。
- HTTPS、资源加载、冒烟试玩和数据服务状态。
- 访问设备、加载时间和错误概览。
- “更新线上版本”和“回退线上版本”两个明确动作。

网址分为三类，不能混在一起：

| 网址 | 面向谁 | 生命周期 |
|---|---|---|
| 构建预览网址 | 创作者和测试器 | 短期、受保护，可过期 |
| 不可变版本网址 | 验收、审计、回滚 | 永久指向同一版本 |
| 稳定玩家网址 | 最终玩家 | 长期不变，可切换到新版本 |

公开玩家页首版只包含：

- 游戏画面。
- 游戏名称和简短说明。
- 操作提示。
- 全屏、静音和重开。
- 版本与作者。
- 举报入口。

玩家网址本身必须有独立标题、封面、图标、分享卡和加载页。横屏、竖屏和 3D 游戏分别给出正确的旋转、性能和操作提示；玩家不应看到制作日志、模型信息或项目内部 ID。

评论、点赞、重混和推荐流后置。

## 9. 移动端

工作台在手机上使用三个一级页签：

- **制作**：指令和时间线。
- **试玩**：沉浸式游戏和设备控制。
- **证据**：合同、测试、资源和版本。

规则：

- 不把三栏缩成三条窄列。
- 底部输入框不被软键盘遮挡。
- 试玩进入全屏后保留明显返回。
- 触控目标至少 44×44 像素。
- 不依赖悬停显示关键操作。
- 支持系统减少动画设置。

## 10. 视觉系统

### 10.1 方向

工作台使用深色石墨底，让生成游戏本身成为画面中最鲜艳的内容；品牌强调色选择“熔炉橙”，表达制作、迭代和能量，不使用常见的紫蓝 AI 渐变。

~~~css
:root {
  --bg: #10110f;
  --surface-1: #171815;
  --surface-2: #1e201c;
  --surface-3: #272923;
  --border: #30332c;
  --border-strong: #44483d;

  --text: #f3f0e7;
  --text-muted: #b7b3a9;
  --text-subtle: #8d8a82;

  --primary: #e2642f;
  --primary-hover: #f0743c;
  --primary-active: #c95024;
  --on-primary: #15100d;

  --success: #49a878;
  --warning: #d5a13d;
  --danger: #db5c50;
  --info: #5b91c9;
}
~~~

语义颜色只表达状态，不当装饰。页面 70%—90% 使用中性色。

### 10.2 字体

- 中文 UI：Noto Sans SC、系统中文无衬线回退。
- 英文与数字：同一 UI 字体，不额外引入装饰字体。
- 文件、日志和探针：JetBrains Mono 或系统等宽字体。
- 生产只使用 400、500、600 三个字重。
- 正文至少 16px，行高 1.5。
- 小标签 12—13px，增加 0.01—0.02em 字距。
- 全大写状态标签增加约 0.08em 字距。
- 全站控制在 7 个字号层级。

### 10.3 间距与形状

- 4px 基础网格：4、8、12、16、24、32、48、64。
- 工作台面板圆角 10px，控件圆角 8px；不使用到处都是的大胶囊。
- 层级主要靠底色、边框和间距，不依赖重阴影。
- 游戏预览可使用更清晰的 1px 边框和独立背景，不套发光霓虹框。

### 10.4 图标

- 使用一套 2px 描边的 Lucide 图标。
- 状态同时使用图标、文字和颜色。
- 不用 emoji 代替产品图标。
- 图标按钮提供 aria-label，桌面命中至少 32px，触控至少 44px。

### 10.5 动效

- 按压：90—120ms。
- 页签与折叠：160—220ms。
- 面板切换：240—320ms。
- 构建中的脉冲只作用于一个当前阶段。
- 所有非必要动效支持 prefers-reduced-motion。
- 不使用超过 500ms 的产品界面动画。

## 11. 组件状态

首轮原型必须覆盖：

- 项目空状态。
- 首次澄清。
- 合同待确认。
- 排队、执行、暂停、取消。
- 首次构建失败。
- 自动修复中。
- 达到预算/重试上限。
- 可玩但部分 P1 跳过。
- 发布中、发布失败、已发布。
- 版本冲突和回滚确认。
- 预览崩溃但工作台正常。
- 资源生成失败但占位资源可用。

## 12. 可用性和无障碍门槛

- 所有按钮、输入和页签可用键盘操作。
- 使用 focus-visible，不移除焦点而不给替代样式。
- 文本对比度达到 WCAG AA。
- 构建状态使用 aria-live polite。
- 失败摘要使用 role alert，但不重复播报每条日志。
- URL 反映项目、版本、页签、阶段和预览设备。
- 图片有尺寸，避免加载时布局跳动。
- 长日志虚拟化或使用 content-visibility。
- 禁止 user-scalable=no。
- 所有错误文案包含下一步或自动恢复说明。

## 13. 原型验收

高保真原型进入实现前必须能演示：

1. 从首页输入第一款黄金游戏的三消想法；界面同时清楚说明平台的多玩法与 3D 路线。
2. 回答一个关键歧义。
3. 检查并确认玩法合同。
4. 进入构建，看到真实阶段与产物。
5. 从失败测试定位到修复。
6. 在桌面和手机画幅试玩。
7. 提出局部修改并看到变化合同。
8. 在版本间比较和回滚。
9. 发布不可变版本。

如果原型只能展示静态“聊天 + 游戏图片”，则没有表达产品真正的可信闭环。
